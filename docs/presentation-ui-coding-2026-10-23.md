## 2. 그대로 말할 수 있는 발표 문구 — 약 2분

안녕하세요. 저는 프로젝트에서 UI/UX와 코딩 도움 카테고리를 담당했습니다.

저희 도구는 사용자가 원하는 AI 응답 방식을 복잡한 프롬프트로 직접 설명하는 대신, 두 결과 중 더 마음에 드는 쪽을 선택하면서 개인화된 시스템 프롬프트를 만드는 도구입니다.

먼저 UI/UX에서는 사용자가 어떤 순서로 사용해야 하는지 쉽게 이해하도록 카테고리 선택, 기능 입력, A/B 비교, 결과 확인 흐름을 구성했습니다. 화면 전환과 카드 애니메이션으로 현재 단계에 집중할 수 있게 하고, 전문 용어 대신 ‘역할별 파일로 분리’, ‘타입을 꼼꼼하게 작성’ 같은 표현을 사용했습니다. 선호가 없을 때는 ‘비슷해요’를 선택하고, 잘못 고른 경우 이전 선택을 수정할 수 있습니다. 마지막에는 만들어진 프롬프트를 확인하고 복사해서 다른 AI 도구에서도 사용할 수 있게 했습니다.

코딩 도움은 사용자가 만들고 싶은 기능을 입력하면 React·TypeScript 코드 A/B를 생성하고, 그중 선호하는 방식을 선택하는 기능입니다. 비교하는 기준은 코드 구조, 스타일 관리 방식, 타입 작성 방식 세 가지입니다. 예를 들어 같은 카운터를 한 파일로 작성할지 역할별 파일로 나눌지 비교하는 방식입니다. 기능의 좋고 나쁨보다 같은 기능을 어떤 방식으로 작성하는 것을 선호하는지 찾는 데 목적이 있습니다.

선택 결과는 ‘컴포넌트와 로직을 분리하고, 디자인 값은 테마로 관리하며, 타입을 명시하라’와 같은 재사용 가능한 지침으로 정리됩니다. 공통 선호 추정 엔진을 활용하고, 코딩 전용 규칙과 검사 로직을 연결했습니다. 모델 자체를 학습시키는 방식은 아닙니다.

실제 AI 호출을 이용한 기존 자동 검증에서는 서로 반대 취향을 설정한 가상 사용자 두 경우를 확인했습니다. 일부 타입 누락을 수정한 뒤 총 14개 코드 결과가 타입, 빌드, 지정 동작, 스타일 검사를 통과했습니다. 다만 이것은 정해진 조건의 자동 검증이며, 실제 사람의 만족도나 모든 기능 입력의 품질을 보장하는 결과는 아닙니다.

현재는 주요 기능이 통합돼 있고, 마지막 추가 검사와 검증 자료 커밋의 반영 여부를 확인해야 합니다. 발표에서는 무료 데모로 조작 흐름을 보여주고, 실제 AI 검증 결과는 별도 기록으로 설명하겠습니다.

## 3. UI/UX를 따로 설명할 때

### 왜 이렇게 구성했는가

사용자가 코딩 용어를 정확하게 모르더라도 예시를 비교해서 선택할 수 있도록 하는 것이 목적입니다. 애니메이션 자체가 핵심 기능은 아니며, 단계가 바뀌었다는 것을 알려주고 선택할 대상에 집중시키는 보조 수단입니다.

### 구현 범위

- 핵심·실험실 카테고리 구분과 카드 선택 흐름.
- 기능 입력 → A/B 비교 → 선호 결과·프롬프트 확인 흐름.
- ‘비슷해요’, 이전 선택 수정, 코드 전체 보기.
- 로그인 등 공통 기능과의 연결, 로딩·오류·빈 입력 안내.
- 프롬프트 복사, 개발 요청을 포함한 복사.
- 작은 화면 대응과 실제 AI·무료 데모의 구분.

로그인·팀 기능·공통 엔진 전체를 혼자 구현했다고 설명하지 않습니다. 자신의 화면 작업과 기능 연결, 팀에서 추가한 공통 기능을 구분합니다.

### 검증을 설명하는 문구

“10월 15일 작업 브랜치의 브라우저 검수 기록에는 가입·로그인·로그아웃, 선택과 이전 선택 수정, 결과·복사, 작은 화면 확인이 있습니다. 오늘은 그 이후 master에 들어간 화면 변경을 코드로 확인했으며, 최신 master 전체를 다시 조작 검수한 것은 아닙니다.”

## 4. 코딩 도움의 동작을 쉽게 설명하기

1. 사용자가 만들고 싶은 기능을 입력합니다.
2. 실제 AI 모드에서는 입력한 기능에 맞는 A/B 코드를 생성합니다.
3. 같은 기능을 유지하면서 특정 스타일 차이를 비교하도록 생성 지침과 검사 규칙을 적용합니다.
4. 사용자의 선택을 공통 선호 추정 엔진에 전달합니다. 선택이 애매한 축은 확정된 취향처럼 다루지 않습니다.
5. 코드 구조·스타일 관리·타입 작성 선호를 시스템 프롬프트로 만듭니다.
6. 사용자가 이 프롬프트를 자신의 개발 요청과 함께 재사용합니다.

| 비교 축 | 사용자에게 설명할 표현 | 결과 지침 예시 |
| --- | --- | --- |
| 코드 구조 | 간결하게 작성 / 역할별 파일로 분리 | 작은 기능은 한 파일에 작성 / 컴포넌트와 로직을 분리 |
| 스타일 관리 | 값을 직접 작성 / 나중에 전체 디자인을 쉽게 수정 | 스타일 값을 직접 지정 / 테마·디자인 토큰으로 관리 |
| 타입 작성 | 단순한 타입은 자동으로 / 타입을 꼼꼼하게 작성 | 추론 활용 / Props·매개변수·반환값 타입 명시 |

React 화면은 JavaScript·JSX 기반입니다. TypeScript는 코딩 도움에서 생성·비교하는 코드의 대상이므로, 프론트 전체를 TypeScript로 만들었다고 설명하지 않습니다.

### 실제 AI와 무료 데모

- 실제 AI: 사용자 요청을 바탕으로 새 코드를 생성합니다. API 사용량이 발생합니다.
- 무료 데모: 준비된 과제로 비교·선호 반영 흐름을 체험합니다. 임의 기능을 실제 구현한 결과가 아닙니다.
- API 실패 후 데모로 전환되었다면 실제 생성 성공으로 집계하지 않습니다.

### 모델 설명 — 오늘 확인한 저장소 기본 설정

코딩 생성의 기본 설정은 `openai/gpt-6-luna`입니다. 같은 모델의 수정 시도 이후에도 검사를 통과하지 못하면, 설정된 경우 `openai/gpt-6.1-sol`로 제한적으로 전환하는 구조입니다. 환경변수로 달라질 수 있으며, 실제 실행 모델은 해당 실행 기록을 기준으로 설명해야 합니다.

선택 이유는 일반 생성 비용을 줄이고, 검사 실패 시에만 더 큰 모델을 사용하는 비용·품질 절충입니다. 모든 모델을 동일 조건에서 비교해 이 조합의 우월성을 입증했다는 뜻은 아닙니다. 위 이름은 저장소의 설정값이며, 오늘 제공업체의 모델 제공 여부나 가격을 새로 확인한 결과는 아닙니다.

GEPA는 별도의 선택적 프롬프트 최적화 과정입니다. 코드 생성 실패 시 모델을 전환하는 과정과 다르며, 모델 학습·파인튜닝도 아닙니다.

## 6. 시연 순서 — 약 3분

1. 발표 전에 서버·프론트를 실행하고, 어떤 브랜치의 화면인지 확인합니다. 준비된 무료 데모를 사용할 경우 처음부터 그렇게 안내합니다.
2. “원하는 코딩 방식을 말로 설명하지 않고 비교해서 고르는 흐름을 보여드리겠습니다”라고 소개합니다.
3. 코딩 도움으로 이동하여 준비된 카운터 과제를 선택하거나 안내된 입력을 사용합니다. 데모가 입력 전체를 구현했다고 말하지 않습니다.
4. 두 코드의 기능은 같고 표현 방식이 다른 비교 의도를 설명합니다. 역할별 분리·테마·타입 명시 중 실제 화면에서 보이는 차이를 짚습니다.
5. 한 번은 ‘비슷해요’를 선택하고, 이전 선택 수정도 보여줍니다.
6. 선택을 마친 뒤 최종 지침과 선택 내용의 연결을 보여주고 프롬프트를 복사합니다.
7. 실제 AI 검증은 저장된 결과와 비용 표로 별도 설명합니다. 무료 시연을 실제 AI 성능 증거로 사용하지 않습니다.

발표 중 유료 호출을 반복할 필요는 없습니다. 실제 AI 시연을 추가한다면 키·연결·호출 한도를 별도로 확인하고, 실패 시 무료 데모임을 밝힌 상태로 전환합니다.

## 7. 예상 질문과 답변

**그냥 AI에게 코딩을 부탁하는 것과 무엇이 다른가요?**

일반 코드 생성보다, 여러 선택에서 반복되는 사용자의 작성 방식 선호를 정리하는 데 초점을 둡니다. 결과는 특정 코드 한 개가 아니라 다음 개발 요청에도 붙여 쓸 수 있는 지침입니다.

**사용자가 원하는 기능도 AI가 만드는 건가요?**

실제 AI 모드에서는 그렇습니다. 무료 데모는 준비된 과제를 사용하므로 구분해서 설명합니다.

**두 코드가 정말 같은 기능인지 어떻게 아나요?**

같은 요구사항과 비교 축을 지정하고 코드 검사도 적용합니다. 기존 검증에서는 지정된 과제의 타입·빌드·동작도 확인했습니다. 하지만 모든 임의 입력에서 기능이 완전히 같다고 보장하지는 않습니다.

**가상 사용자 두 명이 실제로 사용한 건가요?**

아닙니다. 서로 반대인 취향을 미리 정한 자동 선택 시나리오 두 개입니다. 선호가 결과에 반영되는지를 확인하는 기능 검증이며, 실제 사람의 사용성·만족도 평가는 별도로 필요합니다.

**학습 데이터로 AI를 학습시킨 건가요?**

아닙니다. 준비한 비교 자료와 실제 생성 결과를 검사에 사용했고, 사용자 선택으로 선호를 추정해 프롬프트를 구성합니다. 언어 모델의 가중치를 학습하지 않습니다.

**그 금액이 실제 결제된 금액인가요?**

아닙니다. 확인 가능한 호출 기록의 토큰 수에 당시 기록된 단가를 적용한 금액입니다. 제공업체 청구 내역과 대조한 실제 청구액은 확인하지 않았습니다.

**직접 만든 부분은 무엇인가요?**

저는 React 화면의 선택·비교·결과 흐름과 기능 연결, 코딩 도메인의 비교 기준·예시·검사·검증 자료를 중심으로 작업했습니다. 선호 추정 엔진과 GEPA 같은 공통 기반은 재사용하며 팀 작업과 구분합니다.

**완전히 끝났나요?**

주요 구현과 제한된 조건의 검증 기록은 있습니다. 다만 마지막 추가 검사 커밋의 통합, 최신 master의 실행 검수, 실제 사람 평가와 실제 청구액 대조까지 끝났다고 말할 수는 없습니다.

## 8. 발표 직전 남은 확인

- `002ff5f`의 추가 검사·복사 안내 변경을 master와 비교해 필요한 부분만 통합할지 결정합니다.

### 중요한 해석 정정

- B의 0.668은 실제 사용자가 작성한 개인 지침이 아니라 실험자가 정한 일반 지침 하나다.
- D의 0.996은 GEPA 결과가 아니라 8회 모의 선택 후 조립한 프롬프트의 checks 점수다.
- ROUGE-L 0.207 vs 0.168은 n=5의 결과다. 서로 다른 지표 0.996과 0.207을 같은 척도의 하락처럼 해석하지 않는다.
- checks-v-labels 5,379개는 train/val/test 통합 진단이다. 예전에 보정한 자료를 포함해 신규 홀드아웃이 아니다.
- 외부 라벨에서 검사 정확도가 높아져도 같은 검사로 최적화·채점하는 자기평가 문제는 별도로 남는다.
- 0.49/0.61은 탐색한 단일 측정값 임계값의 최고 관측값이지 모든 모델의 성능 상한이 아니다.
- 형식 거리 개선은 지식·사실성 개선과 다르다. ROUGE만으로 지식 이전의 부재도 확정하지 않는다.
- p=0.008은 반복 탐색 뒤 얻은 제한된 저자 표본의 결과로, 새 표본에서 재현할 대상이다.
- 8회는 현재 제품 예산이다. 모든 사용자에게 충분하다는 보장은 없으며, 기존 사례에서 long/normal 혼동도 있었다.
- 전문가 UI는 답변만 입력받는다. 원문 길이가 없으므로 절대 분량과 압축률 중 무엇이 적합한지 실제로 판별하지 못한다.

### 운영에서 확인한 사실

- GitHub 실제 default branch는 master이며 smoke-live 워크플로가 존재했다.
- 확인 시 최근 3회 Actions는 성공이었다. 이 사실만으로 API 생성까지 정상임을 뜻하지 않는다.
- 스모크는 제목·선택 위젯·일부 오류 문자열만 확인한다. 최신 커밋 여부나 8회 완주를 보지 않는다.
- 앱 배포는 submission, 예약 실행은 master다. 양쪽 스모크 코드 차이를 관리해야 한다.
- DailyBudget은 메모리에 있어 재시작하면 초기화된다. 호출 횟수와 실제 토큰 비용은 다르다.
- generator의 원자적 파일 쓰기는 JSON 손상을 막지만 같은 키의 동시 캐시 미스 중복 호출을 막지는 않는다.
- 공개 앱에서 연구용 생성 코드 실행을 활성화하지 않는다. 이번 방어 보완을 완전한 샌드박스로 표현하지 않는다.

## 바로 사용할 실사용자 검증안

1. 먼저 한국어 요약에 집중한다. 별도 카테고리까지 동시에 모집해 표본을 지나치게 나누지 않는다.
2. 파일럿 5~8명은 통계적 우위 증명이 아니라 불편·실패 유형을 찾는 목적이다.
3. 사용자마다 기준 문서 1개로 지침 직접 작성과 8회 선택을 모두 수행한다. 수행 순서는 번갈아 배정하고 시간을 잰다.
4. 작성한 지침은 고정한다. 새 문서 3개에 같은 모델·생성 설정으로 각각 적용한다.
5. 결과물의 방식 이름을 숨기고 좌우를 무작위 배치한다. 선호 A/B/동률, 선호 이유, 사실 오류·핵심 누락을 각각 기록한다.
6. 한 사람이 3개를 평가했다고 3명의 독립 표본처럼 세지 않는다. 사용자별 승률·동률·시간 차이와 개별 사례를 먼저 보고한다.
7. 개발용·최종 평가 자료를 source ID로 분리한다. 실패를 보고 수정했다면 해당 자료는 개발 자료가 된 것이므로 새로운 최종 평가 자료를 준비한다.
8. 파일럿 후 효과 크기와 변동을 보고 본실험 모집 수를 정한다. 지금 임의의 N으로 유의성 보장을 약속하지 않는다.

### 비교군과 기록 필드

| 비교군 | 내용 |
|---|---|
| 기본 | 작업·출력 언어만 지정한 지침 |
| 직접 작성 | 사용자가 자기 요구를 직접 작성, 시간 기록 |
| LLM 지침 생성 | 동일한 사용자 정보로 모델이 만든 지침; 수집 노력도 기록 |
| 8회 선택 조립 | 현재 앱의 기본 산출물 |
| 조립 + GEPA | 비용·대기 시간 대비 추가 효과를 별도 비교 |

기록 필드: participant_id(임의 ID), domain, source_id, split, condition,
model/version, prompt_version, seed, 생성 파라미터, 입력·출력 토큰,
캐시 적중, 총 시간, 완료/이탈, 좌우 배치, 선호/동률, 사실 오류, 핵심 누락,
주관적 만족, 수정 시간, 테스트 응답 여부. 불필요한 실명·민감 원문은 수집하지 않는다.
모든 카테고리에 ROUGE 하나를 적용하지 않는다. 코딩은 기능, 이메일은 요청 보존,
요약은 사실·핵심 보존을 선호와 별도 축으로 평가한다.

## 사용자에게 필요한 자료

개발과 무과금 테스트는 추가 자료 없이 계속할 수 있다. 실제 효과 검증에는 다음이 필요하다.

- 우선 검증할 실제 작업: 기본 제안은 한국어 기사/업무 문서 요약. 본인이 자주 하는 업무가 다르면 그걸 우선한다.
- 공유 권한이 있는 예시 5개: 원문/요청, 본인이 원하는 결과, 싫었던 결과 또는 이유. 이름·전화·비공개 업무 내용은 제거한다.
- 사용해 볼 사람 5~8명 모집 가능 여부. 실제 응답은 대신 만들어 넣을 수 없다.
- 전문가 경로를 검증하려면 가능할 때 본인 작성 (질문, 답변) 쌍 약 30개와 별도 평가 쌍. 30개는 제품 권장치이지 정확도 보장선이 아니다.
- 운영 한도를 정하려면 감당할 하루/월 비용과 예상 동시 사용 인원. API 키 자체는 제공할 필요가 없다.

```text
예시 ID:
카테고리 / 언어:
원문 또는 작업 요청:
내가 원하는 결과:
싫었던 결과 또는 아쉬운 이유:
꼭 보존해야 할 정보:
실험 사용·공유 가능 범위:
```

## 예상 질문에 대한 현재 답

- 사람이 쓴 프롬프트를 이겼나? → 기존 B는 고정 일반 지침이다. 실사용자 직접 작성 비교는 남아 있다.
- 검사 함수가 검증됐나? → 코드 계약과 일부 동작은 검증했다. 사람 라벨 재현은 제한적이며 통합 표본 균형정확도 length .446 / extractiveness .598이다.
- GEPA가 꼭 필요한가? → 앱은 조립만으로 결과를 준다. 일반화된 추가 효용은 독립 평가에서 확인해야 한다.
- 5종 모두 효과가 있나? → 기능 연결과 개인화 효과 검증은 구분한다. 각 카테고리의 현재 근거는 위 표와 같다.
- 전문가 에이전트를 만드는가? → 현재 앱은 글의 분량·문장 지침을 만든다. 지식 검색·도구 사용·자율 작업 수행 에이전트는 아니다.
- 자료가 내 컴퓨터 안에만 있나? → 배포 앱에서는 서버로 전송된다. 전문가 경로가 모델 API를 호출하지 않는다는 뜻과 다르다.

PPTX와 과거 개발 이력은 이번 코드 변경만으로 자동 갱신되지 않는다.

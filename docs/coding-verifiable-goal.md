# 최종 개발 목표: 지정한 코딩 조건의 전달·재사용·검증

2026-11-10. 실사용자 평가 결과를 확보하지 못한다는 조건을 반영한 개발 범위다. 앞서 정한 편의성 평가는 선택적 후속 연구로 남긴다.

## 2026-11-12 현재 제품 검증 추가

[현재 TypeScript/React 4항목 지침 비교](../benchmarks/coding_react_current/README.md)는 이 문서의 별도
6조합 프로토타입과 구분해 실행했다. 새 합성 과제 8개에서 일반 요청·강한 수동 지침·현재 제품 지침의
첫 응답 24개를 보존하고 strict 타입 검사, 실제 ReactDOM/JSDOM 동작, 네 답변 조건을 분리했다.
타입·동작은 세 방식 모두 8/8 과제와 69/69 동작 검사 통과, 네 조건 모두 일치는 0/8·8/8·8/8이었다
(두 독립 검토자 일치). 수동·제품 각 1개의 일본어 주석은 별도 관찰로 남겼다.

현재 제품의 제한된 기술적 근거가 추가됐으며, 아래 6조합 프로토타입의 상태표는 그대로 보존한다.
수동 지침 대비 우위·전체 환경의 정확도·React 코드 스타일 비교·사람의 편의성과 수정 시간은 입증하지 않았다.
제품 지침은 변경하지 않았다. 유료 모델 API를 사용하지 않았고 Codex 사용량은 소비됐다.

## 목표

**사용자가 명시적으로 선택한 코딩 답변 조건을 재사용 가능한 프롬프트로 만들고, 새 작업의 답변에서 조건 준수와 기능 정확도를 분리해 확인하는 도구를 완성한다.**

성과 주장은 ‘검사한 과제에서 지정 조건이 반영됐는가’로 한정한다. 숨은 취향 발견, 만족도, 사람의 수정 시간 단축, 팀 생산성은 이번 완료 조건이 아니다. 사람이 참여하지 않아도 기술적 실험은 가능하지만, 논문의 다른 참가자 결과나 에이전트를 우리 사용자의 결과로 바꾸지 않는다.

## 제품 범위와 두 기능

- **AI 답변 방식 설정:** 설명·주석·구성·출력을 정하는 기존 기능을 유지한다. 새 검증 프롬프트는 우선 설명 형식·전달 형식의 명시적 조건으로 좁혀 시험한다.
- **React 코드 스타일 비교:** 기존 구성·스타일 관리·타입 작성 비교와 저장 기록을 유지한다. 같은 코딩 도움에서 별도로 진입한다. 이 경로의 선호 추정을 새 형식 검사와 합산하지 않는다.
- 첫 검증 대상은 TypeScript/React의 작은 단일 파일 컴포넌트다. 다른 환경, 팀 기능 확대, 자동 GEPA 탐색은 필수 범위에 추가하지 않는다.
- `benchmarks/coding_contract_v1`은 **실행 가능한 별도 프로토타입**이다. 기존 4항목 지침과 저장본을 교체하지 않았다. 검증 후 기본 UI에 연결할 대상이며, 현재 제품 전체가 새 방식으로 전환됐다는 뜻은 아니다.

## 연구 근거와 적용 한계

| 근거 | 채택하는 방법 | 입증하지 않는 것 |
|---|---|---|
| [IFEval](https://arxiv.org/abs/2311.07911) | 프로그램이 판정할 수 있는 명시적 지시를 분리한다 | 우리 선택 횟수의 적정성·사람의 취향 |
| [CodeIF, ACL Industry 2025](https://aclanthology.org/2025.acl-industry.89/) | 코딩 과제에서도 기능 요구와 지시 준수를 평가 대상으로 삼는다 | 현재 React 검사기의 정확성·우리 제품의 우위 |
| [RACE](https://arxiv.org/abs/2407.11470) | 기능 정확도와 요청된 코드 특성을 나누어 평가한다 | 주석/함수 개수만으로 의미적 품질 판단 |
| [EvalPlus](https://github.com/evalplus/evalplus) | 별도 실행 테스트로 기능을 확인한다 | Python 함수 벤치마크로 React 화면 전체 검증 |

이는 평가 방법을 선택하는 근거다. 위 연구가 우리 프롬프트의 효과를 대신 검증하지 않는다. 이번 프로토타입의 설명 개수·파일 형식·질문 수는 **프로젝트가 정한 측정 가능한 계약**이며 논문이 도출한 최적값이 아니다.

## 선택과 프롬프트 생성 절차

1. 개발 환경과 지원 범위를 확인한다. 검증 v1은 TypeScript/React 단일 파일이다.
2. **설명 방식:** 코드만 / 짧은 설명 1~3항목 / 단계 설명 3~5항목.
3. **전달 형식:** Markdown 파일·코드 / 도구에서 읽을 JSON.
4. 필요한 경우 해당 항목의 예시를 본다. 두 값이 정해지면 최종 규칙을 확인하고 생성한다. A/B 비교를 정해진 횟수만큼 채우거나 반복 일치를 추정할 필요가 없다.
5. 지침은 작업 내용 없이 저장하고, 작업 요청만 바꾸어 재사용한다.
6. 받은 답변을 검사해 형식 조건, 문법, 실제 기능, 미검증 항목을 별도로 보여 준다.

두 항목을 직접 선택하면 A/B 비교는 0회다. 예시는 선택을 이해하기 위한 자료이며 표본 수가 아니다. 기존 1~8회 비교 UI는 이 프로토타입 도입 전에 임의로 삭제하거나 새 횟수의 효과가 검증됐다고 표시하지 않는다.

‘핵심 주석이 적절한가’, ‘역할 분리가 좋은가’, ‘설명이 유용한가’는 자동 정답으로 만들지 않는다. 해당 선호를 계속 쓸 수는 있지만 결과에는 의미적 품질 미측정으로 남긴다. 파일 수나 주석 수를 늘리는 것으로 성공 점수를 만들지 않는다.

## 평가 설계

검사기 준비 → 개발 과제 점검 → 최종 과제 고정 → 생성 → 독립 실행 검사 순서다. 생성 결과를 본 뒤 최종 평가 기준을 유리하게 바꾸지 않는다.

- **비교 조건:** 일반 작업 요청, 동일 제약을 직접 적은 지침, 우리 조립 지침. 같은 최종 규칙을 주는 두 입력 방식은 입력 방식의 우위를 검증하는 별도 조건으로 세지 않는다.
- **통제:** 같은 과제·저장소 기준·모델·추론 설정·맥락을 사용한다. 보조 에이전트는 별도 대화/작업 폴더에서 수행하며 상대 답변·평가 정답을 보지 않는다.
- **과제:** 우선 개발용 4개, 최종용 8개의 서로 다른 React 작업을 작성하고 공개한다. 버그 수정, 입력 검증, 상태 전이, props 처리 등을 포함한다. 같은 과제 변형은 같은 분할에 둔다. 12는 빠른 기술 파일럿의 작업량이며 통계적 충분성 근거가 아니다. 아직 과제와 기능 정답 검사를 모두 작성한 상태는 아니다.
- **설정:** 3가지 설명 × 2가지 전달 = 6개 조건. 모든 조합을 검사기 단위 검증에 사용한다. 첫 생성 파일럿은 개발 과제로 범위를 줄여 비용과 검사 오류를 확인한 뒤 최종 실행 수를 고정한다.
- **기능 평가:** TypeScript 타입 검사와 React 실제 이벤트·렌더링 검사를 사용한다. 생성 코드는 검토 후 격리된 환경에서만 실행한다. 문법 통과는 기능 통과가 아니다. 일반/직접/조립 결과를 동일한 사전 고정 검사로 판단한다.
- **측정:** 조건별 지시 준수율, 기능 통과율, 둘을 동시에 만족한 비율, 실패/미지원/평가 실패 수, 모델 호출과 토큰. 미실행을 성공이나 0점으로 바꾸지 않는다. 과제별 원자료와 분모를 함께 공개한다.
- **해석:** 직접 지침과 조립 지침이 비슷하면 동일 조건을 안정적으로 전달했다는 범위에서 보고한다. 선택 UI의 편의성을 입증한 것으로 바꾸지 않는다. 한 과제의 시간이나 다수 변형 수를 독립 사용자 수처럼 세지 않는다.

## 개발 완료 조건

| 항목 | 완료 기준 | 2026-11-10 상태 |
|---|---|---|
| 두 기능 구분 | 시작 화면에서 각각 진입, 기존 경로 유지 | 반영·화면/회귀 검사 완료 |
| 명시 조건 조립 | 지원 6조합의 지침 생성과 설정 보존 | 별도 프로토타입 구현 |
| 자동 검사기 | 정상·위반 답변 대조, 미검증을 성공으로 표시하지 않음 | 12개 테스트 통과 |
| 기능 정답 검사 | 개발 4/최종 8과제의 정답·의도적 오답 대조 | 미완료 |
| 실제 생성 평가 | 고정한 계획의 일반·직접·조립 원자료와 분리 지표 보고 | 미실행 |
| 제품 연결 | 검증된 조건 선택·지침/작업 분리·답변 검사 화면 연결 | 미완료 |

좋은 수치가 나올 때까지 실험을 반복하는 것을 완료 기준으로 삼지 않는다. 기능 퇴행이 있으면 해당 조건을 기본값에 채택하지 않고 실패를 기록한다. 해결하지 못한 범위는 지원 대상으로 표시하지 않는다. 기존 요약 연구와 실험 기록은 별도로 보존한다.

## 다음 구현 순서와 비용

1. 프로토타입 검사 규칙에 맞는 개발 4과제·독립 정답 검사를 먼저 작성한다.
2. 이미 허용된 보조 에이전트 방식으로 소규모 생성 파일럿을 진행한다. 에이전트는 실제 사람을 대신 평가하는 것이 아니라 코드 후보를 만드는 역할이다.
3. 검사 실패 유형을 바탕으로 개발용 프롬프트를 수정하고, 최종 과제를 고정한 뒤 평가한다.
4. 확인한 조건만 기존 AI 답변 방식 설정 화면에 연결한다. 기존 저장본은 다른 버전으로 보존한다.

이번 프로토타입 생성·검사는 API 호출 없이 로컬에서 수행했다. 새 유료 API 생성은 호출 수·토큰 가정·예상 금액·중단 상한을 먼저 알리고 승인 범위 안에서만 실행한다. Codex 사용량은 별개이며 무료 사용량이라고 단정하지 않는다.

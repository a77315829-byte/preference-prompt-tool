# 보고서형 WBS v3.3

**현재본은 v3.3이다.** 기존 5개 단계·16개 주요 작업·일정·상태·선행 관계를 유지하고 설계서 v1.2와 다음 세 항목을 맞췄다.

- UC-02·03의 주 구현 3.1과 관련 작업 3.3(세션 정책 보완 예정)을 구분했다. UC-03의 3.2 공통 사용도 연결표에 표시한다. 하위 UC는 부모 연결 범위를 상속하되 관련 보완은 명시한 범위에만 적용한다.
- 2.1~2.3의 요약 v2 길이·충돌 설명은 문서 반영 완료로, 세션 정책 확정 후 설계·화면·명세 반영은 남은 일로 구분했다. 제품 상태 기준 11/12와 문서 확인일 11/13을 분리하며 새 원문 출력 검증 완료를 주장하지 않는다.
- 열 이름을 **저장소 최초 추가일**로 바꿨다. 해당 경로의 최초 추가 커밋 작성일이며 GitHub 업로드 시점이나 작업의 실제 시작·완료일이 아니다. 기존 13개 경로의 날짜는 유지한다.

- [공유용 PDF](../../../output/pdf/Revealed_WBS_v3.3_보고서형.pdf): WBS·간트·주 구현/관련 UC 연결표, 3쪽.
- [편집용 Excel](../../../outputs/wbs-20261112/Revealed_WBS_v3.3_보고서형.xlsx): 기존 3개 시트 유지, UC 연결표에 관련 WBS 열 추가.
- [구조화 자료](wbs-v3.3.json) · [검수 기록](validation-v3.3.json) · [전체 분석·설계서 v1.2](../../system-design/README.md).

생성 순서: 설계서의 `build_usecase_catalog.py` → `build_v3_3_data.py` → `build_v3_3_pdf.py` 및 `build_v3_3_xlsx.mjs`. Excel 생성기는 번들 `@oai/artifact-tool`을 사용하며 `CODEX_ARTIFACT_NODE_MODULES`에 번들 패키지 경로를 지정한다. 문서 생성에 유료 모델 API나 새 프로젝트 의존성은 사용하지 않는다. v3.2 PDF·Excel·JSON은 이전 기록으로 보존한다.

## 이전 v3.2 — 남은 일과 커밋 근거 추가

v3.2는 v3.1의 5개 단계·16개 주요 작업·일정(계획안)·상태·선행 관계는 그대로 두고, 검토에서 나온 근거 두 가지를 더했다. 아래 용어와 잔여 범위는 당시 기록이며 현재본은 위 v3.3을 따른다.

- [공유용 PDF](../../../output/pdf/Revealed_WBS_v3.2_보고서형.pdf): WBS 표·간트차트·UC 연결표의 3쪽.
- [편집용 Excel](../../../outputs/wbs-20261112/Revealed_WBS_v3.2_보고서형.xlsx): v3.1 통합 문서의 WBS 시트에 두 열을 추가. 수식·조건부 서식은 v3.1과 같다.
- [구조화 자료](wbs-v3.2.json), [검수 기록](validation-v3.2.json).
- 생성 순서: `build_v3_2_data.py` → `build_v3_2_pdf.py`, `build_v3_2_xlsx.py`.

v3.1에서 달라진 점:

- **비고(남은 일)**: 진행·보완 중인 8개 작업에 남은 일을 적었다. 문구는 상세 WBS v1.0(`wbs.json`)의 미완료 활동에 연결하고 날짜는 그 활동의 계획일이다. 3.3의 남은 일을 비교 세션 접근 정책(1.1.5, 4.1.6)으로 둔 것은 종료일을 근거로 한 배정이며 팀 확인이 필요하다.
- **GitHub 최초 커밋**: 7개 작업의 대표 경로가 `microstone`(`cfd1fe4`) 이력에 처음 추가된 날짜를 git에서 읽어 표에 적었다. PDF 간트차트에는 ●(1주차 이전은 ◀)로 표시했다. 작업의 시작·완료일이 아니며 계획 일정은 바꾸지 않았다.
- 단계 요약 행의 연결 UC를 `-`로 바꿨다. UC 연결은 작업 행에만 있다.
- UC 원자료를 현재 `usecase-catalog.json`에서 다시 읽었다. v3.1 JSON은 UC-05 대안 흐름 문구가 이전 것이었다.

바꾸지 않은 것: 작업 이름·ID·UC 대응은 설계서 v1.1과 같아야 하므로 그대로다. 3.3의 이름과 범위(UC-19~24 포함), 설계서 10.8의 "WBS 1.2와 2.3의 산출물 보완" 문구, 담당자 열은 설계서 다음 판본이나 팀 결정과 함께 정리할 항목으로 남겼다.

PDF·Excel 생성에는 `reportlab`·`openpyxl`이 필요하다. 프로젝트 의존성에는 추가하지 않았고 이전 판본과 같은 로컬 번들 Python으로 실행했다. Excel 파일은 실제 Excel에서 열어 확인하지 못했다.

## 이전 v3.1 — UC 연결 열과 연결표 추가

첨부 중간보고서처럼 단계·주요 작업·연결 UC·선행·일정·기간·진행률·상태를 보는 표로 정리했다.
5개 단계와 16개 주요 작업으로 줄였고, 세부 구현·개별 검사 항목은 별도 행으로 나열하지 않았다.

- [공유용 PDF](../../../output/pdf/Revealed_WBS_v3.1_보고서형.pdf): WBS 표·간트차트·UC 연결표의 3쪽.
- [편집용 Excel](../../../outputs/wbs-20261112/Revealed_WBS_v3.1_보고서형.xlsx): WBS·간트차트·UC 연결표. 날짜·상태 수정 시 기간·진행률·간트 갱신.
- [구조화 자료](wbs-v3.1.json), [검수 기록](validation-v3.1.json), [연결 분석·설계서](../../system-design/README.md).

상위 UC-01~UC-24와 하위 79개 목표를 구현 WBS 3.1~3.4에 연결했다. 하위 UC는 부모의 WBS를 상속하며 작업 수를 중복 합산하지 않는다. 공통 UC-03은 요약과 React 비교에서 함께 사용한다. 분석·설계·검증·문서화는 기능 외 작업이므로 UC와 모든 이름을 같게 만들지 않는다. 기준 설명과 공식 출처는 설계서 2.11절에 있다.

v3.0의 날짜·상태·선행·진행률 수식은 유지했다. 그림 상세화만으로 제품 검증이나 미완료 기능의 상태를 완료로 바꾸지 않았다. v3.0 PDF·Excel·JSON은 이전 판본으로 보존한다.

일정은 기존 학기 계획과 후속 계획을 주요 작업 단위로 다시 묶은 제안이다. 과거 실제 날짜는 아니다.
진행·보완 작업의 완료율은 미산정으로 두었고 완료 100%, 예정 0%만 표시했다. 단계 합계의 비율은 계산하지 않는다.
선행 관계에 SS가 있으면 시작 후 병행, 없으면 완료 후 시작한다.
상태 기준은 11/12이며 기존 구현·검사 결과와 앞으로의 보완·출력 검증을 구분한다.

## 이전 v2.0 — 계층도 방식, 사용자 요청 형식과 달라 대체

이전 v1.0은 활동·일정·검증 기록·기능 분해가 혼합되어 WBS의 계층을 읽기 어려웠다.
v2는 프로젝트 → 주요 산출물 → 작업 패키지의 3단계로 다시 구성했다.

- [한 장 WBS PDF](../../../output/pdf/Revealed_WBS_v2.0_한장.pdf): A3 가로, 7개 주요 산출물과 29개 작업 패키지.
- [편집용 Excel](../../../outputs/wbs-20261112/Revealed_WBS_v2.0.xlsx): WBS 계층표와 WBS 사전의 두 시트.
- [v2 구조·기존 활동 연결](wbs-v2.json): 기존 필수 활동 73개를 각각 하나의 주 작업 패키지에 연결.
- [v2 검수 기록](validation-v2.json).

WBS 사전에는 포함 범위·패키지 사이의 경계·완료 기준·책임자 입력란을 둔다.
책임자는 임의 배정하지 않았으며 각 패키지에 한 명을 확정하도록 했다.
공통 기술 설계는 1.1에, 기능 구현·단위 검사는 해당 제품 패키지에,
통합 회귀·독립 출력 평가 기록은 1.6에, 문서 편집·인도 작업은 1.7에 배정한다.
이 경계는 같은 작업을 여러 패키지에서 중복 계산하지 않기 위한 것이다.

일정·선행 관계·상태·공수·검증 로그는 활동 관리 자료에 두고 WBS 코드로 연결한다.
실사용자 연구·공개 배포·과거 Streamlit 정리는 별도 후속 목록으로 보존하며 이번 필수 범위에 합산하지 않는다.
새 구조는 팀의 범위·책임 확인 전 초안이다. 기존 73개 활동의 누락·중복 없음은 확인했지만,
이 매핑 검사만으로 실제 프로젝트의 모든 범위가 완전하다고 인증하는 것은 아니다.

## 기준과 적용

- [PMI WBS 실무 표준 3판 공식 소개](https://www.pmi.org/standards/work-breakdown-structures-third-edition): 공식 표준의 존재와 전체 범위 분해 목적을 확인했다. 유료 표준 본문 전체를 열람한 것으로 표현하지 않는다.
- [PMI 공개 자료](https://www.pmi.org/learning/library/applying-work-breakdown-structure-project-lifecycle-6979): 100% 규칙과 도표·목록·표 등 여러 표현 방식을 확인했다.
- [NASA WBS Handbook, 2021](https://www.nasa.gov/wp-content/uploads/2023/08/nasa-work-breakdown-structure-handbook.pdf): 산출물 계층, 필요한 만큼의 분해 수준, WBS 사전의 범위·경계 설명을 참고했다(2.1, 3.3.4, 3.4.4).

특정 기관 양식 준수 인증이나 NASA의 계약 요구 전체 적용을 주장하지 않는다.
이번 프로젝트에 필요한 계층 구조·범위 경계·사전 원칙을 적용한 수정본이다.

## 기존 자료에서 확장한 범위

이전 WBS는 [4주 계획](../../PROJECT_PLAN.md)과 주간보고의 학기 전체 9개 작업 묶음에 있었다.
이번 판본은 주간보고 묶음 ID를 유지하고 77개 세부 작업으로 확장했다.
별도로 현 분석·설계서의 요구사항을 8개 대기능 → 16개 논리 기능 → 54개 세부 기능으로 연결했다.
참고 중간보고서에서는 기능 계층 및 WBS·선행·날짜 구조만 참고했다.

각 작업에 요구사항, 선행 작업, 담당 제안, 일정·공수 제안, 상태, 산출물, 완료 기준, 확인 근거를 붙였다.
기능 분해는 개발 작업과 다른 관점의 목록이므로 작업 수나 공수에 다시 합산하지 않는다.

| 구분 | 항목 수 |
|---|---:|
| 전체 세부 작업 | 77 |
| 필수 작업 | 73 |
| 필수 중 완료 확인 | 50 |
| 필수 중 남은 작업 | 23 |
| 선택 후속·외부 대기 | 4 |

잔여 필수 공수 64시간은 팀 합산 추정이다. 실제 투입 시간이나 확정 약속이 아니다.
완료 항목 비율은 단순 개수 비율이며 전체 진척·품질·사람의 효과를 뜻하지 않는다.

## 현재 완료와 후속 검증의 경계

요약 입력 12,000자 제한, 발췌 분량 상·하한 충돌 처리 및 해당 기술 회귀·CI는 확인한 범위로 기록했다.
새 원문에서 요약 v2 지침을 수동 지침과 다시 비교하는 작업은 `4.2.6`의 예정 작업이다.
이전 원문 9개의 결과를 최신 v2 출력 검증으로 바꾸지 않았다.
코딩의 AI 답변 방식 설정과 React 코드 스타일 비교는 유지하며, 한·영 의미 정렬 후 새 과제 재비교는 별도로 남겼다.

현재 목표에서 사람의 편의성·수정 시간 측정은 선택 후속으로 관리한다.
공개 배포와 과거 Streamlit 정리는 완료로 처리하지 않았다.
이번 문서 작업에서 유료 모델 API나 새 출력 실험은 실행하지 않았다.

## 팀에서 수정할 곳

담당 제안은 최신 주간보고의 윤정우·고차원 기준이다. 과거 기여 실적을 배정한 것이 아니다.
후속 일정은 기존 학기 마지막 보고일인 12월 18일까지의 제안이며 팀 합의가 필요하다.
과거 실제 시작·종료·공수는 확인하지 못한 값을 만들지 않고 공란으로 두었다.

엑셀 `상세 WBS`의 노란 입력 셀에서 상태·담당·시작·종료·공수를 변경하면 집계와 일정표가 갱신된다.
기간은 달력일이며 상태 변경은 완료 근거를 확인한 후 기록한다.
내용이 바뀌면 JSON 원본과 공유 PDF도 같은 버전으로 갱신한다.
기존 보고서와 고정 실험 기록은 당시 판본으로 보존한다.

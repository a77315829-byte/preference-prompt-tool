# 코딩 스타일 파일럿 사용자 평가

상태: 미실시. 이 문서는 절차와 빈 기록 양식이며, 실제 참가자/결과를 만들지 않았습니다.

## 목적과 역할

- 차원: TypeScript/React 예시와 선택 UI 검수
- 정우: 기존 문서 요약과 공통 추정 엔진 설명/회귀 확인
- 태정(예정): 통합 실행, 동의·평가 진행, 결과 집계
- 주장 범위: 선호 선택 → 축 추정 → 시스템 프롬프트 반영. LLM 학습이나 성능 향상 입증이 아닙니다.

## 평가 전

1. 48개 코드의 요구사항, 기능 동등성, 스타일 차이를 팀원이 검수합니다.
2. 자료 버전, 브랜치 커밋, 실행 모드와 브라우저를 기록합니다.
3. 참가자에게 목적, 보관 기간, 철회 방법을 설명하고 동의를 받습니다. 이름/연락처/회사 코드/API 키는 수집하지 않습니다.
4. 무작위 참가자 ID를 사용하고 A/B 표시 방향을 참가자 간 교차 배치합니다. 현재 앱은 고정 시드이므로 교차 배치 실험은 진행자가 별도로 기록해야 합니다.
5. 현재 React 세션은 서버 메모리에만 있습니다. 새로고침/서버 재시작 후 복구되지 않고 연구 로그 자동 저장도 없습니다.

## 진행

1. 카테고리를 직접 찾게 하고 소요 시간·길을 잃은 지점을 기록합니다.
2. 무료 데모로 8회 비교합니다. 코드에 없는 기능을 상상해서 선택하지 않도록 요구사항을 먼저 읽게 합니다.
3. 판단 불가/동률은 진행자 기록에 남깁니다. 현재 앱에는 건너뛰기 버튼이 없으므로 억지 A/B 선택으로 연구 라벨을 만들지 말고 해당 세션을 중단 또는 평가에서 제외합니다.
4. 결과 화면에서 세 가지 스타일과 프롬프트가 본인 취향에 맞는지 1~5점과 이유를 받습니다.
5. 코드 복사·다시 시작·뒤로 가기를 수행하게 하고 오류를 기록합니다.
6. 별도 효과 평가 시에만 holdout 두 과제에 기본/개인화 프롬프트를 적용합니다. 동일한 모델·버전·설정으로 생성하며 비용 동의를 먼저 받습니다. 조건명을 숨기고 순서를 교차 배치합니다.
7. 기능 성공 여부와 선호/동률/판단 불가를 별도로 평가합니다. 컴파일 실패를 취향 문제로 처리하지 않습니다.

## 빈 기록 양식

- 참가자 ID / 동의 여부:
- 날짜 / 브랜치 커밋 / 데이터 버전:
- 실행 모드 / 화면 크기 / 코딩 경험(자율 응답):
- 카테고리 찾기 시간 / 완료·중단 / 문제:
- 라운드별: 과제, 표시 순서, 선택(A/B/동률/판단 불가), 이유
- 결과 스타일 일치도(1~5) / 이해도(1~5):
- 복사 성공 / 재시작 성공 / 불편한 점:
- holdout(별도): 과제, 모델·설정, 두 생성물 식별자, 기능 성공, 선호·동률·판단 불가
- 개인정보 제거 확인 / 보관·철회 처리:

## 집계 원칙

참가자 수와 응답 수를 분리합니다. 완료율, 축별 일치도, 기능 성공률,
개인화 선호율, 동률·판단 불가율을 각각 보고합니다. 데모 UI 사용성 결과와
유료 LLM 효과 평가를 섞지 않습니다. 소수 파일럿의 평균만으로 일반적 우월성이나
통계적 유의성을 주장하지 않습니다.

## 발표용 설명

사용자는 복잡한 코딩 프롬프트를 직접 작성하지 않고 예시를 선택합니다.
공통 Estimator가 선택 기록으로 스타일을 추정하고, 그 결과를 재사용 가능한
시스템 프롬프트로 조립합니다. 코딩 자료는 6개 과제·48개 변형·72개 비교 쌍의
합성 파일럿이며 실제 사람의 선호 데이터가 아닙니다. 선택에는 4개 과제만 쓰고
2개는 후속 평가용으로 남깁니다. 현재 자동 검사는 기능 연결을 검증하며 사용자
만족도나 LLM 성능 향상을 입증하지 않습니다.

# 코딩 도움 사용자 평가 계획 및 기록지

상태: **참가자 평가는 아직 실시하지 않았습니다.** 아래는 실행 절차와 빈 기록지입니다. 자동 테스트나 합성 선택 결과를 사람의 평가로 보고하지 않습니다.

바로 진행할 때는 [참여자 안내·설문·진행자 기록 키트](coding-user-evaluation-kit.md)를 사용합니다. 첫 사용과 안내받은 추가 조작을 분리하고, 실제 응답은 빈 기록지에 수집합니다. 아래의 상세 기준은 유지하되, 두 단계의 성공률을 섞어 집계하지 않습니다.

## 자동 선택 시뮬레이션 결과 (실제 참가자 아님)

2026-10-12에 같은 데모 과제(클릭 횟수 표시·초기화 버튼)로 서로 다른 다섯 가지 선택 패턴을 끝까지 실행했습니다. 각 회차의 A/B 위치를 고정해 가정하지 않고, 실제 후보의 스타일 값을 확인해 선택했습니다. 아래 결과는 **선택 로직과 프롬프트 조립의 정확성**만 검증하며, 사용성 점수·사용자 선호 데이터가 아닙니다. 실제 AI 호출이나 비용은 없었습니다.

| 가상 패턴 | 구조 | 스타일 관리 | 타입 작성 | 결과 |
|---|---|---|---|---|
| 간결·직접·추론 | 한 파일 | 값 직접 작성 | 추론 중심 | 3회 선택, 목표 선호와 프롬프트 일치 |

| 간결·테마·명시 | 한 파일 | 테마/토큰 | 꼼꼼히 명시 | 3회 선택, 목표 선호와 프롬프트 일치 |
| 분리·직접·추론 | 역할별 분리 | 값 직접 작성 | 추론 중심 | 3회 선택, 목표 선호와 프롬프트 일치 |

추가로 첫 선택을 반대로 누른 뒤 `이전 선택 수정`으로 돌아가 원하는 값을 고르는 경우와, 같은 입력·선택 패턴을 두 번 실행했을 때 후보 내용 및 최종 프롬프트가 같은 경우를 확인했습니다. 재현 테스트는 `tests/test_coding_personas.py`에 있으며, 기존 코딩 테스트와 합쳐 **31개 통과**했습니다. 화면에서 카테고리를 찾는 시간, 코드 차이의 이해도, 복사 버튼의 발견 가능성, 실제 취향과의 일치도는 이 테스트로 알 수 없으므로 아래 참가자 평가가 여전히 필요합니다.

## 평가하려는 것

1. 사용자가 코딩 도움 카테고리를 찾고, 만들 기능을 입력한 뒤 화면에 제시된 A/B 비교를 끝낼 수 있는가?
2. 두 코드가 같은 기능을 구현한다고 이해하고, 코드 구조·스타일 관리·타입 작성의 차이를 구별할 수 있는가?
3. 선택 결과로 나온 세 가지 선호와 시스템 프롬프트가 사용자의 실제 취향과 맞는가?
4. `비슷해요 · 고르기 어려워요`, 이전 선택 수정, 전체 코드 보기, 프롬프트 복사를 스스로 사용할 수 있는가?

이 평가는 **사용성과 주관적 선호**를 확인합니다. 코드의 실행 가능성·기능 동일성은 별도 자동/수동 코드 검증으로 판단하며, 사용자 응답만으로 AI 모델의 성능 향상을 입증하지 않습니다.

## 실행 모드와 준비

- **무료 데모:** API 키 없이 `PPT_LIVE`를 끄고 실행합니다. 화면에 표시되는 준비된 코딩 과제를 비교하는 모드입니다. 참가자가 입력한 기능을 구현한 코드가 **아니므로**, 이 모드에서는 “내 기능에 맞는 코드 생성”을 평가하지 않습니다.
- **실제 AI 생성:** `PPT_LIVE=1`과 유효한 API 키로 실행합니다. 참가자가 입력한 기능으로 A/B 코드를 만듭니다. 호출에는 비용이 들 수 있으므로 팀에서 참가자 수·최대 호출 수·예산을 먼저 승인한 뒤 진행합니다. 키 누락·한도 초과·생성 실패 시 데모로 전환될 수 있어, **매 세션의 화면 표시와 서버 로그에서 실제 모드를 확인**합니다. 전환된 세션은 AI 생성 평가에서 제외하고 데모 사용성 평가로만 집계합니다.
- 두 모드 모두 React 화면과 API 서버를 함께 실행합니다. 실행 방법은 [README](../README.md)의 “웹 UI로 사용해보기”를 따릅니다. API 서버가 꺼진 상태의 프론트 단독 고정 예시는 엔진을 거치지 않으므로 평가 대상에서 제외합니다.
- 브랜치, 커밋, 브라우저, 화면 크기, 서버 모드, 프롬프트/모델 설정을 기록합니다. 평가 중 코드를 바꾸면 버전을 새로 기록합니다.
- 현재 비교 세션은 서버 메모리에 있어 서버 재시작 시 복구되지 않습니다. 참가자의 선택 기록을 자동으로 연구 로그에 저장하지 않으므로 진행자가 아래 양식에 수동 기록합니다.
- 기본 코딩 도메인은 세 가지 선호 축을 한 번씩 비교해 **3회** 진행됩니다. 서버의 최대 설정은 8회이지만, 비교할 질문이 더 없으면 일찍 끝납니다. 평가 기록에는 화면에 표시된 실제 총 회차를 적습니다.

### 이 저장소를 macOS에서 평가용으로 실행할 때

무료 데모 평가에서는 터미널 두 개를 열고 저장소 루트에서 아래처럼 실행합니다. `PPT_LIVE`가 설정된 터미널을 재사용하지 말고 `unset`으로 꺼진 것을 확인합니다. API 키 값은 화면 공유·기록지·로그에 남기지 않습니다.

```bash
# 터미널 1 — 저장소 루트
unset PPT_LIVE
.venv/bin/python api_server.py

# 터미널 2 — 저장소 루트
npm run dev
```

브라우저에서 Vite가 출력한 로컬 주소를 열고, 서버에 `mode: demo`와 세션별 `[session]` 로그가 나오는지 확인합니다. API 서버를 끄고 프론트만 실행하면 고정 예시로 넘어갈 수 있으므로 **평가 세션으로 기록하지 않습니다**. 실제 AI 모드는 비용·호출 한도를 팀이 승인한 뒤 별도 세션으로 실행하고, 설정만 `PPT_LIVE=1`로 바꿉니다. 키나 비용 승인 없이 실제 AI 모드라고 표기하지 않습니다.

## 참가자와 진행 방식

우선 3~5명으로 작은 파일럿을 진행하되, 모집 인원은 실제 가능한 범위에서 정합니다. 진행 전에 목적·기록 범위·보관 기간·철회 방법을 알리고 동의를 받습니다. 실명, 연락처, 회사 코드, 비밀번호, API 키는 기록하지 않습니다. 실제 AI 모드에 넣을 기능 요청에도 개인정보나 비공개 코드를 포함하지 않도록 안내합니다.

참가자에게 보낼 안내 문구 예시:

> “코딩 예시를 골라 나만의 React/TypeScript 프롬프트를 만드는 화면을 10~15분 정도 사용해 보시겠어요? 사용 중 헷갈린 부분과 결과가 취향에 맞는지 여쭤보겠습니다. 정답은 없고, 원치 않는 질문은 건너뛰거나 언제든 중단하셔도 됩니다. 이름이나 실제 업무 코드는 수집하지 않습니다. 참여 가능하시면 기록 범위와 보관 기간을 먼저 안내드리겠습니다.”

진행자는 동의 여부를 먼저 기록하고, 동의하지 않으면 시작하지 않습니다. 관찰 중에는 방법을 설명하지 않고 도움 요청이 나온 순간만 적습니다. 테스트가 끝나면 아래 질문을 같은 순서로 묻습니다.

1. “두 코드가 같은 기능을 하는 것으로 보였나요? 다르다고 느꼈다면 어디였나요?”
2. “어떤 차이를 보고 선택하셨나요? 차이가 잘 안 보인 회차가 있었나요?”
3. “결과에 나온 세 가지 스타일 설명이 본인의 선택과 맞나요?”
4. “생성된 프롬프트를 실제 코딩 도구에 붙여 넣어 쓰고 싶나요? 그렇지 않다면 무엇이 부족한가요?”
5. “화면에서 가장 헷갈렸던 순간과 바꾸고 싶은 점은 무엇인가요?”

1~5점은 모든 참가자에게 같은 기준으로 안내합니다. **일치도**는 1=전혀 맞지 않음, 3=일부만 맞음, 5=매우 잘 맞음; **이해도**는 1=무슨 뜻인지 모르겠음, 3=일부 이해함, 5=혼자 설명할 수 있음; **사용 의사**는 1=사용하지 않겠음, 3=상황에 따라 사용, 5=다시 사용하고 싶음입니다. 2·4점은 양옆 기준 사이로 응답하게 합니다.

진행자는 사용법을 먼저 설명하지 않고 다음 문장만 읽습니다.

> “React/TypeScript로 만들고 싶은 작은 기능을 적고, 매번 더 마음에 드는 코드를 골라 보세요. 둘 다 비슷하거나 판단하기 어려우면 그렇게 표시해도 됩니다. 끝나면 결과가 본인의 취향을 잘 설명하는지 말씀해 주세요. 정답은 없습니다.”

실제 AI 모드에서 과제 편차를 줄이려면 모든 참가자에게 같은 기준 요청을 먼저 줍니다: “클릭 횟수를 보여 주고 초기화할 수 있는 React 버튼 컴포넌트.” 이후 본인이 만들고 싶은 다른 작은 기능도 자유롭게 시도하게 할 수 있지만, 기준 과제와 자유 과제의 결과는 따로 기록합니다. 무료 데모에서는 입력값과 다른 준비된 과제가 나올 수 있음을 참가자가 화면에서 알아차리는지도 관찰합니다.

1. 시작 화면에서 코딩 도움을 찾아 선택하게 하고 걸린 시간과 막힌 지점을 기록합니다.
2. 기능 요청을 입력하고 시작하게 합니다. **무료 데모/실제 AI/실패 후 데모 전환** 중 실제 표시 모드를 기록합니다.
3. 화면에 제시된 비교를 끝까지 진행하게 합니다(기본 코딩 도메인은 3회). 각 라운드에서 A/B 중 선택하거나 `비슷해요 · 고르기 어려워요`를 누를 수 있습니다. 후자는 유효한 “선호 미결정” 응답이며 억지로 A/B를 고르게 하지 않습니다. 전체 코드 보기를 열었는지, 어느 차이를 보고 골랐는지 기록합니다.
4. 한 번은 이전 선택을 수정해 보게 합니다. 결과 화면에서 마지막 선택 수정도 시도합니다. 진행자가 대신 눌러야 했다면 성공으로 기록하지 않습니다.
5. 결과의 세 스타일 항목과 시스템 프롬프트를 읽고 일치도·이해도를 각각 1~5점으로 평가하게 합니다. `비슷해요`만 선택해 미결정된 축은 프롬프트에서 빠지는지 확인합니다. 프롬프트와 기능 요청 복사를 시도하게 합니다.
6. 실제 AI 생성 세션에서는 “입력한 기능이 두 코드에 모두 구현됐는지”를 참가자 의견과 별도로 진행자가 코드 확인 결과로 기록합니다. 컴파일/실행 실패를 취향 불일치로 계산하지 않습니다.
7. 마지막에 불편했던 화면, 코드의 차이를 이해하기 어려웠던 이유, 실제 사용 의사를 자유롭게 듣습니다. 진행자는 정답을 유도하지 않습니다.

| 개발 경험(자율 응답) / 기준 과제 또는 자유 과제 | |

| 프롬프트 복사 / 기능 요청과 함께 복사 | |

| 타입 작성 선호 결과 / 본인 평가(1~5) | |
| 프롬프트 이해도(1~5) / 실제 사용 의사(1~5) | |
| 가장 어려웠던 순간 / 개선 의견 | |
| 개인정보 제거·보관·철회 처리 | |

라운드별로 아래 한 줄씩 **실제 표시된 회차만큼** 기록합니다. 화면의 A/B 방향은 바뀔 수 있으므로, 문자만 적지 말고 보인 스타일도 함께 기록합니다.

| 회차 | 비교 축 / 기능 | A 스타일 | B 스타일 | 선택(A·B·비슷해요) | 선택 이유 / 혼란 | 전체 보기 사용 | 기능 동일성 의심 |
|---|---|---|---|---|---|---|---|
| 1~3 (기본 코딩 도메인) | | | | | | | |

실제 AI 세션만 추가 기록합니다: A/B 각각의 실행·타입 검사 결과, 기능 요구사항 충족 여부, 단지 스타일만 달랐는지, 모델/설정, 호출 수와 비용(확인 가능한 경우). 원문 코드나 참가자 입력에 민감 정보가 있으면 기록지에 복사하지 않습니다.

## 집계와 발표 원칙

- 완료율 = 해당 세션에 표시된 비교를 모두 마치고 결과 화면까지 도달한 사람 / 평가를 시작한 사람. 데모와 실제 AI 모드의 분모를 분리합니다.
- 작업 성공률 = 카테고리 찾기·선택 수정·복사를 **도움 없이** 해낸 사람 / 해당 작업을 시도한 사람. 작업별로 계산합니다.
- 스타일 일치도는 세 축의 1~5점 분포와 이유를 함께 보고합니다. `비슷해요`는 A/B 선호표에 넣지 않고 별도로 빈도를 셉니다.
- 실제 AI 세션의 기능 성공률은 코드 검증 결과를 분모와 함께 보고합니다. API 실패 후 데모 전환과 취향 불일치를 구분합니다.
- 소수 파일럿의 평균만으로 일반적인 사용자 선호나 통계적 우월성을 주장하지 않습니다. 관찰되지 않은 결과 칸은 “미평가”로 둡니다.

기존 합성 코딩 데이터셋(6개 과제, 48개 변형, 72개 비교 쌍)과 자동 벤치마크는 구현의 재현성·안전장치 검증 자료입니다. 실제 참가자의 선택 데이터가 아닙니다. 별도의 개인화 효과 비교를 하려면 동일한 모델·설정으로 기본 프롬프트와 개인화 프롬프트의 결과를 만들어, 기능 성공과 블라인드 선호를 따로 평가하고 비용 승인을 먼저 받습니다.

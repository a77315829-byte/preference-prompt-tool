코드 확인 기준: `master` (2026-09-30 저녁). 원본은 `ui/ux` 의 `b93adcd` 기준으로 작성됐고,

문서 목적: 발표자가 프로젝트를 이해하고 설명하기 위한 대본·진행·질의응답 안내

> 이 문서는 PPT 원본을 수정하지 않는다. 페이지는 표지부터 센다. 아래에서 ‘계획’으로 표시한 기능은 구현 완료처럼 발표하지 않는다. 초기 타깃·팀 역할·일정·예산은 팀 확정 전까지 제안이다. 발표 직전에는 최신 코드와 공개 배포본을 따로 확인한다.

## 1. 발표에서 전달할 한 가지

> 분야별 전문가가 만든 작업 템플릿을 사용자가 비교 선택으로 개인화하고, 한곳에서 저장하고 반복 사용하는 서비스를 목표로 합니다. 요약으로 공통 엔진을 검증해왔고, 코딩과 AWS 비용 보고로 적용 범위를 넓히고 있습니다.

위 문장에서 **저장·반복 사용의 통합 경험은 앞으로 만들 제품 목표**다. 현재 확보한 것은 선택 기반 생성, 도메인별 연결, 시험 적용 등 개별 기능이다.

발표의 흐름은 다음 질문에 순서대로 답한다.

1. 누가 어떤 일을 반복해서 불편해하는가?
2. 비교 선택은 그 과정의 어느 부분을 바꾸는가?
3. 현재 무엇을 만들었고 무엇을 관찰했는가?
4. 어떤 검증과 제품 기능을 다음에 완성할 것인가?
5. 팀이 어떻게 나누어 책임질 것인가?

연구 한계는 관련 결과 바로 옆에서 짧게 밝힌다. 이후 계획에서 그 한계를 어떻게 확인할지 연결한다. 한 슬라이드마다 모든 약점을 다시 나열할 필요는 없다.

## 2. 발표 시간과 팀 분담

발표 시간이 아직 정해지지 않았으므로 **12분 발표 + 별도 질의응답**을 기본안으로 한다. 아래 시간은 연습용 배분이며 말하는 속도에 따라 조정한다.

| 구간 | 페이지 | 권장 시간 | 담당 역할 제안 |
|---|---|---|---|
| 문제·목표 | 1~6 | 2분 30초 | 총괄·공통 엔진 담당 |
| 제품·구조·범위 | 7~11 | 2분 30초 | 화면·코딩 담당 |
| 근거·검증·일정 | 12~17 | 4분 | 실험 담당 |
| 조직·운영·마무리 | 18~25 | 3분 | AWS·운영 담당, 마지막은 총괄 |

세 사람의 실제 이름과 역할은 팀에서 확정한다. 한 사람이 두 구간을 담당해도 된다. 페이지마다 발표자를 바꾸지 말고 구간 단위로 넘긴다.

**8분으로 줄여야 할 때:** 1, 3, 4, 7, 8, 11, 13, 14, 15, 16, 18, 25쪽을 중심으로 말한다. 나머지는 빠르게 넘기거나 질문 때 참조한다. 표의 모든 행을 읽지 않는다.

**시연을 포함할 때:** 60~90초를 구조 설명 시간에서 확보한다. API 생성과 GEPA 전체 실행을 현장에서 기다리는 구성은 피하고, 이미 준비한 입력·선택·결과의 연결을 보여준다. 데모 데이터는 화면과 말로 표시한다.

## 4. 슬라이드별 발표 대본

### 1쪽 — 표지

**핵심:** 비교 선택을 통해 개인에게 맞는 프롬프트를 만든다.

**말할 내용**
> 안녕하세요. 저희는 결과물 두 개 중 더 마음에 드는 쪽을 고르면, 그 선택을 바탕으로 개인에게 맞는 프롬프트를 만들어주는 도구를 개발하고 있습니다. 장기적으로는 분야별 전문가가 작업 템플릿을 추가하고, 사용자가 여러 작업의 프롬프트를 한곳에서 만들고 다시 쓰는 서비스를 목표로 합니다.

**다음 연결:** “먼저 어떤 불편에서 출발했는지 말씀드리겠습니다.”

### 2쪽 — Agenda

**말할 내용**
> 문제와 목표, 현재 구현 범위를 설명한 뒤, 확보한 실험 근거와 앞으로의 검증 계획, 팀별 수행 방안을 말씀드리겠습니다.

목차를 항목마다 설명하지 않고 짧게 넘긴다.

### 3쪽 — 프로젝트 추진 배경

**핵심:** 반복해서 원하는 출력 방식을 설명하는 부담을 줄일 수 있는지 확인한다.

**말할 내용**
> AI를 사용하면서 답변을 더 짧게 해달라거나, 예시를 먼저 보여달라는 지시를 반복하는 경우가 있습니다. 저희는 이런 반복 작업을 하는 사용자에게 초점을 맞추려 합니다. 프롬프트 설계에 익숙하지 않은 사용자가 지침을 체계적으로 개선하는 데 어려움을 겪는다는 선행 연구도 있습니다. 그래서 원하는 결과를 비교해서 고르는 방식이 직접 지침을 쓰는 부담을 줄일 수 있는지 검증하고 있습니다.

**주의:** ‘모든 사람은 자기 취향을 설명하지 못한다’, ‘비교가 무조건 쉽다’는 결론은 내리지 않는다. 초기 타깃인 학생 개발팀·주니어 개발자는 팀이 검증할 가설이다.

**다음 연결:** “이 부담을 줄이기 위해 입력 과정을 다음과 같이 설계했습니다.”

### 4쪽 — 문제 정의 및 추진 전략

**말할 내용**
> 사용자는 조건이 다른 두 결과를 비교합니다. 시스템은 선택 이력에서 어떤 축값을 선호하는지 추정하고, 이를 프롬프트 문구와 평가 함수로 바꿉니다. 기본 산출물은 추정된 선호를 조립한 프롬프트입니다. GEPA는 그 이후 선택적으로 개선을 시도하는 단계이며, 대표 비교 실험의 D 조건은 GEPA 없이 조립한 결과입니다.

**설명 보충:** 한 축의 지시만 바꿔도 모델 출력의 다른 성질이 함께 변할 수 있다. 후보 텍스트가 실제로 한 속성만 다르다고 보장하는 설계는 아니다.

**다음 연결:** “따라서 성공 여부도 생성 완료뿐 아니라 결과와 사용자 부담을 함께 보겠습니다.”

### 5쪽 — 프로젝트 목표 및 성과 지표

**말할 내용**
> 목표는 세 부분으로 나눕니다. 첫째, 비교 선택이 선호를 얼마나 잘 반영하는가입니다. 둘째, 직접 지침을 쓰는 것에 비해 시간과 수정 부담이 줄어드는가입니다. 셋째, 다른 분야 담당자가 공통 엔진을 고치지 않고 기능을 추가할 수 있는가입니다. 기존 실험은 첫 번째의 제한된 근거이며, 사용자 부담과 반복 사용은 이번 수행 기간에 직접 측정할 계획입니다.

**PPT 권장 상태:** 구현 완료 / 제한된 조건에서 관찰 / 검증 예정 / 범위 밖.

**주의:** 단순히 버튼을 8번 누르고 종료했다고 선호를 정확히 복원한 것으로 세지 않는다.

### 6쪽 — 기대효과

**말할 내용**
> 사용자는 반복해서 쓰는 작업의 출력 방식을 저장해두고 새 입력에 적용할 수 있게 됩니다. 분야 담당자는 자신의 전문성을 템플릿과 검사 기준으로 제공할 수 있습니다. 이러한 기대효과는 작성·수정 시간, 프롬프트 재사용 여부, 새 도메인 추가 공수로 확인하겠습니다.

**주의:** 저장·재사용을 통합한 보관함은 계획이다. 시간 절감률은 아직 실측값으로 제시하지 않는다.

### 7쪽 — 구축 범위 개요

**말할 내용**
> 공통 엔진과 분야별 도메인 팩을 중심으로 개발합니다. 요약은 기존 실험을 보강하는 기준 도메인으로 유지하고, 코딩과 AWS 비용 보고는 팀원의 전문성으로 확장할 계획입니다. 리뷰·이메일·자동 축 발견은 실험 범위로 관리해 검증 범위를 과도하게 넓히지 않겠습니다. 제품 기능은 템플릿 탐색, 개인화, 저장과 실행으로 이어지도록 정리하려 합니다.

**주의:** 위 범위 조정은 팀 합의가 필요한 제안이다. 아직 확정하지 않았다면 “이렇게 우선순위를 제안합니다”로 말한다.

### 8쪽 — 시스템 아키텍처

**말할 내용**
> 화면과 서비스, 선호 엔진, 도메인 팩을 분리했습니다. 공통 엔진은 축의 이름과 값 목록을 받아 비교와 추정을 수행합니다. 분야 담당자는 YAML의 지시문과 검사 함수, 데모와 평가 사례를 제공합니다. 새 도메인의 등록과 화면 연결은 필요하지만, 선호 학습 엔진을 매번 다시 만들지 않는 구조입니다. React는 개발 화면, Streamlit은 기존 공개 데모로 구분합니다.

**주의:** ‘YAML 하나만 쓰면 분야의 품질까지 검증된다’고 말하지 않는다. 공개 배포본이 현재 로컬 기능을 모두 포함하는지도 별도 확인한다.

### 9쪽 — 기능 요구사항

**말할 내용**
> 현재는 도메인 로드, 후보 생성, 비교 선택, 선호 추정과 프롬프트 조립이 연결되어 있습니다. 다음 제품 단계에서는 추천 템플릿에서 시작하고, 개인화한 프롬프트를 보관해 새로운 입력에 반복 사용하는 흐름을 보강하려 합니다. GEPA 최적화와 사용자가 가져온 프롬프트의 점검·다듬기는 서로 다른 기능으로 관리합니다.

**강조:** 앱은 현재 1위 값과 도전자만 비교하고 같은 질문을 다시 묻지 않는다. 물을 게 없으면 8회 전에 끝난다. 결과는 도구별로 바로 가져갈 수 있다(ChatGPT·Claude·Gemini 복사, Copilot·Cursor·AGENTS.md 파일).

### 10쪽 — 비기능 요구사항

**말할 내용**
> 운영에서는 비용, 대기 시간, 데이터 처리를 함께 관리합니다. 생성 결과를 캐시하고 사용량 제한을 두었지만 메모리 상한은 재시작 시 초기화될 수 있습니다. 원문이 피드백 로그에 남지 않는 것과 생성 캐시가 서버에 저장되는 것은 구분하고, 공개 운영 전에 보존·삭제 정책을 명확히 하겠습니다.

**주의:** 원문이 서버로 전송되지 않는다고 설명하지 않는다. 모델을 부르는 경로(세션 시작·GEPA 최적화·프롬프트 다듬기)에는 모두 하루 상한이 있고, 호출 한 번에 60초·출력 2,048토큰 제한이 걸리며, 모델은 서버가 정한다. 다만 상한은 메모리 카운터라 서버를 재시작하면 0으로 돌아간다 - 영속 예산 한도는 아니다.

### 11쪽 — 카테고리별 검증 수준

**말할 내용**
> 분야마다 확보한 근거가 다릅니다. 영어 요약에는 모의 선호 복원과 비교군 실험이 있고, 한국어는 기능 검증과 사용자 파일럿 준비가 되어 있습니다. 코딩은 스타일 선택 외에 빌드와 기능 정확성을 확인해야 합니다. AWS는 서비스별 비용 현황을 상세도와 강조점에 맞춰 설명하는 범위이며, 유휴 리소스를 확정하는 도구로 소개하지 않습니다.

**다음 연결:** “이 차이를 숨기지 않고 분야별 완료 기준으로 관리하겠습니다.”

### 12쪽 — 수행 방법론

**말할 내용**
> 먼저 가설을 정하고 측정 방법을 만든 뒤, 결과를 보고 채택하거나 수정합니다. 최적화한 지표만으로 최종 성과를 주장하지 않고 별도 지표와 대조합니다. 실험 조건과 실패한 가설도 기록해 다른 팀원이 같은 결과를 확인할 수 있도록 하겠습니다.

**주의:** 캐시는 원문·조립 프롬프트·모델 등 조건이 같은 요청을 재사용한다. ‘같은 프롬프트라면 원문이 달라도 호출하지 않는다’는 의미가 아니다.

### 13쪽 — PoC 수행 결과

**말할 내용**
> 기존 모의 실험에서는 특정 문서·페르소나 조건에서 완전복원율 80%를 관찰했습니다. 이는 실제 사용자 정확도와는 다릅니다. 기존 비교에서는 독립 지표인 ROUGE-L이 일반 지침 0.168, 선택 기반 조립 0.207이었습니다. 같은 5문서에 취향을 정확히 명시한 강한 지침을 추가하자 직접 지침 0.200, 선택 기반 0.207로 평균이 가까웠고 문서별로 3승 2패였습니다. 이 결과를 바탕으로 성능의 보편적 우위보다 비슷한 결과를 얻는 과정의 사용자 부담을 검증하려 합니다.

**선택적으로 덧붙일 내용**
> 피드백 어블레이션의 0.98 대 0.44는 최적화 목표 지표의 결과입니다. 내 글 경로의 형식 거리 감소는 별도 연구 결과로, 전문 지식 전이를 뜻하지 않습니다.

**주의:** 강한 비교군의 D 는 기존 A/B/D 실험의 D 와 같은 값(0.207)이다. 처음 커밋된 표의 0.209·5/5 는 기본 선택기를 바꾼 브랜치에서 다시 돌아 생긴 값이라 2026-09-30 에 정정했다. ‘가깝다’는 관찰은 통계적 동등성 입증이 아니다.

### 14쪽 — PoC 한계와 보완 검증 계획

**말할 내용**
> 다음 검증은 세 가지에 집중하겠습니다. 선택에 사용하지 않은 새 문서에서도 결과가 유지되는지, 사용자가 직접 작성하는 것보다 부담이 줄어드는지, 도메인이 달라져도 내용 정확성을 유지하는지입니다. 강한 비교군은 소규모 결과를 확보했으며 표본을 확대해야 합니다. GEPA는 추가 비용에 상응하는 효과가 있는지 별도 비교하겠습니다.

**완료 기준 수정:** ‘p값 산출’ 대신 문서 분리, 조건 고정, 결과·불확실성·실패 사례 보고로 적는다. 유의한 결과가 나올 때까지 표본을 늘리는 계획으로 설명하지 않는다.

### 15쪽 — 실사용자 파일럿

**말할 내용**
> 첫 파일럿은 한국어 요약에서 직접 지침 작성과 선택 기반 방식 두 가지를 비교합니다. 수행 순서를 교차 배정하고 시간을 잰 다음, 새로운 문서의 결과를 방식 이름 없이 보여줍니다. 선호뿐 아니라 사실 오류와 누락도 기록하고, 한 사람이 평가한 여러 문서를 참여자 한 명의 결과로 집계합니다. 5~8명 파일럿의 목적은 실패 유형과 사용 부담을 찾아 본실험을 설계하는 것입니다.

**운영 준비:** 모집 대상, 참여 시간, 동의 안내, 문서 출처, 사례 지급 여부, 보존·삭제 기한은 시작 전에 확정한다. 민감한 개인 문서 대신 사용 가능한 공통 평가 문서를 먼저 준비한다.

**주의:** LLM 생성 지침·GEPA까지의 다섯 조건은 후속 확장이다. 두 조건 도구에 다섯 조건을 이미 구현했다고 발표하지 않는다.

### 16쪽 — 프로젝트 추진 일정

**말할 내용**
> 일정은 범위 확정과 기존 근거 정리, 요약 파일럿과 도메인별 정확성 검증, 저장·실행 기능 연결, 결과 정리 순으로 배치하겠습니다. React 공개 전환은 핵심 흐름과 오류 처리를 확인한 뒤 진행합니다. 초기 범위 점검과 중간 검증 결과 점검에서 기능을 조정해, 연구와 제품 작업이 동시에 과도해지지 않도록 관리하겠습니다.

**주의:** 현재 PPT의 12주는 계획 틀이다. 실제 학기 종료일과 다르면 시작·종료 날짜부터 맞춘다. 이미 완료한 기간을 앞으로 수행할 기간처럼 표시하지 않는다.

### 17쪽 — 단계별 산출물 및 R&R

**말할 내용**
> 각 단계는 화면 완성 여부뿐 아니라 확인 가능한 산출물로 관리합니다. 도메인 담당자는 템플릿, 축과 검사 함수, 평가 사례를 함께 제출하고, 실험 담당자는 조건과 결과 파일을 남깁니다. 통합 담당자는 공통 엔진 연결과 화면 흐름을 확인합니다.

**주의:** 담당자 빈칸은 발표 전 실제 이름으로 채운다. 확인되지 않은 기여를 대본에서 배정하지 않는다.

### 18쪽 — 추진 조직 및 역할

**말할 내용**
> 역할은 공통 기반과 분야별 책임으로 나누려고 합니다. 요약 담당은 기존 검증과 공통 엔진을, 코딩 담당은 해당 작업의 템플릿과 실행 정확성을, AWS 담당은 비용 데이터와 보고 정확성을 책임지는 방식입니다. 화면 통합, 파일럿 운영, 발표 자료도 담당자를 지정하겠습니다.

**전제:** 실제 합의가 끝났다면 ‘나누었습니다’로 바꾼다. 주 10시간은 가정이며 팀원별 실제 투입 가능 시간을 확인해야 한다.

### 19쪽 — 협업 및 의사결정

**말할 내용**
> 작업 브랜치에서 변경하고 리뷰와 자동 검사를 거쳐 통합하는 것을 원칙으로 하겠습니다. 도메인 담당자가 품질 기준을 제안하고, 공통 엔진에 영향을 주는 변경은 함께 검토합니다. 범위나 일정이 바뀌면 결정 이유와 산출물에 미치는 영향을 기록하겠습니다.

**주의:** 기준 브랜치는 `master` 이고, 작업 브랜치 → CI(API 없는 테스트·프론트 빌드) → master 통합은 이미 운영 중이다. `submission-final` 태그는 기존 제출본 기록이며 Streamlit 공개 배포는 `submission` 브랜치를 본다. 회의 운영 등 나머지는 계획으로 말한다.

**주의:** 테스트 수는 기준 날짜와 실행 조건을 붙인다. 과거 통과 기록을 현재 배포의 검증 결과로 소개하지 않는다.

**주의:** 오라클 변경 후 복원율이 오른 사실만으로 검사 함수가 사람 선호를 정확히 측정한다고 주장하지 않는다. 온도 0도 완전한 재현성을 보장하지 않는다.

## 5. 숫자를 질문받았을 때 펼칠 근거표

### 5.1 기존 비교와 새 비교는 별도 실험이다

| 실험 | 조건 | checks | ROUGE-L | 발표 시 해석 |
|---|---|---:|---:|---|
| 기존 A/B/D | 일반 지침 B | 0.668 | 0.168 | 실험자가 작성한 일반 지침, 실제 참여자 아님 |
| 기존 A/B/D | 선택 기반 D | 0.996 | 0.207 | 5문서, GEPA 없는 조립본 |
| 강한 비교군 추가 | B | 0.668 | 0.168 | 동일한 일반 지침 조건 |
| 강한 비교군 추가 | B+ | 0.964 | 0.200 | 정답 축값을 다른 문구로 옮긴 코드 생성 지침 |
| 강한 비교군 추가 | B-LLM | 0.610 | 0.152 | 축 설명을 모델에 주어 한 문장 지침 생성 |
| 강한 비교군 추가 | D | 0.996 | 0.207 | 기존 D 와 같은 값 (2026-09-30 정정) |

- 강한 비교군 실험에서 D 대 B+는 5문서 중 3개에서 D가 높다. 우위나 동등성을 입증했다고 말하지 않는다.
- B+는 실제 사람이 시간을 들여 작성한 자료가 아니다. `build_strong_direct_prompt()`가 정답 축값을 자연어로 옮긴다.
- B-LLM은 한 모델·메타프롬프트·한 문장 지침 조건이다. 상용 프롬프트 생성기 전체의 성능을 대표하지 않는다.
- D 대 B 는 4/5승(+0.039, p=0.375)이다. 처음 커밋된 강한 비교군 표의 5/5승은 선택기가 바뀐 채 돌아간 결과라 정정했다.
- n=5에서 5/5승이어도 양측 부호검정 p=0.0625다(B+ 대 B, D 대 B-LLM). 통계적 우위를 주장하지 않는다.
- B-LLM 이 약한 이유를 ‘번역 과정이 정보를 잃는다’로 설명하지 않는다. B+ 는 채점 기준의 숫자(‘2문장 이하’)를 받았고 B-LLM 이 받은 설명은 실험자가 쓴 숫자 없는 문장이었다 - 정보는 모델에 들어가기 전에 빠졌다.
- 페르소나 5명의 추출성이 전부 `normal` 이라 사실상 길이 축만 시험했다.
- checks는 축 정의와 밀접한 내부 지표다. ROUGE-L은 참조 요약과의 텍스트 겹침으로, 사실 정확성이나 만족도 전체를 뜻하지 않는다.

근거: [기존 결과](../experiments/results/baseline_comparison.csv), [강한 비교군 결과](../experiments/results/strong_baseline_comparison.csv), [실험 구현](../experiments/strong_baseline_comparison.py).

### 5.2 다른 숫자의 사용 범위

| 수치 | 의미 | 이 수치로 말할 수 없는 것 |
|---|---|---|
| 모의 완전복원 80% | 과거 특정 문서·시드·선택기 실험의 집계 | 실제 사용자 80% 만족, 최신 선택기 동일 성능 |

검사 함수 근거: [라벨 대조 결과](../experiments/results/checks_vs_labels.json). 통합 표본에는 보정에 참고했던 데이터가 포함될 수 있으므로 독립 검증으로 소개하지 않는다.

## 6. 예상 질문과 짧은 답변

### Q1. 정확히 누가 쓰나요?

> 초기에는 AI로 문서 이해·코딩·비용 현황 확인을 반복하는 학생 개발팀과 주니어 개발자를 가설로 잡고 있습니다. 분야를 여러 개 제공하되 같은 사용자가 반복하는 작업에 집중하려 합니다. 실제 반복 사용 여부는 파일럿에서 확인하겠습니다.

### Q2. 그냥 AI에게 프롬프트를 만들어달라고 하면 되지 않나요?

> 그것도 중요한 비교군입니다. 저희는 원하는 스타일을 먼저 설명해야 하는 부담을 비교 선택으로 줄일 수 있는지 봅니다. 소규모 모델 생성 지침 비교는 있지만, 그 결과만으로 기존 도구 전체보다 낫다고 주장하지는 않습니다.

### Q3. 8번 선택이 더 귀찮을 수도 있지 않나요?

> 맞습니다. 8회는 상한이고, 같은 질문은 다시 묻지 않으며 물을 게 없으면 더 일찍 끝납니다(코딩은 3회). 그래도 모든 사용자에게 적절하다는 근거는 없습니다. 직접 작성과 비교의 전체 시간과 수정 횟수를 재겠습니다. 일회성 작업은 기본 템플릿을 바로 쓰고 반복 업무에 개인화를 적용하는 흐름도 계획하고 있습니다.

### Q4. 취향을 정확히 설명할 수 있으면 필요 없나요?

> 강한 직접 지침과 선택 기반 결과의 평균이 가까운 관찰을 얻었습니다. 이미 정확한 지침이 있는 사용자는 바로 사용하도록 하고, 원하는 형식을 잡기 어려운 사용자에게 비교 기능이 도움이 되는지 확인하겠습니다.

### Q5. MACSum은 무엇인가요?

> 같은 원문에 대해 길이·추출성 같은 속성을 조절한 사람이 작성한 요약을 제공하는 데이터셋입니다. 속성 조합을 숨긴 가상 선호로 삼아 비교 선택이 그 조건을 복원하는지 실험했습니다. 실제 사람을 대상으로 한 사용자 연구와는 다릅니다.

### Q6. Bradley–Terry는 무엇을 하나요?

> 두 선택지의 상대적인 선호를 승패 기록으로 추정하는 모델입니다. 저희 구현은 비교에서 다른 축값의 효용을 갱신해 더 선호하는 값을 추정합니다. 모델의 언어 지식을 학습하거나 사용자의 전문 지식을 저장하는 과정은 아닙니다.

### Q7. 검사 함수로 프롬프트도 만들고 채점도 하면 자기평가 아닌가요?

> 내부 지표에는 그 한계가 있습니다. 그래서 참조 요약과 비교하는 ROUGE-L을 병기했고 사람 라벨과의 일치도도 측정했습니다. 검사 함수의 라벨 재현이 충분하지 않다는 결과도 있어, 최종 사용자 효과는 별도 블라인드 평가로 확인하려 합니다.

### Q8. GEPA는 왜 쓰며 없어도 되나요?

> GEPA는 출력과 평가 피드백을 바탕으로 프롬프트 후보를 수정·평가하는 최적화기입니다. 축별 피드백을 활용할 수 있어 연결했습니다. 다만 현재 기본 경로는 조립만으로 동작하며, GEPA의 추가 이득이 비용을 정당화하는지는 별도 검증 대상입니다.

### Q9. ‘프롬프트 다듬기’도 GEPA인가요?

> 현재 사용자가 가져온 프롬프트를 구조적으로 점검하고 모델이 다시 쓰는 경로는 별도 기능입니다. 여러 출력과 평가를 반복하는 GEPA 최적화(결과 화면의 ‘선호 기준으로 최적화’ 버튼)와 구분합니다. 문장이 정돈됐다는 것만으로 작업 성능이 향상됐다고 보지 않습니다.

### Q10. 요약 검증이 코딩과 AWS에도 적용되나요?

> 적용되는 것은 공통 연결 구조입니다. 품질 검증은 분야마다 새로 해야 합니다. 코딩은 빌드와 동작을, AWS는 조회 금액·통화·기간과 근거 없는 주장 여부를 확인하면서 표현 선호를 평가합니다.

### Q11. AWS에서 정말 낭비 자원을 찾아주나요?

> 현재 실조회는 서비스별 비용 현황입니다. 그것을 원하는 상세도와 강조점으로 설명합니다. 유휴 자원 확정이나 절감액 보장은 하지 않으며, 그런 탐지는 리소스 상태와 사용량 등 추가 근거가 필요한 후속 범위입니다.

### Q12. 전문가가 들어오면 무엇을 추가하나요?

> 작업 목적과 입력 조건, 기본 템플릿, 개인화할 축, 검사와 평가 사례를 도메인 팩으로 제공합니다. 공통 엔진을 재사용하되 해당 분야의 품질은 담당자가 검증하고 범위를 공개하는 구조를 목표로 합니다.

### Q13. 프롬프트 모음 사이트와 어떻게 다른가요?

> 템플릿 탐색을 출발점으로, 결과 비교를 통한 개인화와 저장·재실행을 연결하려 합니다. 모음·보관함 통합은 계획이며, 사용자가 실제로 반복해서 쓰는지 확인해야 차별점이 성립합니다.

### Q14. 5~8명으로 효과를 주장할 수 있나요?

> 첫 파일럿은 실패 유형과 사용 부담을 찾기 위한 것입니다. 참여자 단위로 결과를 보여주고 일반적 효능을 확정하지 않겠습니다. 본실험은 최소 의미 있는 효과와 변동성, 운영 가능성을 고려해 사전에 설계하겠습니다.

### Q15. 사람 데이터를 어디에 저장하나요?

> 웹앱 입력은 서버에서 처리됩니다. 피드백 로그에 원문을 기록하지 않는 경로가 있어도 생성 캐시와 API 전송은 별개입니다. 실험 안내에는 전송 대상, 보존 범위와 삭제 방법을 명시하고 참여 동의를 받겠습니다.

### Q16. 이미 많이 만들었는데 왜 수행계획서인가요?

> 기존 PoC를 출발점으로 다음 수행 기간의 제품화와 검증을 계획한 자료입니다. 이미 관찰한 결과와 앞으로 달성할 목표를 표에서 구분하겠습니다.

### Q17. AI 도구가 개발을 다 한 것 아닌가요?

> 개발 보조 AI를 사용했습니다. 팀이 책임지는 부분은 문제와 범위 결정, 비교 조건과 평가 설계, 코드 검토, 결과 해석과 운영입니다. 누가 무엇을 맡았는지는 실제 작업 기록과 산출물로 설명하겠습니다.

실제 AI 활용 범위를 팀원별로 확인하고 답한다. 사용하지 않은 도구를 나열하거나 AI 사용을 숨기지 않는다.

## 7. 시연과 리허설

### 60~90초 시연안

1. 공개 여부와 데모/실시간 모드를 먼저 말한다.
2. 동일한 원문에서 길이 또는 표현 방식이 다른 두 결과를 보여준다.
3. 한두 번 선택하고 실제로 준비한 완료 세션으로 이동한다. 중간 단계를 건너뛴다고 밝힌다.
4. 생성 프롬프트의 어떤 문구에 선택이 반영됐는지 짚는다.
5. 시험 적용 화면이 준비돼 있으면 새로운 입력의 결과를 보여준다.
6. 저장·보관함이 아직 없으면 기능을 시연한 것처럼 말하지 않고 후속 계획으로 설명한다.

실패 시 멘트: “현재 실시간 호출이 지연돼 준비한 동일 흐름의 화면으로 설명드리겠습니다.” 준비 화면을 현재 실시간 결과라고 소개하지 않는다.

### 발표 직전 체크

- [ ] 팀명·담당자·실제 일정·회의 주기·예산을 확인했다.
- [ ] PPT의 ‘보완 필요’를 실행 계획 또는 확정된 내용으로 바꿨다.
- [ ] 초기 사용자와 요약·코딩·AWS 우선 범위를 팀이 합의했다.
- [ ] 구현 완료와 계획 기능을 구분했다.
- [ ] 두 비교 실험의 D 수치와 4/5·5/5 승수를 섞지 않았다.
- [ ] B와 B+를 실제 사용자 작성 실험이라고 설명하지 않는다.
- [ ] 공개 링크와 현재 브랜치의 기능 차이를 확인했다.
- [ ] 데모 데이터·실제 조회 데이터·준비 화면을 구분했다.
- [ ] API 키·개인 문서·계정 식별자가 발표 화면에 나오지 않는다.
- [ ] 한 번 시간을 재며 발표했고 질문 담당도 정했다.

### 배경 문헌

- [Why Johnny Can’t Prompt, CHI 2023](https://doi.org/10.1145/3544548.3581388): 비전문 사용자의 프롬프트 설계 어려움에 관한 연구. 우리 방식의 시간 절감률을 입증한 자료는 아니다.
- [Training language models to follow instructions with human feedback, 2022](https://arxiv.org/abs/2203.02155): 사람의 출력 평가를 모델 학습에 사용한 배경. 본 프로젝트는 모델을 재학습하지 않는다.
- [MACSum](https://github.com/psunlpgroup/MACSum): 속성을 조절한 요약 데이터와 실험 출처.
- [GEPA 논문](https://arxiv.org/abs/2507.19457): 자연어 피드백과 실행 결과를 활용하는 프롬프트 최적화 배경. 논문의 효과를 본 서비스에서 재현했다고 가정하지 않는다.

문헌은 배경과 방법의 근거로 사용하고, 우리 서비스의 효과는 우리 실험과 사용자 검증으로 설명한다.

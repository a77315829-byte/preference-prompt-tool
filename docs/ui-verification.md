## 구현 범위

- 문서 요약, 코딩 도움, 한국어 문서 요약, 혼합 문서 요약, AWS Idle Tracker,
  리뷰, 이메일, MACSum 평가의 8개 카테고리를 기존 Python 서비스에 연결했다.
- 카테고리 카드는 화살표, 표시점, 좌우 키보드, 가로 드래그, 휠로 전환한다.
  페이지 전체가 아래로 움직이는 대신 한 화면 안에서 장면을 전환한다.
- 비교 시작 → 8회 A/B 선택 → 선호와 시스템 프롬프트 확인 → 복사/다시 시작을 연결했다.
- 무료 데모와 유료 API 모드를 명시적으로 구분한다. 연결 실패를 샘플 성공으로 대체하지 않는다.
- 중복 선택을 막고, 응답 유실 시 결과를 추측하지 않고 다시 시작하도록 안내한다.
- 작은 화면의 코드와 결과는 내부 영역에서 스크롤한다. 전체 페이지 고정이
  긴 코드나 프롬프트를 읽지 못하게 하는 방식은 피한다.

복사 완료 표시와 다시 시작이 동작하는지 확인했다. AWS 무료 샘플 조회도 확인했다.

## 자동 검사

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest tests/ -m 'not api' -q -p no:cacheprovider
npm --prefix frontend run build
```

- Python: **255 passed, 2 skipped, 16 deselected**.
- Vite: 프로덕션 빌드 성공.
- 기존 Streamlit: 로컬 8502 포트에서 정상 시작하고 `/_stcore/health`의 `ok`
  응답을 확인한 뒤 검사용 서버를 종료했다. 이 확인만으로 모든 Streamlit 화면을 검수한 것은 아니다.
- API 회귀 검사: 모든 8개 카테고리의 데모 8회 완료, 동시 중복 제출 시 1회만 기록,
  잘못된 세션 거절, 외부 오류의 민감한 내용 숨김, AWS 월별 비용 합산을 포함한다.
- 실제 LLM 호출과 실제 AWS 조회는 수행하지 않았다. 외부 API 오류는 테스트 대역으로 검사했다.

## 브랜치 분리와 통합

- `ui/ux`: React 화면, 로컬 API, API 회귀 검사, README 화면 이미지.
- `submission`: 합성 코딩 데이터셋, 코딩 데모 연결, 사용자 평가 절차.
- 두 브랜치를 아직 병합하지 않았다. 이 UI 브랜치의 코딩 데모는 기존 생성기를 사용한다.

`submission`의 별도 검사에서는 관련 Python 테스트 **31개**가 통과했고,
48개 TS/TSX 예시와 120단계 모의 상호작용을 검사했다. 이는 TypeScript 전체 의미 검사,
실제 React 브라우저 테스트, 사용자 선호 평가를 대신하지 않는다.
데이터셋은 합성 자료이며 사람의 선호 정답이 없다. 실제 사용자 평가 결과는 아직 없다.

통합 담당자는 두 브랜치의 변경을 검토·병합한 후 위 회귀 검사를 다시 수행하고,
새 코딩 데이터셋으로 React의 8회 비교와 결과를 다시 확인해야 한다.
서비스와 테스트의 겹치는 변경은 한쪽 파일 전체로 덮어쓰지 않고 병합한다.

## 남은 검수와 제한

- API 모드: 사용자 키와 비용 승인을 받은 뒤 실제 LLM 공급자별 호출 검증이 필요하다.
- AWS: 현재 실제 조회는 서비스별 청구 비용 집계이다. 유휴 리소스 식별이나 낭비 금액
  확정 기능은 아니다. 무료 샘플의 리소스 ID·금액은 가상이며 데모 비교에도 이를 알린다.
  실제 유휴 판단은 별도 리소스 목록·사용 지표·권한 설계가 필요하다. 리소스를 삭제하지 않는다.
- 사용자 평가: `submission`의 `docs/coding-user-evaluation.md` 절차로 동의를 받고
  평가해야 한다. 자동 검사 수치를 사용자 만족도나 선호 정확도로 보고하지 않는다.
- 현재 API는 인증 없는 로컬 개발용이며 세션은 메모리에 저장된다. 공개 배포 전에
  인증, 세션 만료, 호출 제한, 영구 저장, CORS 제한을 적용해야 한다.

1-1. 배경 — 개인화는 "서술"에 의존한다

지금의 개인화 수단은 전부 사용자가 자기 취향을 글로 설명할 수 있다고 가정한다.

① 커스텀 인스트럭션

사용자가 "간결하게", "전문적으로" 같은 문구를 직접 작성한다. 추상적 형용사가 실제로 어떤 출력이 되는지는 사용자가 알 수 없다. 본 실험의 비교군 B에 해당한다.

② 프롬프트 생성 도구

"어떤 프롬프트를 원하냐"를 다시 묻는다. 질문의 형태만 바뀌고 서술 부담은 그대로다.

③ 파인튜닝 · 선호 정렬

선호 데이터로 모델 자체를 바꾼다. 개인 단위로는 데이터량·비용·접근성이 모두 성립하지 않는다.

이 가정이 깨지는 지점

사람은 두 결과물을 비교하면 즉시 고를 수 있지만, 무엇을 기준으로 골랐는지 서술하지 못한다. 실험에서 비교군 B(직접 작성한 지침)는 독립 지표 ROUGE-L 0.168에 머물렀고, 같은 페르소나에서 비교 선택으로 조립한 프롬프트는 0.207에 도달했다. 서술 능력이 아니라 판별 능력을 입력으로 쓰면 더 나은 결과가 나온다는 뜻이다.

이 과제가 하는 것

  • 상용 API를 부품으로 호출해 조합한다
  • 개인 적합도를 목표로 한다

이 과제가 하지 않는 것

  • 모델을 학습하거나 파인튜닝하지 않는다
  • "범용적으로 좋은 프롬프트"를 목표로 하지 않는다
  • 산출물이 모든 사람에게 잘 맞으면 개인화 실패로 본다

1-4. 기술 계보와 차별점

가져다 쓴 것과 직접 만든 것을 명시적으로 구분한다.

가져다 쓴 것 (기성 부품)

  • GEPA — 반성적 프롬프트 진화 (Agrawal et al., ICLR 2026)
  • DSPy — 자동 프롬프트 최적화 프레임워크
  • LiteLLM — 다중 모델 API 통합 인터페이스
  • MACSum — 혼합 속성 제어 요약 데이터셋 (Zhang et al., TACL 2023)
  • rouge-score — 독립 채점용 ROUGE-L (LCS 기반)
  • Kiwi — 한국어 형태소 분석
기성 도구를 쓰는 것이 감점 요인이 아니라, 어디까지가 기성품인지 명시하지 않는 것이 감점 요인이다. 본 계획서는 모든 결과에 대해 어느 부품이 기여했는지를 함께 적는다.

직접 만든 것 (라이브러리로 대체 불가)

  • engine/selector.py — 다음에 보여줄 쌍 선택. 불확실도 기반 능동 질의
  • engine/estimator.py — 선택 이력 → 축별 선호 + 확신도
  • engine/metric_builder.py — 선호 → GEPA용 평가 함수 조립
  • agents/domain_onboarding.py — 축 제안 → 검사 코드 작성 → 판별력 실측 → 재시도
  • agents/expert_onboarding.py — 저자 코퍼스에서 형식 앵커 추출

차별점 — 구조화 피드백

GEPA는 점수만이 아니라 자연어 피드백도 받는다. 본 도구는 축을 명시적으로 갖고 있으므로 "길이 위반: 6문장(목표 3문장 이하). 원문 수치 3개 중 1개 누락." 같은 피드백을 낼 수 있다. 범용 최적화 도구가 할 수 없는 부분이고, 효과를 어블레이션으로 실증했다(3-2).

2-1. 시스템 개요 — 두 개의 입력 경로

같은 산출물(개인 전용 프롬프트)에 도달하는 서로 다른 두 경로를 제공한다.

경로 A — 비교 선택 (주 경로)API 사용

입력: 과제 카테고리 선택 + 원문 입력 + 8회 비교 클릭
처리: 라운드마다 축 조합이 다른 후보 2개를 동시 생성 → 선택 이력 누적 → 축별 선호 추정 → 평가 함수 조립 → GEPA 최적화
산출: 시스템 프롬프트 + 추정된 축별 선호 + 갈린 비교 수 게이지

왜 8회인가

수렴 곡선 실측에서 불확실도 기반 선택이 8~9라운드에 2축 완전 도달했다. 더 늘려도 복원율이 오르지 않고 이탈만 늘어난다. 라운드 수는 service.TOTAL_ROUNDS 한 곳에서 관리한다.
경로 B — 전문가 자료 (보조 경로)API 0회

입력: 자기가 쓴 답변 뭉치를 구분선(---)으로 나눠 붙여넣기. 권장 30개 이상
처리: 전부 파이썬 코드로 계측. 단어·문장·문단·글머리 기호 비율을 재고, 절대 단어 수와 압축률 중 변동계수가 작은 쪽을 길이 모수화로 선택
산출: 29단어 길이의 형식 앵커가 붙은 프롬프트 + 측정된 형식 프로필

경로 B의 설계상 이점

효과가 전부 코드 계측에서 나오므로 사용자의 글이 어디로도 전송되지 않는다. 같은 자료를 예시로 프롬프트에 넣어봤을 때 형식 거리는 0.146 → 0.149로 차이가 없었다(페어드 p=0.727). 보낼 이유가 없다.

학습 예시에서 절대 단어 수와 압축률의 변동계수를 각각 재서 작은 쪽을 쓴다. 상수를 박지 않는다. 여유 계수 0.6을 두면 저자 11명 × 20개 분할 = 220개 분할을 전부 올바르게 판정한다(계수 없이는 13개를 놓친다). 요약 페르소나 3명은 전원 압축률, 실제 저자 16명은 전원 절대 단어 수가 선택됐다.

앵커의 두 절은 각각 다른 일을 한다

문장당 단어 수는 판별력 1.02로 탈락했지만, 앵커에서 그 절을 빼면 모델이 문장을 잘게 쪼개 문장당 단어가 13~17로 내려간다 — 저자(18~23)도 모델 기본값(22.2)도 아닌 값이다. 형식 거리가 3~11배 나빠진다.

3-1. 방법론 — 측정 우선 개발

축을 채택하기 전에 판별력을 먼저 측정한다. 11개 절대 규칙으로 문서화해 팀 전체가 공유한다.

절대 규칙 (전문 발췌)

  1. 엔진 코드에 도메인 특정 단어가 등장해서는 안 된다
  2. API 호출 결과는 반드시 캐싱한다
  3. 새 라이브러리를 추가하기 전에 먼저 묻는다
  4. API 키를 코드에 하드코딩하지 않는다
  5. 한 번에 파일 하나 또는 함수 하나 단위로 작업한다
  6. 평가 지표는 가능한 한 코드로 직접 잰다. 모델 판정은 최후 수단
  7. 최적화에 사용한 지표만으로 최종 성능을 보고하지 않는다. 독립 지표를 병기한다
  8. 한국어에서는 정량 복원율을 산출하지 않는다 — 답안지가 없다
  9. 생성된 코드는 검증 후에만 실행한다
  10. 신규 모듈은 기존 파이프라인과 분리한다
  11. 개별 케이스의 작은 차이를 결론으로 쓰지 않는다

규칙 6·7이 생긴 경위

비교군 D의 프롬프트는 검사 함수로 조립한 평가 함수에 대해 최적화되고, 그 결과를 다시 같은 검사 함수로 채점한다. 자기가 최적화한 함수로 자기를 채점하는 구조이므로 순환 논증으로 지적당할 수 있다. 그래서 최적화에 전혀 쓰이지 않은 독립 지표를 추가하고, 점수가 낮아져도 그대로 보고한다. 0.996보다 0.85가 더 믿을 만한 결과다.

규칙 11이 생긴 경위 — 가장 최근

저자 한 명의 결과를 보고 "모델이 큰 길이 목표에 체계적으로 미달한다"는 결론을 냈다가 폐기했다. 요청 단어 수를 20~320으로 바꿔 전달 함수를 직접 재보니 모델은 요청값을 거의 정확히 따랐다(요청/실제 비율 0.99~1.06). 실제 원인은 실험 설계였다 — 학습 부분집합과 홀드아웃 부분집합의 평균 길이가 체계적으로 달랐다 (long에서 98.5 대 128.4단어). 거의 완벽한 준수를 미달로 읽은 것이다.

측정 우선의 실제 효과

감정 축을 만들 때 사전 없이 바로 구현하지 않고, 3,000건으로 별점 파생 라벨과의 단조성을 먼저 확인했다(−0.0022 / 0.019 / 0.0392). 임계값도 중앙값 사이 중점을 실측 분포에서 뽑았다. 이 절차를 밟은 축은 이후 문제를 일으키지 않았다.

왜 이 결과가 중요한가

"우리는 축을 명시적으로 갖고 있어서 구조화된 피드백을 줄 수 있고, 범용 최적화 도구는 못 하는 부분"이라는 본 과제의 기여 주장에 대한 유일한 직접 증거다. 다른 변수 없이 피드백 형식 하나만 바꿔서 나온 차이라 인과관계를 주장할 수 있다.

이 실험을 한 번 다시 설계해야 했다

1차 시도에서는 시드를 추정 선호로 조립했는데, 그러면 시드가 이미 평가 함수에 최적화돼 검증 점수가 처음부터 1.0으로 포화된다. 두 조건 모두 개선할 여지가 없어 무의미한 비교였다. 시드를 일부러 못 맞는 것으로 바꿔 재실행했다.

최적화 루프에서 완전히 분리된 ROUGE-L을 쓴다 — 알고리즘이 다르고(검사 함수는 bigram Dice, 이쪽은 LCS 기반), 비교 대상도 다르다(원문이 아니라 사람이 작성한 정답 요약). 데이터셋 자체의 ROUGE 구현은 외부 실행기가 필요해 설치 부담이 커서, 표준으로 쓰이는 순수 파이썬 구현으로 대체했다.

3-4. 확보된 결과 ③ 복원율 — 그리고 오라클을 다시 만든 일

페르소나 오라클 재설계 — 0~8% → 80%

처음에는 "그 속성 조합의 사람 요약 = 답안지"로 삼아 단어 겹침으로 페르소나의 선택을 대행했다. 그런데 원문을 그대로 발췌하는 후보가 고유명사를 가져와 정답 요약과 우연히 어휘가 더 겹쳐 엉뚱한 축으로 수렴했다 — 내용 겹침과 문체 겹침을 구분하지 못한 것이다.
정답 요약 텍스트 대신 검증해둔 검사 함수를 페르소나의 실제 축값에 대고 두 후보에 돌려 점수가 높은 쪽을 고르는 방식으로 바꿨다. 5문서 평균 완전복원율이 0~8%에서 80%로 올랐다.

같은 시기에 발견한 언어 혼재 버그

전에는 엔진은 안 고쳐도 데모 생성기를 손으로 써야 한다는 구멍이 남아 있었다. 공용 데모 생성기가 여러 도메인이 공유하는 축을 실제로 구현하면서, 리뷰·이메일은 정의와 검사 함수만으로 다섯 번째 카테고리까지 동작한다. 다섯 카테고리 전부의 8회 완주를 검사하는 테스트가 있다.

한국어에서 실제로 고쳐야 했던 것

한국어는 조사가 붙어 "정부는/정부가/정부의"가 전부 다른 토큰이 된다. 표면형 비교는 겹침을 과소평가하므로 형태소 분석기로 어간만 추출해 비교한다. 스팟 체크에서 발췌형 조합은 겹침 94%, 서술형 조합은 40%로 명확히 갈렸다.

배포 제약 때문에 두 번째 백엔드가 필요했다

형태소 분석기 모델이 88MB라 무료 티어에서 빌드 실패나 메모리 초과 위험이 있었다 — 제출 링크가 죽으면 실격이라 감수할 수 없는 위험으로 판단했다. 지연 로드로 바꾸고 사전이 필요 없는 문자 4-gram 겹침 대체 경로를 뒀다.
처음엔 어절 끝 조사를 규칙으로 떼려 했으나 실패했다 — "전문가"의 "가"를 주격 조사로 오인해 중간 대역 겹침이 0.59 → 0.47로 내려가 임계값을 잘못 넘었다. 문자 n-gram은 조사가 어절 뒤에 붙는 한국어 특성상 그 문제가 없다.

불확실도 방식이 순차보다 빠르지 않고 둘 다 6라운드에 복원하는 것이 실제 곡선이라, "불확실도가 더 빠르다"를 테스트로 박지 않았다. 대신 둘 다 복원 후 되돌아가지 않는 것과, 무작위는 15라운드에도 유지하지 못하는 것(평균 1.8/2)을 고정했다. 바라는 값이 아니라 관측된 값을 고정한다.

좋은 테스트의 증거

응답 기록에 필드를 추가했을 때 기존 개인정보 테스트가 즉시 깨졌다 — 키 화이트리스트를 정확히 검사하고 있었기 때문이다. 자유 텍스트를 막는 것도 규약이 아니라 코드로 강제했다(숫자만 허용). "원문은 기록하지 않는다"가 약속이 아니라 성질이 됐다.

# 9. 검증 설계와 확인된 결과

## 9.1 검증 질문

이번 기술 검증의 질문은 ‘사용자가 명시하거나 확인한 조건을 제품 지침이 새 입력에서도 전달하는가’다. 요약은 조건 준수와 내용 보존, 코딩은 타입·실제 DOM 동작·조건 준수를 따로 확인한다. 사용자가 아직 모르는 취향을 정확히 찾는지, 몇 번 고르면 충분한지, 사람의 시간과 노력이 줄어드는지는 다른 질문이다.

일반 요청은 조건이 없는 기준선이고, 수동 지침은 같은 조건을 잘 적은 강한 기준선이다. 제품이 일반보다 목표 조건에 잘 맞아도 수동보다 낫다는 결론은 나오지 않는다. 수동과 같은 결과는 관찰된 동률이며 통계적 동등성 증명이 아니다. 같은 태스크에서 여러 검사를 통과했다는 이유로 표본 수를 검사 수만큼 늘려 보고하지 않는다.

## 9.2 공통 실험 절차

| 순서 | 고정·처리할 항목 | 편향 방지 |
|---|---|---|
| 1 | 이전 관찰 과제와 다른 원문/기능 과제 선정 | 개선에 쓴 자료를 최종 평가로 재사용하지 않음 |
| 2 | 목표 조건·공통 요구·수동/제품 지침 확정 | 방식별로 기능 요구를 유리하게 바꾸지 않음 |
| 3 | 검사·판정 기준·정답/오답 대조 고정 | 생성 결과를 본 뒤 합격 기준 변경 금지 |
| 4 | 독립 보조 에이전트에 조건별 입력 제공 | 다른 조건 답변·평가 결과 열람 금지 |
| 5 | 첫 응답을 파일·해시로 보존 | 좋은 답변만 골라 교체·재생성 금지 |
| 6 | 생성 코드 사전 검토·문자 그대로 적용 | 누락 코드 보완·실패 수정 후 최초 점수 보고 금지 |

보조 에이전트는 Codex 사용량을 소비하지만 이번 실험에서 별도 유료 모델 API를 호출하지 않았다. 정확한 디코딩 설정·청구 토큰 정보가 모두 제공되는 독립 API 실험과는 다르다. 한 조건의 여러 과제를 같은 생성 대화에서 처리한 상관 가능성도 남는다.

## 9.3 요약 조건 충돌 수정 비교

요약의 후속 비교는 수동·당시 현재본·충돌 처리 수정본을 새 원문 9개에서 평가했다. 모든 방식에 같은 보존 대상과 해결된 조건을 제공했다. 따라서 제품만 추가 정보를 받은 비교가 아니다. 원문의 핵심 명제와 지정 보존 내용, 분량·표현 조건, 사실 문제를 분리했다.

두 독립 검토자의 집계가 같았다. 이 결과는 수정본의 우위를 보여 주지 않는다. 충돌 처리의 기술적 역할은 해결 전 지침을 차단하고 명시한 변경만 적용하는 것이다. 핵심 내용 보존은 실제 답변에서 여전히 별도 확인해야 한다. 원문·평가 기준의 범위를 벗어난 완전한 사실성 보증으로 표현하지 않는다.

공개 문서에는 점수와 감사 기록을 첨부하고 데이터셋 원문 전체를 재배포하지 않는다. 근거는 `evidence/summary-contract-scores.json`, `evidence/summary-contract-audit.json`이다. MACSum 원문을 사용한 이전 연구와 현재 명시 조건 확인의 목적을 구별하며, 데이터셋 사용만으로 사람의 선호 추정이 입증되지는 않는다.

## 9.4 실패 성찰과 실제 GEPA의 판단

실패 사례 성찰 실험은 개선용과 최종 평가용 원문을 나눴지만 안정적인 이득을 확보하지 못해 기본 지침을 유지했다. 이어 실제 설치된 GEPA 탐색에 Codex 보조 에이전트 응답을 연결한 오프라인 실험에서는 개선 6개·후보 선택 6개·최종 9개를 별도로 두었다.

탐색 후보 선택 점수는 원본 약 0.7778, 두 성찰 후보 약 0.7222와 0.6667이었다. 선택된 best_index는 0이며 보충 안내가 없는 기존 지침이다. 비채택 후보를 나중에 더 비교했다고 최종 선택을 바꿔 보고하지 않는다. `evidence/summary-gepa-result.json`에 탐색 결과를 보존한다.

따라서 GEPA를 모든 결과의 필수 단계로 만드는 근거는 확보하지 못했다. 연구용 내용 보존 평가와 운영 코딩 최적화의 정적 점수는 목적·과제·실행 범위가 다르다. 모델 API를 쓰지 않고 이 연구를 했다는 사실은 운영 GEPA가 무료라는 뜻도 아니다.

## 9.7 React 타입·동작 검사 계약

TypeScript 5.9.3 strict와 설치된 React 타입으로 실제 검사했다. 공개 Component·Props 계약의 양방향 호환성을 확인하고 명시적 any·타입 억제문을 별도로 기록했다. 타입 추론 선호도 동일한 strict 환경이다. 타입을 많이 적었다는 사실이 타입 통과를 대신하지 않는다.

React/ReactDOM 19.3.0과 JSDOM 20.0.3에서 컴포넌트를 실제 마운트하고 입력·클릭·제출·props 갱신을 수행했다. 과제별 새 마운트로 7개 검사, 방식별 56개다. 일반 CSS side-effect import를 지원하고 24개 답변의 소스 50개, CSS 14개를 원문 그대로 적용했다.

모든 요청에 같은 실행 계약을 제공했다. 외부 네트워크·타이머·저장소·새 패키지·CSS Modules·원격 CSS 등을 제외했다. CSS 변수 계산은 JSDOM 한계가 있어 computedStyle을 정답 판정에 사용하지 않았다. 패널 색상·간격은 실제 스타일 선택 대상을 만들기 위한 공통 과제 요구였다.

사전 대조에서는 정답 구현 8개가 타입과 56개 동작 검사를 통과하고, 타입은 맞지만 기능이 틀린 변이 8개를 모두 탐지했다. 실행기 개발 검사 22/22를 통과했다. 이 사전 대조와 실제 생성 답변 검사의 표본·목적은 다르므로 합산해 제품 성능 점수를 늘리지 않는다.

## 9.8 React 세 스타일 조건의 독립 검토

검토자 A/B는 방식 이름·원 프롬프트·타입/동작 점수·서로의 판단을 보지 않고 같은 기준으로 평가했다. 파일 수만으로 역할 분리, theme이라는 변수명만으로 디자인 토큰, 타입 표기 수만으로 적절한 타입 작성이라고 판단하지 않는다. 인용 근거와 모호한 부분을 남겼다.

현재 영어 inferred는 공개 경계 중심의 짧은 표현이고 한국어에는 빈 배열·null 등의 필수 타입 예외가 더 자세하다. 공통 과제 계약에 strict를 위해 필요한 타입 예외를 동일하게 허용했다. 제품 지침 본문 자체는 바꾸지 않았다. separated도 영어의 component/state/styles와 한국어의 스타일 또는 상태 분리 사이에 해석 차이가 있어 원판정과 메모를 보존했다.

따라서 이번 점수는 정확히 이 공통 계약과 영어 지침 조합의 결과다. 추가 계약 없는 임의 작업, 한국어판, 팀 집계, 선택 UI, 유료 후보 생성·재시도, GEPA의 결과를 검증한 것은 아니다.

## 9.10 말할 수 있는 결과와 없는 결과

확인한 결과는 이미 정한 스타일 조건을 제품 지침으로 전달할 수 있었고, 제한된 새 과제에서는 기능을 해치지 않았다는 것이다. 강한 수동 지침도 같았다. 이 검증은 알려진 목표의 전달 실험이며 목표를 찾아내는 사용자 선호 추정 실험이 아니다.

아직 검증하지 않은 것은 실제 개발 저장소 통합, 실브라우저 레이아웃·보조기기, 다양한 모델·디코딩 설정, 실제 사용자 만족·수정 시간·학습 효과, 팀 채택이다. 동작 168회 통과는 24개 답변에 대한 고정 검사 합계이며 독립 사용자 168명의 결과가 아니다. 작은 합성 과제의 전부 통과를 범용 정확도 100%로 표현하지 않는다.

## 9.11 근거 보존과 다음 변경

React 새 실험은 완료 해시 126개와 이전 네 항목 실험 157개 해시를 확인했다. 과제·입력·코드 검토·실제 적용 파일·실행 결과·두 검토·집계를 읽을 수 있다. 공개 문서의 evidence 사본은 원본 바이트를 유지한 읽기 전용 근거이며 원래 경로를 전제로 하는 실행 스크립트를 그대로 독립 실행 배포한 것은 아니다.

다음 제품 변경은 영어/한국어의 필수 타입 예외와 역할 분리 의미 정렬부터 검토하는 것이 타당하다. 변경 후에는 이번 8개를 독립 최종 평가로 다시 부르지 않고 새 과제를 쓴다. 요약도 평가 오류와 조건 충돌을 분리해 고치고 별도 원문에서 확인한다. 추가 유료 모델 API가 필요한 실험은 실행 전에 예상 비용과 상한을 먼저 제시한다.

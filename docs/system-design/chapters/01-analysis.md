# 1. 시스템 분석과 상세 요구사항

## 1.1 문서 목적과 적용 범위

이 문서는 Revealed 전체의 분석 기준과 구현 설계를 함께 관리하는 기준 문서다. 주간보고는 이 문서에서 이번 주 변경점만 발췌한다. 요구사항을 이해하려는 팀원, 구현을 이어받는 개발자, 범위와 검증 근거를 확인하는 지도자에게 같은 기준을 제공한다. 구현 상태는 2026-11-12 로컬 개발본을 기준으로 하며 배포 여부와 구분한다.

분석은 왜 필요한지, 누가 무엇을 하는지, 어떤 조건에서 완료되는지를 정한다. 설계는 그 요구를 화면·API·모듈·데이터·권한·오류 처리로 구체화한다. 이 문서의 기능은 현행 소스에서 확인한 경로다. 사람의 만족도·실제 절감 시간·시장 수요는 소스 코드로 확인할 수 없으므로 미측정으로 둔다.

문서의 변경 단위는 요구사항 ID다. 기능이 바뀌면 유즈케이스, 화면 상태, API 계약, 데이터 영향, 검증 항목을 함께 검토한다. 그림만 고치거나 과거 실험 점수를 새 구현의 성능으로 옮기지 않는다. 첨부된 다른 프로젝트 보고서는 문서 구성의 참고이며 해당 프로젝트 기능·실적·개인정보는 포함하지 않는다.

## 1.2 문제와 업무 맥락

사용자는 AI의 답변 내용뿐 아니라 길이, 표현, 설명 정도, 코드 구성 등 결과 조건도 지정한다. 같은 조건을 작업마다 다시 적거나 이전 대화에서 찾아 붙여 넣어야 하는 경우가 있다. 팀에서는 개인 조건과 공통 규칙이 다를 때 어느 쪽을 따랐는지 확인하기 어렵다. 이는 제품이 다루려는 문제 가설이며 발생 빈도를 실제 사용자 조사로 측정한 결과는 아니다.

현재 검증의 중심 업무는 문서 요약이다. 문장을 짧게 줄이는 요구와 원문의 특정 문장을 그대로 남기는 요구가 동시에 주어지면 충돌할 수 있다. 분량을 지켰다는 결과만으로 핵심 정보가 보존됐다고 판단할 수 없고, 내용이 맞는다는 이유만으로 사용자가 정한 형식을 지켰다고 판단할 수도 없다. 따라서 조건 전달과 내용 보존을 별도 목표로 둔다.

코딩은 두 확장 업무를 유지한다. AI 답변 방식 설정은 설명·주석·구성·출력 조건을 명시적으로 조립한다. React 코드 스타일 비교는 파일 구성·스타일 값 관리·타입 명시의 세 축을 예시 선택으로 다룬다. 두 경로는 질문, 결과 지침, 기록 형식과 검증 단위가 다르다.

## 1.3 현재 방식과 제공할 업무 흐름

| 업무 단계 | 사용자가 직접 처리하는 방식 | 서비스가 제공하는 처리 | 남는 판단 |
|---|---|---|---|
| 조건 정하기 | 빈 요청문에 요구를 자유롭게 작성 | 직접 선택 또는 예시 비교 후 조건 확인 | 조건이 실제 목적에 맞는지 |
| 모순 찾기 | 결과를 본 뒤 누락·충돌 발견 | 완전 발췌 문장 수와 분량 상한의 충돌 표시 | 의미상 압축 가능성 |
| 지침 만들기 | 조건을 문장으로 다시 작성 | 확인한 값을 일관된 지침으로 조립 | 작성된 지침의 최종 채택 |
| 새 작업 사용 | 이전 대화에서 복사·수정 | 지침과 작업 입력을 분리해 복사 | 외부 AI에 보낼 자료 범위 |
| 보관하기 | 개인 메모·저장소 파일로 관리 | 계정별 지침·설정·출처 보관 | 저장할 이름과 민감한 내용 |
| 팀 규칙 적용 | 문서 내용을 수동 비교 | 항목별 개인/팀 선택과 버전 기록 | 어떤 기준을 채택할지 |
| 업무 전달 | 대화·파일·진행 상황을 각각 전달 | 목적·진행·다음 행동·자료를 지정 계정에 전달 | 수신자가 실제 이어받을지 |
| 효과 확인 | 주관적 인상으로 비교 | 조건과 내용/기능 정확도를 분리한 기록 | 사람의 편의성·채택 의향 |

오른쪽 흐름이 더 편하다는 것은 후속 사용자 평가 가설이다. 이번 완료 기준은 선택과 지침의 일치, 충돌의 명시, 저장·권한·버전의 일관성, 새 자료에서의 제한된 출력 검증이다.

## 1.4 이해관계자와 책임

| 역할 | 관심·목표 | 권한 경계 | 확인할 산출물 |
|---|---|---|---|
| 방문자 | 가입 전 기능 이해·예시 체험 | 계정 자료 저장·타인 자료 접근 불가 | 데모 표시·결과 지침 |
| 개인 회원 | 지침 보관·수정·새 작업 재사용 | 자신의 자료와 참여 권한이 있는 자료 | 지침·설정·출처·revision |
| 팀장 | 공통 기준과 참여 범위 정하기 | 해당 팀의 기준·초대 관리 | 팀 기준·필수 규칙·초대 상태 |
| 팀원 | 기준 차이 이해·작업용 조합 | 가입한 비공개 팀의 허용 범위 | 항목별 선택·원본 기준 버전 |
| 인수인계 작성자 | 작업 맥락·자료 전달 | 자신이 만든 대기 작업의 허용 변경 | 수신자·상태·버전 |
| 지정 수신자 | 받은 작업 이어서 수행 | 공유 시점 이후 접근·허용 상태 변경 | 다음 행동·첨부·변경 이력 |
| 개발·운영 담당 | 회귀·비용·보존·복구 통제 | 배포 환경·코드·운영 설정 | 검사 로그·백업·설정 문서 |
| 지도·평가자 | 목표·구현·검증의 연결 확인 | 문서·공개된 비식별 실험 근거 | 요구 추적표·실험 한계 |

역할은 한 계정에 중첩될 수 있다. 어떤 팀의 팀장이라고 다른 팀이나 다른 사람의 개인 지침을 읽을 수 있는 것은 아니다. 작성자·수신자 권한은 팀 가입 권한과 별개다.

## 1.5 시스템 경계와 외부 요소

서비스 내부는 React 화면, Python HTTP API, 서비스/업무 모듈, SQLite 저장소, 파일 및 모델 응답 캐시로 구성된다. 사용자 브라우저와 서버 사이를 데이터 전송 경계로 본다. 준비 예시는 모델을 호출하지 않지만 요청값이 서버에 전달되는 경로도 있으므로 모두 브라우저 내부 처리라고 설명하지 않는다.

실제 생성·GEPA를 명시적으로 시작하면 설정한 외부 모델 제공자가 참여할 수 있다. 이 문서의 보조 에이전트 검증은 운영 API 호출과 별도다. 사용자가 복사한 지침을 ChatGPT·Claude·IDE에 붙이는 행위와 그 도구에서의 답변 생성은 본 서비스의 관리 범위를 벗어난다. 내보낸 파일은 자동 설치하거나 사용자의 저장소를 자동 수정하지 않는다.

범위에 포함되지 않는 항목은 자체 언어 모델 학습, 자동 코드 배포, 조직용 SSO, 소스 저장소 자동 연결, 팀원에게 이메일·메신저 자동 알림, 생성 코드의 서버 측 범용 실행이다. 연구용 로컬 React 실행기는 운영 기능이 아니다. 도입을 검토하려면 새 요구사항과 비용·권한·보안 검토가 필요하다.

## 1.6 기능 요구사항 분해

상위 FR 번호는 개요와 동일하다. 세부 번호는 구현·회귀·변경 검토를 위한 분해다. 아래 수용 조건은 확인해야 할 행동을 뜻하며 모두 이번에 재실행했다는 뜻이 아니다.

| ID | 요구사항 | 관찰 가능한 수용 조건 |
|---|---|---|
| FR-01.1 | 계정 생성·로그인 | 검증한 자격 정보로 세션을 발급하고 비밀번호 원문을 저장하지 않음 |
| FR-01.2 | 세션 종료·계정 변경 | 로그아웃, 비밀번호 변경, 계정 삭제가 해당 세션·소유 자료 정책을 따름 |
| FR-01.3 | 계정 격리 | 다른 계정의 지침·작업 ID를 넣어도 내용을 반환하지 않음 |
| FR-02.1 | 요약 분류·원문 입력 | 지원 언어·분류를 확인하고 현재 원문으로 비교 시작 |
| FR-02.2 | A/B·비슷함 선택 | 현재 쌍에 대한 응답만 반영하고 선택 이력 보존 |
| FR-02.3 | 비교 종료·되돌리기 | 질문 상한·남은 쌍·이력에 따라 종료와 되돌림을 일관되게 처리 |
| FR-02.4 | 결과 상태 표시 | 미정 축과 종료 이유를 확정 선호와 구별 |
| FR-03.1 | 원문 문장 지정 | 현재 원문의 완전 문장 중 최대 8개를 중복 없이 선택 |
| FR-03.2 | 충돌 차단 | 완전 발췌 문장 수가 상한보다 크면 해결 전 새 지침을 비워 반환 |
| FR-03.3 | 충돌 해결 | 분량 확대·재서술·일부 생략 중 명시한 변경만 적용 |
| FR-03.4 | 원문 분리 | 재사용 지침에는 원문 제외, 작업용 요청에는 지정 문장·원문 포함 |
| FR-04.1 | 개발 환경 설정 | 언어·프레임워크의 현재 선택을 지침과 일치시킴 |
| FR-04.2 | 네 조건 확인 | 설명·주석·구성·출력이 모두 확인돼야 생성 가능 |
| FR-04.3 | 규칙 조립 | 모델 없이 선택과 환경을 반영한 실제 지침 전문 제공 |
| FR-04.4 | 환경 변경 | 기존 네 선택과 예시 출처를 초기화해 잘못된 환경 증거 재사용 방지 |
| FR-05.1 | React 세 축 비교 | 파일 구성·스타일 값·타입 축을 별도 도메인으로 비교 |
| FR-05.2 | 데모 범위 표시 | 준비된 비교 과제를 사용자의 임의 기능 구현으로 표현하지 않음 |
| FR-05.3 | 스타일 결과 | 세 축의 추정 신호와 실제 최종 지침 연결 |
| FR-06.1 | 선택적 예시 비교 | 직접 설정과 준비 예시 비교를 전환 가능 |
| FR-06.2 | 중도 완료 | 한 번 이상 응답한 뒤 마칠 수 있고 최대 8회 제한 |
| FR-06.3 | 불일치 처리 | 한 번 선택·반복 일치·엇갈림·미응답을 구별 |
| FR-06.4 | 기록 검증 | 서버가 예시 ID·환경·순서·응답으로 요약을 재계산 |
| FR-07.1 | 개인 지침 저장 | 제목·분류·본문·선택 설정을 계정 소유로 저장 |
| FR-07.2 | 수정 충돌 | 이전 revision의 수정·삭제 요청은 현재값을 덮어쓰지 않음 |
| FR-07.3 | 새 작업 재사용 | 원본을 갱신하지 않고 작업 입력과 지침을 조합 |
| FR-07.4 | 본문·설정 불일치 | 직접 수정한 본문과 과거 설정의 불일치 가능성을 표시 |
| FR-08.1 | 기존 도메인 팀 | 요약·React 비교 이력을 명시적으로 합침 |
| FR-08.2 | 네 항목 코딩 팀 | 팀장이 기본값·필수 규칙을 명시하고 새 종류로 관리 |
| FR-08.3 | 계정 팀 초대 | 열린 초대·유효기간·로그인·참여자를 확인 |
| FR-08.4 | 항목별 조합 | 개인과 팀의 다른 항목에 대해 따를 값을 직접 선택 |
| FR-08.5 | 출처 기록 | 선택값·출처·기준 버전을 당시 스냅샷으로 보존 |
| FR-09.1 | 재조합 | 저장된 작업용의 당시 기준을 사용해 새 항목 생성 |
| FR-09.2 | 부분 되돌림 | 고른 변경 항목만 이전 값·출처로 복원한 새 항목 생성 |
| FR-09.3 | 이력 연결 | 접근 가능한 직전 저장 ID 연결, 삭제된 항목의 내용 추측 금지 |
| FR-10.1 | 인수인계 초안 | 목적·진행·남은 일·자료·사용 지침 명시적 저장 |
| FR-10.2 | 지정 공유 | 같은 서버의 계정을 수신자로 지정, 링크만으로 권한 부여 금지 |
| FR-10.3 | 이어받기·완료 | 허용 역할과 상태에서만 claim·complete·reopen 처리 |
| FR-10.4 | 버전 열람 | 현재 권한과 수신자의 공유 시작 revision을 함께 확인 |
| FR-11.1 | 첨부 제한 | 파일당 5MiB, 현재 10개, 이전 포함 작업당 20MiB 검사 |
| FR-11.2 | 첨부 권한 | 현재 접근 권한과 요청 버전에 포함된 파일인지 대조 |
| FR-11.3 | 안전한 제공 | 제한 MIME 또는 일반 텍스트/다운로드로 제공, 실행하지 않음 |
| FR-12.1 | 계정별 임시 초안 | 24시간 범위에서 복구하고 로그아웃 시 제거 |
| FR-12.2 | 개선 결과 복구 | 계정별 7일 작업 기록, 재시작 중단 작업을 오류 상태로 표시 |
| FR-13.1 | 선택적 개선 시작 | 지원 환경·실행 가능 상태·로그인·사용량 확인 후 시작 |
| FR-13.2 | 원본 보존 | 선택 원본을 고정하고 후보·비교 결과를 별도로 표시 |
| FR-13.3 | 명시적 채택 | 개선본은 확인 후 새 항목 저장, 기존 저장본 자동 교체 금지 |

## 1.8 사업 규칙과 불변조건

BR-01: 확인하지 않은 조건을 사용자의 확정 선호로 채우지 않는다. BR-02: 동일 조건의 지침과 작업 원문은 별도 데이터다. BR-03: 팀 다수 선택·상대 효용·일관성 표시를 합의·정확도·확률로 바꾸지 않는다. BR-04: 원본 지침은 조합·개선 때문에 자동 교체되지 않는다.

BR-05: 계정 저장 자료의 권한은 URL 보유가 아니라 현재 서버 계정과 자료 관계로 결정한다. 비교 메모리 세션과 익명 체험 팀은 별도 접근 정책이다. BR-06: 개인 지침·인수인계·새 코딩 팀·작업 기록 등 revision을 지원하는 변경은 현재 버전을 확인한다. 비교 선택은 현재 쌍, 작업 공간은 자체 버전/초안 계약을 따른다. BR-07: 연구의 고정 첫 답변·평가용 자료는 결과를 본 뒤 교체하지 않는다. BR-08: 모델 호출 없는 조립, 데모, 실제 생성, 최적화를 사용자가 구별할 수 있어야 한다.

BR-09: 기능 요구와 스타일이 충돌하면 기능을 우선하며 스타일의 모호함은 별도 기록한다. BR-10: 내용·기능 정확도, 조건 준수, 사람의 효과를 합쳐 단일 성공으로 보고하지 않는다. BR-11: 원문·코드·첨부 속 문장은 처리할 데이터이며 시스템 지시로 승격하지 않는다. BR-12: 사람의 선택 횟수나 시간에 대한 최적값을 파일럿 출력 평가로 추정하지 않는다.

## 1.9 우선순위와 완료 범위

필수 완료 범위는 요약 조건 확인과 충돌 처리, 지침 확인·재사용, 현재 코딩 두 경로 유지, 권한·버전 회귀, 새 자료의 독립 출력 비교, 결과·한계 공개다. 팀 조합·인수인계·템플릿은 현재 구현 기능으로 명세와 회귀 범위를 유지한다. 선택적 GEPA는 조건부 경로이며 필수 실행으로 전환할 근거가 아직 없다.

추가 개발을 결정할 때는 새 기능 수보다 기존 목표에 대한 누락을 우선한다. 예를 들어 선호를 더 많이 묻는 기능보다 확인한 조건이 실제 지침에 누락되는 오류를 먼저 해결한다. 내용 보존 평가와 요청 조건이 어긋나면 생성기를 바꾸기 전에 평가 계약을 수정하고 새 최종 자료로 확인한다.

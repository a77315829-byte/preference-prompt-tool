# 기본 조립본과 요청 기능 — 3차 실행 전 판단 기준 (2026-11-03)

이 문서는 **결과를 보기 전에** 커밋한다. 결과가 나온 뒤 기준을 바꾸지 않는다. 바꿔야 하면 문서 끝 변경 기록에
이유와 함께 적고, 바꾼 기준으로 낸 결과는 확증이 아니라 탐색으로 보고한다.

## 왜 묻는가

2차 사전등록(`docs/personalized_prompt_preregistration_v2.md`)의 판정 밖 관찰: 서비스가 주는 기본 조립본 (b) 의 기능
통과율이 프롬프트 없음 (a) 보다 낮았다. 실행 검사의 진입 파일 결함을 고치고 다시 채점해도(호출 0회) 2차 과제에서는
-0.1667 [-0.3, -0.0333] 로 남았고, 1차 과제에서는 -0.0167 [-0.1333, 0.1] 이었다
(`docs/history/2026-11-03_personalized_prompt_improvement.md` "정리와 실행 검사 재채점"). 과제 세트에 따라 갈린다.

2차에서 (b) 가 떨어진 출력은 주로 요청의 글자를 바꿨다("화씨 32°F" → "32°F", 버튼 글자에 좋아요 수를 넣음)거나
설치되지 않은 `styled-components` 를 썼다. 그래서 그 두 가지를 직접 짚는 규칙 한 줄을 시험한다. **이 가설은 2차 결과를
보고 세웠다** - 그래서 판정은 새 과제에서만 한다.

## 묻는 것

1. (주) 기본 조립본 "항상 지킬 것" 맨 앞에 요청 대조 규칙 한 줄을 더한 (d) 가 (b) 보다 **기능 통과율을 높이면서 축 검사
   통과율은 크게 해치지 않는가.**
2. (보고용, 판정 아님) 새 과제에서도 (b) 가 (a) 보다 기능 통과율이 낮은가.

## 설계 (고정)

| 항목 | 값 |
|---|---|
| 조건 | (a) 시스템 프롬프트 없음 (b) 기본 조립본 (d) (b) + 아래 규칙 한 줄. 나머지 글자는 (b) 와 같다 |
| 추가 규칙 (`REQUEST_CHECK_RULE`) | 코드를 내기 전에 개발 요청에 따옴표로 적힌 화면 문구, 버튼 글자, 표시 형식을 하나씩 대조하라. 글자를 바꾸거나 덧붙이지 말고, 요청에 없는 라이브러리(예: styled-components)를 쓰지 마라. |
| 생성 모델 | `openai/gpt-4o-mini` (서비스 후보 생성 기본값) |
| 언어 | `ko` 최종 프롬프트 |
| 프로필 | 1·2차와 같은 4개 (`PREREGISTERED_PROFILES`) |
| 선택 이력 | 1·2차와 같은 가상 사용자, 데모 후보, 최대 8라운드 |
| temperature / 반복 | 0.7 / holdout 3회 (반복마다 캐시 폴더를 나눈다) |
| 분석 단위 | 프로필 × 과제 × 반복. 짝 비교는 같은 단위끼리 |
| 실행 검사 | `evaluate_trial.evaluate_candidate` — 32977ae 의 진입 파일 수정 포함 |

### 새 holdout 과제

`benchmarks/coding_ai_quality/v6.json` (split `holdout_v3`): `notify_switch`, `step_counter`, `todo_add`,
`color_choice`, `word_count`. 2차 `char_counter` 의 모호함을 보고 버튼 글자를 "정확히"로 적고 상태 문구는 버튼 바깥
별도 문단에 두라고 요청 문구에 명시했다. 생성은 한 번도 돌리지 않았다. 시나리오는 정답 구현이 통과하고 한 군데만 틀린
변형이 실패하며, 역할별로 나눈 답(실행용 `App.tsx` 껍데기 포함)도 정답이면 통과하는지 먼저 확인했다
(`tests/test_runtime_scenarios_v6.py`). 시나리오를 다듬다 `step_counter` 의 값 확인이 버튼 글자와 이어 붙는 결함을
찾아 고쳤다 - 생성 전이다.

### 단계

1. **Pilot (판정하지 않음)** — calibration 4과제 × 4프로필 × 1회. (a)·(b) 는 1·2차 pilot 캐시를 탄다. 파이프라인과 추출률만
   본다. 코드 결함을 고치면 holdout 전에 변경 기록에 적는다. **규칙 문구·기준·임계값은 pilot 결과를 보고 바꾸지 않는다.**
2. **확증** — holdout_v3 5과제 × 4프로필 × 3회.

```bash
python -m experiments.request_check_comparison --split holdout_v3 --repeats 3          # 사전 확인 (호출 0회)
# 1. pilot
python -m experiments.request_check_comparison --split calibration --execute --max-api-calls 36 --output-name rc_pilot
python -m experiments.request_check_comparison --split calibration --cached-only --behavior --reviewed-outputs \
    --output-name rc_pilot_behavior
# 2. 확증 (생성 → data/request_check_outputs 검토 → 실행 검사)
python -m experiments.request_check_comparison --split holdout_v3 --repeats 3 --execute --max-api-calls 135 \
    --output-name rc_holdout
python -m experiments.request_check_comparison --split holdout_v3 --repeats 3 --cached-only --behavior \
    --reviewed-outputs --output-name rc_holdout_behavior
```

### 호출과 비용 (실행 전 추정, 청구액 아님)

| 단계 | 최악 요청 수 (상한) | 예상 |
|---|---|---|
| pilot | 36 | (d) 16회 ((a)·(b) 캐시) |
| 확증 | 135 | 135회 |

1·2차 실측 기준 생성 1회 ≈ 입력 700 / 출력 500 토큰. 잔액·청구 금액은 확인하지 않는다.

## 지표

- **기능 통과율** (주 지표): tsc 타입 검사 + esbuild 빌드 + 과제의 고정 jsdom 시나리오가 모두 통과한 비율. 실행하지
  못한 출력(추출 실패 등)은 분모에 남기고 통과로 세지 않으며 미확인 수를 따로 적는다.
- **축 검사 통과율** (보호 지표): 목표 프로필 세 축의 지정 검사 통과 비율.
- 짝지은 차이 (d)−(b), (b)−(a) 의 평균과 95% 부트스트랩 구간 (단위 복원추출 2,000회, 시드 0).

## 판정 기준 (holdout_v3 결과에만 적용)

두 가지를 **모두** 만족할 때만 "요청 대조 규칙을 기본 조립본에 넣을 근거가 있다"로 적는다. 넣을지는 팀이 정한다.

1. **기능 이득**: (d)−(b) 기능 통과율 평균 차이 ≥ **+0.10** 이고 95% 구간 하한 > 0.
2. **스타일 비열등**: (d)−(b) 축 검사 통과율 차이 ≥ **−0.05**.

값은 스크립트 상수(`MIN_FUNCTIONAL_GAIN`, `MAX_STYLE_DROP`)와 같고 결과 파일의 `summary.criteria` 가 계산한다.

**보고용 (판정 아님)**: (b)−(a) 기능 통과율 차이의 95% 구간 상한 < 0 이면 "기본 조립본의 기능 저하가 새 과제에서도
나타났다"(`rule_based_functional_drop_replicated`), 아니면 "새 과제에서는 확인되지 않았다"로 적는다.

## 누락 처리

- 생성 오류 행은 같은 명령을 다시 실행해 한 번만 재시도한다(완료된 행은 캐시를 탄다). 남은 누락은 조건별로 보고하고
  짝 비교에서는 두 조건이 다 있는 단위만 쓴다.
- 결과를 본 뒤 단위·과제를 빼지 않는다.

## 이 결과가 말하지 않는 것

- 실제 사람의 선호, 임의 입력에 대한 기능 동일성, 사용자 만족, 다른 모델·언어(`en`)·도메인으로의 일반화.
- 규칙이 두 가지(글자 대조, 라이브러리 금지)를 함께 담는다. 기준을 넘어도 어느 쪽이 작동했는지는 가르지 못한다.
- 표본이 작다(확증 60단위). 넘지 못한 것은 "이 설계로 확인되지 않았다"로 적는다. 과제·프로필 단위의 작은 차이는
  결론으로 쓰지 않는다 (절대 규칙 11).

## 변경 기록

- 재시도 (누락 처리 규칙대로, 기준·문구·코드는 바꾸지 않음): pilot 1차에서 (d) 1행 Timeout → 같은 명령 1회 재실행.
  holdout 1차는 실행 중 Mac 이 잠자기에 들어가 15행이 실패(Timeout 11, InternalServerError 2, 실패 요청까지 상한에
  세어 생긴 요청 상한 2) → 같은 명령 1회 재실행으로 180행 완료. 1차 결과는 `rc_pilot_attempt1.*`, `rc_holdout_attempt1.*`.
  pilot·holdout 의 `source_sha256` 은 같다.

## 결과 (2026-11-04)

확증(holdout_v3 5과제 × 4프로필 × 3회 = 60단위, `experiments/results/rc_holdout_behavior.*`):

| 기준 | 값 [95% 구간] | 기준 | 충족 |
|---|---|---|---|
| (d)−(b) 기능 통과율 | -0.0167 [-0.1, 0.0667] | ≥ +0.10, 하한 > 0 | 아니오 |
| (d)−(b) 축 검사 통과율 | +0.0056 [-0.05, 0.0611] | ≥ −0.05 | 예 |

**판정: 기준 미충족. 요청 대조 규칙을 기본 조립본에 넣을 근거는 확인되지 않았다.**

**보고용 (판정 아님)**: (b)−(a) 기능 통과율 -0.0667 [-0.1333, -0.0167] — 구간 상한이 0 보다 작아 "기본 조립본의 기능
저하가 새 과제에서도 나타났다"(`rule_based_functional_drop_replicated: true`). 다만 크기는 2차 재채점(-0.1667)보다
작다. 조건별 기능 통과율 (a) 1.0, (b) 0.9333, (d) 0.9167, 미확인 (a) 0, (b) 0, (d) 3. 축 검사 통과율 (a) 0.4444,
(b) 0.6778, (d) 0.6833 - (b)−(a) +0.2333 [0.1667, 0.3] 으로 개인화 자체는 작동했다.

**설계 한계 (결과를 보고 안 것)**: 새 과제는 요청 문구를 분명히 쓴 탓에 쉬웠다 - (a) 가 60/60, (b) 가 56/60 을 통과했다.
(b) 가 0.9333 이면 (d) 가 낼 수 있는 기능 이득은 최대 +0.0667 이라 **+0.10 기준은 이 과제에서 처음부터 닿을 수 없었다.**
그래서 이 결과는 "규칙이 효과 없다"가 아니라 "이 과제 세트로는 잴 수 없었다"에 가깝다. 사전에 (b) 의 통과율을 몰랐고,
결과를 본 뒤 기준을 바꾸지 않는다.

판정 밖 관찰 (사례 수준, 결론으로 쓰지 않는다 - 절대 규칙 11): (b) 의 실패 4건 중 3건은 설치되지 않은
`styled-components` 를 써 타입 검사에서 떨어졌고 모두 separated/theme 프로필이었다. (d) 에서는 그런 실패가 없었지만 파일
추출 실패(미확인) 3건이 새로 나왔다.

사용량(공급자 보고 토큰, 청구서 아님): pilot 16 + 재시도 1회, holdout 135 + 재시도 13회. 합계 165회, 입력 112,412 /
출력 65,515 토큰. 잔액·청구 금액은 확인하지 않았다. 생성 코드(pilot 48 + holdout 180)는 실행 전에 import 와 위험 API 를
전수 검색했다(React·react-dom·설치되지 않은 styled-components 만 import, 파일·네트워크·프로세스 접근 없음).

# Luna 100회 코딩 프롬프트 파일럿 — 2026-11-09

승인받은 **100회 생성을 완료**했다. 사용량 환산 비용은 **$0.01391**, 승인 상한은 **$0.23**이다.
동일 과제 20개에서 일반 프롬프트의 기능 통과는 **18/20**, 우리 프롬프트 4종은 **14~17/20**이었다.
이번 파일럿은 정확도 향상을 뒷받침하지 않는다. 상세 주석 설정은 주석 수에 영향을 줬지만,
함수 분리 차이는 없었고 일부 응답은 요청한 출력 형식을 지키지 않았다.

이는 20개 Python 과제에서 관찰한 결과다. 우리 방식이 항상 열등하거나 개인에게 쓸모없다는
결론도 아니다. 실제 선호·수정 시간·8~10회 선택의 충분성은 측정하지 않았다.

## 설계와 비용

- HumanEval 10개 + MBPP 10개에 일반 지침과 우리 지침 4종을 각각 적용: **20 × 5 = 100회**.
- 과제는 무료 단계에서 `SHA256("pilot-v1:" + task_id)` 순서로 데이터셋별 10개를 고정했다.
  결과를 보고 과제를 바꾸거나 실패 과제를 제외하지 않았다. 조건 순서도 고정 해시로 섞었다.
- 우리 조건은 주석 `essential/detailed` × 구조 `compact/modular`이다.
  설명 `brief`, 출력 `complete`, 언어 Python, 프레임워크 없음으로 고정했다.
- 실제 서비스의 `build_coding_instructions()`가 만든 **직접 설정 지침**이다.
  사용자 8~10회 선택이나 GEPA를 실행한 결과로 표시하지 않는다.
- 일반 지침에는 같은 개발 환경·공통 규칙을 넣고 네 가지 작성 선호 부분을 뺐다.
  따라서 일반 대비 차이는 주석·구조만의 순수 효과가 아니다. 주석·구조 각각의 비교는
  나머지 설정이 같은 우리 2×2 조건 안에서 해석한다.
- 동일한 과제 요청문을 사용했다. 정답 구현·추가 테스트·평가 결과는 모델에 제공하지 않았다.
- 요청 및 반환 모델은 `gpt-6-luna`, `reasoning.effort=none`, Standard, 출력 최대 4,096토큰.
  모델은 alias이며 별도 날짜 고정 snapshot은 응답에서 확인되지 않았다. 기본 추론 설정의 결과로 일반화하지 않는다.
- 100개 모두 `completed`, 입력 **46,510토큰**, 출력 **18,518토큰**.
  `$0.10 × 46,510 / 1,000,000 + $0.50 × 18,518 / 1,000,000 = $0.01391`.
  [공식 Luna 단가](https://developers.openai.com/api/docs/models/gpt-6-luna)를 적용한 값이며
  청구서 대조값은 아니다. 세금·환전 수수료는 제외한다.
- 호출 전 최대 예약액 합계는 **$0.2274505**. 입력 예산은 실제 토크나이저 측정이 아닌
  UTF-8 바이트 수의 1.1배 + 요청당 128토큰이었다. 실제 사용량은 이 예산 안에 들어왔다.
- [공식 prompt cache 설정](https://developers.openai.com/api/docs/guides/prompt-caching)에 따라
  `mode=explicit`에 breakpoint를 지정하지 않아 공급자 캐시 쓰기 비용을 만들지 않았다.
  모든 응답의 cache read/write 사용량이 0임을 확인했다. 프로젝트의 **응답 파일 캐시**는 별도로 유지한다.
- API 자동 재시도·후보 재생성·상위 모델 전환·유료 판정 모델은 사용하지 않았다.
  27회 후 Windows의 일시적 파일 잠금으로 다음 호출 예약 저장이 실패했다.
  이때 28번째 네트워크 호출은 시작되지 않았고, 로컬 파일 저장만 보완한 뒤 캐시 27개를 재사용했다.
  총 생성 시도는 정확히 100회다.

## 정확도와 출력 형식

아래 기능 통과는 **기본 테스트와 추가 테스트를 모두 통과한 과제 수**다.
조건별 20과제를 분모로 유지했다. 각 과제·조건당 답변은 하나이며 단일 표본 pass@1이다.

| 조건 | 기본 테스트 | 기능 통과: base+plus | 일반 대비 승/동률/패 | 한 코드 블록 준수 | 형식까지 포함한 엄격 통과 |
|---|---:|---:|---:|---:|---:|
| 일반 | 19/20 | **18/20 (90%)** | — | 20/20 | 18/20 |
| 핵심 주석 + 간결한 구성 | 18/20 | 16/20 (80%) | 0 / 18 / 2 | 17/20 | 13/20 |
| 핵심 주석 + 역할 분리 | 19/20 | 17/20 (85%) | 0 / 19 / 1 | 14/20 | 11/20 |
| 상세 주석 + 간결한 구성 | 18/20 | 17/20 (85%) | 0 / 19 / 1 | 17/20 | 15/20 |
| 상세 주석 + 역할 분리 | 17/20 | 14/20 (70%) | 0 / 16 / 4 | 15/20 | 10/20 |

일반이 실패하고 우리 조건이 성공한 과제는 이번 표본에서는 없었다.
같은 20개 과제를 반복해서 비교한 것이므로 우리 조건 80개를 독립 과제 80개로 세지 않는다.
작은 표본이고 조건당 한 번만 생성했으므로 통계적으로 확정된 우열이나 실패 원인의 인과 추정은 하지 않는다.

일부 응답은 함수 구현 외에 실행 예제를 두 번째 코드 블록으로 덧붙였다.
원래 계획대로 **한 블록 요구 위반을 실패로 세는 엄격 점수**를 유지했다.
기능과 형식을 구분하기 위해 **요구 함수가 정의된 유일한 구현 블록**을 실행하는 보조 분석을 추가했다.
이는 출력 형식을 관찰한 후, 생성 답변의 기능 테스트를 실행하기 전에 추가한 규칙이다.
여러 구현 중 테스트에 통과한 것을 선택하지 않았으며 코드를 고치거나 블록을 합치지 않았다.
100개 모두 이 보조 추출에서 유일한 구현·문법 검증을 통과했다. 표의 기능 통과와 아래 정적 지표는 이 추출 기준이다.

| 조건 | HumanEval+ | MBPP+ NoExtreme |
|---|---:|---:|
| 일반 | 10/10 | 8/10 |
| 핵심·간결 | 10/10 | 6/10 |
| 핵심·역할 분리 | 10/10 | 7/10 |
| 상세·간결 | 9/10 | 8/10 |
| 상세·역할 분리 | 8/10 | 6/10 |

## 실제로 달라진 코드

아래 평균은 조건별 구현 20개에서 계산했다. `#` 주석과 함수 docstring은 분리했다.
빈 줄 제외 코드 줄 수에는 docstring과 같은 블록 안의 사용 예제도 포함된다.
출력 토큰 수는 코드뿐 아니라 답변 설명을 포함한다.

| 조건 | 평균 # 주석 수 | docstring 있는 함수 수 평균 | 평균 함수 수 | 평균 코드 줄 수 | 평균 출력 토큰 |
|---|---:|---:|---:|---:|---:|
| 일반 | 0.15 | 0.60 | 1.00 | 11.40 | 180.75 |
| 핵심·간결 | 0.25 | 0.60 | 1.00 | 9.30 | 170.10 |
| 핵심·역할 분리 | 0.00 | 0.75 | 1.00 | 9.90 | 173.55 |
| 상세·간결 | 0.60 | 0.80 | 1.00 | 12.00 | 198.10 |
| 상세·역할 분리 | 0.65 | 0.85 | 1.00 | 11.25 | 203.40 |

같은 구조 설정 안에서 상세 주석은 핵심 주석보다 평균 0.35개(간결)·0.65개(역할 분리) 늘었다.
간결 구성에서는 20과제 중 7개 증가·12개 동일·1개 감소, 역할 분리에서는 10개 증가·10개 동일했다.
모든 과제에서 주석이 늘었다는 뜻은 아니다. 주석 개수는 유용성 점수가 아니다.

100개 구현 모두 함수가 하나였다. 우리 역할 분리 지침은 불필요한 계층을 만들지 말라는 조건도
포함하며 이번 과제들이 작기 때문에, 이 결과만으로 역할 분리가 잘못되었다고 단정하지 않는다.
다만 **이 데이터와 함수 개수 지표에서는 구조 선택에 따른 차이를 검출하지 못했다.**

RACE의 고정 정적 함수는 함수 snake_case, 길이, 함수 docstring, 주석 비율, 함수 개수 조건을 각각 측정했다.
조건별 snake_case 충족은 모두 19/20, 함수 두 개 조건은 모두 0/20이었다.
RACE 전체 벤치마크 점수나 종합 품질 점수로 합치지 않는다.
전체 항목은 [결과 JSON](../../benchmarks/coding_public/results/2026-11-09-luna-pilot.json)에 있다.
[사용한 RACE 원본](https://github.com/jszheng21/RACE/blob/3b8ee591abd5febd8ae8ec17c7b9907949c5e1d5/race/codeeval/metrics_utils.py)의
추출 함수와 AST가 동일함을 무료 단계에서 검증했다.

### 차이가 있는 사례: HumanEval/40

일반 응답은 정렬과 두 포인터를 사용했고 추가 테스트까지 통과했다.
상세·간결 응답도 같은 접근에 `# 인덱스가 서로 다른 세 원소를 찾는다.`라는 주석과 doctest 실행부를 추가했고 통과했다.
상세·역할 분리 응답은 다른 알고리즘을 생성했다. 그 구현에는 다음 조건이 있었다.

```python
if -(first + second) in values and -(first + second) != first and -(first + second) != second:
    # 찾은 값이 현재 두 원소와 같더라도, 리스트에 남은 별도 원소가 있는지 확인한다.
    needed = -(first + second)
    if l.count(needed) > int(first == needed) + int(second == needed):
        return True
```

이 답변은 기본 테스트를 통과했지만 추가 테스트의 `[0, 0, 0]` 등에서 실패했다.
세 원소의 **위치**가 달라야 하는 과제에서 위 조건은 값이 같다는 이유로 후보를 배제한다.
주석은 중복을 처리한다고 설명하지만 조건문이 그 처리를 막는다.
이는 추가 테스트가 발견한 구체적 실패의 예이며, 주석 지침이 원인이라는 인과 증거는 아니다.

### 차이가 없는 사례: HumanEval/48

일반·상세 간결·상세 역할 분리의 핵심 구현은 모두 `return text == text[::-1]`였고 통과했다.
간단한 과제에서 선택한 구조나 주석 설정이 항상 코드를 바꾸지는 않았다.

## 평가기와 재현

- HumanEval+ v0.1.10, MBPP+ NoExtreme v0.2.0. 선택한 20과제의 **정답 20/20 통과,
  의도적 오답 20/20 실패 검출**을 같은 환경에서 확인했다.
- 이전 전체 MBPP 정답 대조에서 실패한 Mbpp/255는 원래 고정 파일럿에 포함되지 않는다.
  그 문제를 해결했다고 주장하거나 전체 MBPP 평가를 통과한 것으로 표시하지 않는다.
- 고정 이미지 `ganler/evalplus@sha256:26b118098bef281fe8dfe999bf05f1d5b45374b4e6c00161ec0f30592aef4740`.
  publisher tag는 v0.3.1이지만 설치 패키지는 0.4.0.dev2, 컨테이너 Python은 3.11.10이다.
- [공식 EvalPlus 수정](https://github.com/evalplus/evalplus/commit/6eb1e199c2e370518e7bf3e8eee6322c2b23c89c)의
  find_zero 결과 기록 두 줄을 적용했다. 메모리 중복 복사를 피하도록 바깥 작업 스케줄러만
  단일 ThreadPoolExecutor로 바꿨으며, 각 후보는 공식 guarded child process에서 실행했다.
  수정 없는 기본 실행기 결과라고 표현하지 않는다.
- 호스트에서는 AST·문법·import 검사를 수행하고 생성 코드를 실행하지 않았다.
  Docker는 network none, read-only root, 비root, 3GB/2CPU, 권한 제거를 적용했다.
  컨테이너에는 공개 입력·생성 답변·평가 파일만 제공했다. API 키와 전체 프로젝트는 마운트하지 않았다.
- 공개 파일·요청·응답·컨테이너 결과의 해시를 저장했다. 결과에 기록된 dataset hash와
  실제 평가 solution이 캐시에서 추출한 코드와 같은지도 확인했다.
- 결과 JSON: `benchmarks/coding_public/results/2026-11-09-luna-pilot.json`.
- 원문 요청/응답·사용량 장부·Docker 로그: `data/public-code-benchmarks/luna-pilot-v1/`.
  이 폴더는 Git에서 제외된다. 원문 응답을 지워서 유료 재생성하지 않는다.
- 실행 방법과 비용 차단은 [벤치마크 README](../../benchmarks/coding_public/README.md)를 따른다.
  기존 서비스와 `engine/`는 변경하지 않았다. 새 라이브러리도 추가하지 않았다.
- 관련 자동 검사 **46개 통과**. 완료 캐시 100건을 네트워크 클라이언트 없이 재사용해
  추가 모델 호출 0회를 확인했다.

## 이 결과가 정하는 다음 순서

1. **기능 통과를 먼저 확인한 뒤 스타일을 비교한다.** 주석·설명·구조가 좋아 보여도 테스트를 대신하지 못했다.
2. **출력 형식 충돌을 줄인다.** 전체 코드와 간결한 사용 방법을 요구할 때 사용 예제를 별도 블록으로
   덧붙이지 않도록 하는 후보를 검토한다. 이번 파일럿 프롬프트를 결과에 맞춰 고쳐 재평가한 척하지 않는다.
3. **역할 분리가 자연스러운 실제 과제를 추가한다.** 단일 알고리즘 함수 외에 입력 검증·변환·저장 같은
   여러 책임이 있는 작은 실제 작업에서 구조 선택을 평가해야 한다. 함수 개수만 늘리는 목표는 피한다.
4. **정답인 답변끼리 실제 사용자 선호·수정 시간을 비교한다.** 기능 통과율, 선호, 수정 시간을 별도로 기록한다.
   그 뒤에 8/10회 선택과 더 긴 선택의 안정성을 비교한다.

이번에 본 20과제로 프롬프트를 조정한다면 이 과제는 개발용으로 구분하고,
남은 미사용 과제에서 최종 평가를 사전 등록해야 한다. 추가 유료 생성은 실행하지 않았다.

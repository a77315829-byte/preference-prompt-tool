# 선택 횟수 완화 후 독립 검증과 세 조건 코드 비교

2026-11-09, microstone. 선택 흐름은 `4078021`을 기준으로 검사했다.

**수정한 조기 종료·선택 보존은 검사한 범위에서 정상이다. 출처 검증 오류 2개를 찾아 고쳤다. 실제 React 버그 수정에서는 일반·직접 설정·4회 예시 비교 모두 9/9를 통과했으며, 특정 방식의 우월성은 입증하지 못했다.**

## 1. 기능 검사와 수정

서로 다른 두 보조 에이전트가 프로덕션 코드를 바꾸지 않고 독립적으로 검증했다.

| 범위 | 결과 |
|---|---|
| 코딩 1~8회 각각에서 완료 | 모두 정상, 선택하지 않은 항목은 직접 확인 |
| 한 번 선택·반복 일치·엇갈림·미응답 | 구분 유지 |
| 메뉴 이동 복원·이전 응답 변경·취소 | 이후 기록 초기화와 기존 확정 값 보존 정상 |
| UI 생성 프로필 → 실제 백엔드 검증 | 10개 모두 요약 일치·왕복 보존 |
| 영어/한국어 요약 최대 8회 종료 | 데모의 모든 A/B/동률 분기에서 450개 완료 경로 검사 |
| 완료 후 마지막 답변 취소/교체 | 1,350개 검사, 추가 질문이 필요한 96개는 정상 재개 |
| 저장·DB 재개·직접 수정·재사용·내보내기 | v1/v2/v3와 v4 1~8회 기록 정상 |

여기서 경로 개수는 자동 생성한 상태 전이 사례 수다. 사람 수, 독립 과제 수, 선호 복원 정확도 표본 수가 아니다. 요약 검사는 데모 후보를 사용했고 유료 모델을 호출하지 않았다. 화면 검사는 실제 React를 JSDOM에서 실행하며 HTTP는 모의 응답이다.

발견한 결함과 수정:

1. **v4 기본 예시의 출처 ID가 언어를 구분하지 않았다.** Python 예시 선택 기록에서 환경만 Ruby로 바꿔도 서버가 수용하고 Ruby 출처로 다시 표시했다. 새 ID에 언어·프레임워크 식별값을 포함하여 환경이 맞지 않으면 거절한다. 기존 v4 저장본은 ID·종류·언어가 담긴 정식 이름을 대조하여 읽고, 과거에 없던 환경 검증 정보를 새로 확보한 것처럼 바꾸지 않는다.
2. **기존 v3 기록의 `example=null`에서 AttributeError가 발생했다.** 딕셔너리 여부와 출처 필드를 먼저 검증하도록 바꾸고, 잘못된 입력은 HTTP 400으로 반환한다. v3의 언어 출처 불일치도 거절한다.

부모 에이전트가 두 실패를 먼저 재현했다. 수정 후 독립 저장 검사 23개와 관련 정규 검사를 합쳐 **122개 통과**. 별도로 수정 전 UI가 생성한 10개 프로필의 호환성도 재확인했다. 해당 명령에는 `-m 'not api'`를 적용했으며 API 키나 `.env`를 읽지 않았다.

호환 한계: 이전 기본 예시 출처에는 프레임워크 정보가 없으므로 과거 프레임워크까지 증명할 수 없다. 이미 잘못된 언어 이름으로 저장·정규화된 오래된 기록도 원래 언어를 복구할 증거가 없다. 새 ID는 환경 불일치 검사용이며 사용자가 실제로 예시를 보았다는 인증 수단은 아니다.

변경 파일은 `coding_elicitation.py`, 재발 방지는 `tests/test_adaptive_comparison.py`다. 배포·서버 재시작은 수행하지 않았다.
[독립 검사 스크립트와 원자료](../../benchmarks/adaptive_audit/README.md).

## 2. 일반·직접 설정·예시 비교의 실제 코드 결과

사용자 요청에 따라 세 명의 새 보조 에이전트에게 동일 과제를 배정했다. 부모 대화 이력은 전달하지 않고 동일 세션 모델·추론 설정을 상속했다. 각자의 작업 폴더만 수정하도록 제한했다.

기존에 비교했던 실제 `CodingTrialPanel` 작업 요청 동기화 버그를 같은 기준 커밋 `3b6b550`에서 다시 풀었다. 과제 난도를 유지한 추가 조건 비교이며 새 과제 표본이 늘어난 것은 아니다. 현재 본선 코드에서는 이미 고친 버그이므로 실험 후보를 제품에 다시 덮어쓰지 않았다.

| 조건 | 고정 기능 검사 | 에이전트 작업 시간 | 기존 소스 변경 |
|---|---:|---:|---:|
| 수정 전 기준 코드 | 5/9 | 해당 없음 | 없음 |
| 일반 요청 | 9/9 | 206.731초 | 1파일, +13/−3 |
| 직접 설정 지침 | 9/9 | 175.225초 | 1파일, +14/−2 |
| 예시 비교 4회 지침 | 9/9 | 180.302초 | 1파일, +7/−4 |

세 후보 모두 첫 제출 후 추가 수정 없이 통과했다. 평가기는 생성 전에 고정한 9개 동작 검사이며 해시도 보존했다. 실제 소스는 JavaScript/React JSX다. TypeScript 컴파일·전체 앱 정확도·배포 환경·보안 점수가 아니다.

일반안은 편집 여부에 따라 최신 부모 요청과 로컬 값을 골랐다. 직접 설정안은 미편집 양식만 effect로 동기화했다. 예시안은 `null`인 로컬 덮어쓰기 값을 미편집 상태로 사용했다. 세 접근 모두 검사한 동작을 만족했다. 줄 수나 effect 유무로 품질 우열을 정하지 않는다.

직접 설정과 예시 비교는 실험자가 정한 **동일한 네 선호**다. 핵심 설명·필요한 주석·간결한 구성·변경 부분 중심을 사용했다. 생성된 지침의 네 규칙은 문자열 대조로 같고 출처 안내만 다르다. 예시 4회는 네 항목을 한 번씩 선택한 상태다. 사용자가 선호를 발견했거나 반복 일관성이 확보됐다는 의미가 아니다.

시간은 첫 도구 호출에서 기록한 UTC부터 마지막 제출 도구 호출까지다. 분석·파일 수정·자체 검사·도구 대기를 포함하며 사람의 코드 수정 시간은 아니다. 세 조건은 같은 호스트에서 겹쳐 실행되었고 부모의 다른 검사도 진행되어 자원 경쟁이 있었다. 조건별 1회라 31.5초/26.4초의 관측 단축을 인과적 효과나 기대 절감 시간으로 쓰지 않는다. 이전 2조건 실험에서는 맞춤이 오히려 약 10초 길었다.

별도 모델 API 요청 **0회**, 새 의존성 설치 없음. Codex 사용량·실제 계정 청구는 조회하지 않았고 사람의 선호·설정 시간·수정 시간은 모두 미측정이다.
[프로토콜·프롬프트·패치·검사 로그·원자료](../../benchmarks/coding_prompt_routes/README.md).

## 3. 이 결과로 정할 방향과 회의 답변

직접 설정을 기본으로 유지하고 예시 비교는 선택을 말로 정하기 어려울 때 쓰는 선택 경로로 둔다. 이미 고른 값의 재사용과 팀 기준 전달이 유용한지 검증한다. 횟수를 늘리는 것 자체를 성과로 삼지 않는다.

- **“짧게 끝내도 제대로 동작하나요?”** 1~8회 완료, 미정 항목 처리, 저장·복원은 검사했다. 적은 선택으로 취향을 정확히 알아냈다는 실증은 아직 아니다.
- **“일반 프롬프트보다 좋나요?”** 이 과제에서는 기능 검사가 동률이다. 에이전트 시간 차이는 관측했으나 표본이 작아 우위라고 말하지 않는다.
- **“그러면 예시 비교는 왜 필요한가요?”** 선호를 직접 설명하기 어려운 사용자의 설정 부담을 줄인다는 가설이다. 같은 설정을 전달하면 규칙이 같으므로, 코드 검사만으로 예시 입력 방식의 가치를 판단할 수 없다.
- **“다음에는 무엇을 측정하나요?”** 실제 참여자에게 일반 요청·직접 설정·예시 비교를 순서가 겹치지 않게 배정하고, 여러 버그/기능 과제에서 최초 설정 시간, 이후 수정 시간, 기능 검사, 익명화한 결과 선호를 따로 기록한다. 과제·완료 조건·분석 기준을 먼저 고정한다.
- **“효과가 없으면요?”** 예시 비교의 비용이 이득보다 크면 보조 경로로 축소하거나 제거한다. 재사용·팀 기준 공유도 따로 평가하여 실제 도움이 확인된 기능만 남긴다.

이번 결과의 결론은 기능 안정성과 주장 범위의 확인이다. 사용자 가치가 확보됐다는 최종 검증으로 보고하지 않는다.

# 사전등록: 앱 선택기와 동점 처리의 선호 추정 정확도 (2026-10-06)

돌리기 전에 커밋한다. 결과를 본 뒤 기준을 바꾸지 않는다.

## 왜

`2026-10-06_gepa_app_results.md` 에서 앱 경로의 정확 복원이 12/30 이었다. 같은 30명을 기본
선택기로 학습한 지난 실험(`heldout_comparison.json`)은 19/30 (63%) 이었다. 두 실행은 선택기와
함께 동점 처리 방식도 사실상 달랐다:

- 기본 선택기는 1위 값을 늘 같은 쪽에 놓지 않지만, 앱 선택기(`contrast_first`, `avoid_repeats`)는
  양 끝 값부터 묻고 A/B 배치를 무작위로 정한다.
- 두 실행 모두 페르소나는 legacy-a (두 후보 점수가 같으면 A) 였다.

`service._rebuild` 의 주석은 "합성 사용자로 전 조합을 재면 복원율은 기본 동작과 같다"고 적는다.
그 측정은 실제 생성 없이 조합만 비교한 것이라 동점이 없다. 실제 생성에서는 검사 함수 점수가
같은 경우가 생긴다. 낮은 복원이 **선택기 때문인지, 동점을 A 로 몰아준 페르소나 때문인지** 가른다.

## 설계

같은 30명 (`heldout_comparison.pick_personas(30)`), 같은 학습 문서, 8회, 후보 생성 gpt-4o-mini.
학습만 한다 (프롬프트 적용·GEPA 없음).

| 칸 | 선택기 | 동점 처리 |
|---|---|---|
| default × legacy-a | `UncertaintySelector(seed=0)` 기본 | 같으면 A |
| default × record-tie | 같음 | 같으면 "비슷해요" (tie) |
| app × legacy-a | `service.start_session` / `submit_choice` | 같으면 A |
| app × record-tie | 같음 | 같으면 "비슷해요" |

default 칸은 `heldout_comparison.learn_prompt` 를, app 칸은 앱 함수를 그대로 쓴다. default ×
legacy-a 는 19/30, app × legacy-a 는 12/30 을 재현해야 한다 (같은 시드·캐시). 재현되지 않으면
나머지 칸을 해석하지 않고 그 차이부터 적는다.

## 지표

- **주 지표: 정확 복원** - 두 축의 추정값이 페르소나 조합과 모두 같은 사람 수. 신호가 없어 정하지
  못한 축(`has_signal` 거짓)은 틀린 것으로 센다 (앱은 그 축을 프롬프트에서 뺀다).
- 축별 정확 복원, 정하지 못한 축 수, 8회 중 동점(점수가 같았던 비교) 수.

## 판정 (미리 정한다)

주 비교는 **app × record-tie 대 app × legacy-a** (앱에는 이제 "비슷해요" 버튼이 있으므로 실제
사용에 가까운 쪽이 record-tie). 사람별 페어드 - 한쪽에서만 맞힌 사람 수로 양측 부호검정
(`experiments/result_statistics.sign_test_p`).

- record-tie 가 더 많이 맞히고 p < 0.05 → "낮은 복원은 동점을 A 로 몰아준 페르소나 탓이 크다".
- 차이가 p ≥ 0.05 → "동점 처리로는 설명되지 않음". 이어서 app 대 default (같은 동점 처리끼리)를
  같은 방식으로 본다 - app 이 덜 맞히고 p < 0.05 면 "앱 선택기 자체가 실제 생성에서 덜 복원한다"
  로 적고, 아니면 "30명으로는 원인을 가르지 못함" 으로 적는다.
- 어느 경우도 앱 동작은 이 결과만으로 바꾸지 않는다. 바꿀 근거가 나오면 별도로 제안한다.

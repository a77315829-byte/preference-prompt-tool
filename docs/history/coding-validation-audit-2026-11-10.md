# 코딩 검증 범위 재점검

2026-11-10, `microstone`. 기존 코드·문서·보존된 결과를 읽어 확인했다. 이번 점검에서 모델 API를 호출하거나 생성 코드를 실행하거나 기존 결과를 다시 만들지 않았다.

**코딩은 일부 구현과 제한된 생성 결과를 검증했지만, 현재 제품 전체의 기능 정확도·맞춤 지침의 우위·사람의 사용 효과가 검증된 상태는 아니다.** 요약 검증이 이를 대신하지 않는다. 다음의 세 층을 구분해야 한다.

- 선택·저장·재사용이 의도대로 작동하는가: 구현 검사가 있다.
- 만든 지침으로 나온 코드가 조건과 기능을 만족하는가: 일부 과제 결과가 있으나 현재 지원 범위 전체에는 부족하다.
- 사람이 더 편하고 빠르게 쓰며 결과를 선호하는가: 실사용자 결과가 없다.

## 이번 점검에서 직접 대조한 범위

Luna 파일럿 JSON의 100개 행을 조건별로 다시 세어 위 기능·엄격 통과 수가 집계와 같은 것을 확인했다. 실제 버그 2조건·3조건 결과 JSON과 TAP 로그 위치, 프로토타입 12개 통과 로그도 확인했다. 새 생성·평가 실행은 하지 않았다.

공개 무료 검사 스냅샷과 현재 파일 SHA-256를 비교하면 `coding_examples.py`·`coding_framework_examples.py`는 같고 `coding_elicitation.py`·`coding_instructions.py`는 다르다. 이것만으로 동작 변화나 회귀를 단정하지 않지만, 과거 스냅샷을 현재 코드 그대로의 검증이라고 표시해서는 안 된다. 이후 선택 흐름 검증 기록은 별도로 존재한다.

이전 React 생성 실험의 `data/coding_ai_quality_trial.json`, `stage4.json`, 서비스 경로의 `routed/holdout/holdout_v2/holdout_v3/product_search/signup/todo_evaluation.json`, `stage5_eval.json`, `stage6_eval.json`은 현재 작업 공간에서 찾을 수 없었다. 기존 문서의 성공 기록을 삭제하거나 재현했다고 표현하지 않는다. 현재 보존된 패치·로그·집계가 있는 2026-11-09 실제 버그 실험과 증거 수준이 다르다.

Luna 100회는 이전에 승인받아 실행한 유료 API 실험이고 기록된 사용량 환산 비용은 $0.01391이다. **이번 재점검의 유료 API 호출은 0회**다. 과거 비용을 현재 요금 견적으로 재사용하지 않는다.

## 현재 제품과 프로토타입의 차이

현재 AI 답변 방식 설정은 설명·주석·구성·출력 **4항목**을 유지한다. `coding_contract_v1`은 설명 개수/형식과 Markdown·JSON 전달 **2항목**만 검사하는 별도 모듈이며 웹 앱의 생성기를 대체하지 않았다. JSON 전달은 현재 제품의 ‘변경 부분 중심’과 같은 설정이 아니다.

React 코드 스타일 비교는 구성·스타일 관리·타입 작성의 **3축**이며, AI 답변 방식 설정의 4항목과 별도 기능이다. 해당 경로의 합성 자료나 타입·빌드 결과를 새 4항목의 효과로 옮겨 쓰지 않는다. 현재의 GEPA 13개 환경 지원은 **연결·제한된 평가 지원 범위**이지 13개 환경 모두의 코드 실행 정확도 검증 완료라는 뜻이 아니다.

## 다음에 해야 할 코딩 검증

요약 개선이 끝나도 코딩 검증은 별도로 남는다. 첫 후속 실행은 TypeScript/React 하나로 좁히고, 현재 제품에서 실제 내보내는 지침을 동결해 아래를 진행하는 것이 맞다.

1. 개발 4과제·최종 8과제 계획에 맞춰 상태 전이·입력 검증·props 변경·기능 추가 등 서로 다른 작업과 독립 인수 검사를 먼저 작성한다. 기존 요청 동기화 버그와 유사 변형은 새 최종 과제 수에 넣지 않는다. 정답과 의도적 결함으로 검사기를 대조한다. 이 과제 수는 작업량 제한이며 통계적 충분성 근거가 아니다.
2. 일반 요청, 동일 조건을 명시한 강한 수동 프롬프트, 현재 제품 조립 프롬프트를 같은 작업·코드·모델 설정으로 비교한다. **직접 설정과 예시 선택이 같은 지침을 만들면 별개의 효과 조건으로 세지 않는다.** 새 프로토타입을 시험하려면 현재 제품과 별도 버전으로 표시한다.
3. 독립 보조 에이전트의 첫 결과를 보존하고, 코드를 먼저 검토한 뒤 비밀 데이터 없는 격리된 실행 환경에서 TypeScript 검사·빌드·React 실제 렌더링/이벤트를 확인한다. JSDOM과 실제 브라우저, 모의 HTTP와 실제 API 검사를 구분한다. 현재 정적 GEPA 점수로 실행 검사를 대체하지 않는다.
4. 지시 준수·기능 통과·동시 통과·미실행/미지원 수를 분리한다. 설명·주석의 유용성, 자연스러운 역할 분리는 개수만으로 성공 처리하지 않는다. 사용자 없이 수행한 에이전트 시간은 사람의 시간 절감으로 보고하지 않는다.
5. 실패와 동률도 완료 결과로 공개한다. 현재 기본 지침이 수동보다 더 낫다는 결론을 강제로 만들지 않고, 기능 회귀가 있는 후보는 자동 채택하지 않는다. 유료 API 없이 코드 후보를 만들 수 있지만 Codex 사용량은 소비될 수 있다.

사용자에게는 **“코딩도 추가 검증이 필요합니다. 일부 구현·과제는 검사했고, 현재 기능 전체의 정확도와 개인화 효과는 아직 확보하지 못했습니다”**라고 설명하는 것이 정확하다.

# 2026-11-04 코딩 GEPA 항목별 판정과 점수 근거

## 변경 이유

큰 숫자만 보이는 74 → 74는 무엇을 검사했는지와 사용자 선택의 반영 여부를 설명하지 못했다. 더 나은 후보를 찾지 못한 경우의 사후 점수는 원본 유지 결과인데, 탈락 후보의 점수로 오해할 수도 있었다.

## 구현

- 비교 화면은 기능 정적 검사와 네 가지 선택 선호의 전후 확인 수·항목별 증가/감소/유지를 우선 표시한다. 별도 확인 과제가 기본이며 후보 선택 과제로 전환할 수 있다.
- `coding_evaluation_report.py`에 기존 기능 65%·형식 35%·기본 구조 미확인 0점의 계산 규칙을 공통화했다. v1의 판정 조건·가중치·반올림·후보 채택 조건·평가 버전은 바꾸지 않았다. 점수를 높이기 위한 기준 조정은 하지 않았다.
- 환경별 검사에서 설명 글자 수·인식된 줄 시작 번호/목록, 주석 수, 함수/코드 블록 또는 클래스 수, 변경 과제 여부와 import/클래스 선언 유무를 기록한다. 기존에 없던 측정값을 과거 기록에 채워 넣지 않는다.
- 보고서에 계산 비중과 선택별 판정 기준, 후보 선택 과제의 전후 세부 결과를 포함한다. 기존 별도 과제 결과·원본·보관함 저장 방식은 유지한다.
- `CodingEvaluationBreakdown.jsx`는 항목별 결과를 먼저 보여 주고 계산식·숫자는 접힌 참고 정보로 둔다. 세부 기준과 과제별 관측값도 펼쳐 확인한다. 상세 기록이 없으면 미기록임을 안내한다.
- 개선이 없거나 별도 과제에서 같거나 낮으면 추가 개선이 확인되지 않았다고 표시한다. 원본 유지 시 프롬프트·답변의 사후 표제를 원본 유지로 바꾼다. 같은 총점에서도 항목별 상쇄 변화를 구분한다.

## 74점 해석과 한계

- 이번 Spring Boot 사례는 과제별 기능 검사 4/4가 충족되어 65점, 형식 선호 1/4(출력 방식)가 충족되어 8.75점, 합계 73.75점(정수 반올림 74점)이다. 별도 과제 2개를 합치면 기능 8/8·선호 2/8이다.
- 설명은 325자/209자였으나 v1 정규식이 요구하는 줄 시작 번호/목록을 인식하지 못했다. 마크다운 제목에 붙은 번호는 누락될 수 있다. 주석은 1개/0개, 클래스는 1개/0개였다. 숫자·개수 기반 대리 지표의 한계이며 실제 선호 미반영이라는 확정 판정이 아니다. 변경 부분만 출력하면 클래스 수가 적어질 수 있는 지표 간 관계도 검증이 필요하다.
- 65/35 비중이 사용자 만족도를 예측한다고 검증하지 않았다. 74점은 일반적인 프롬프트 품질·성공률·만족도 점수가 아니다. 이번 원본 유지 결과는 GEPA의 개선 효과를 보여 주지 않는다.
- 선택 기반 지침 생성·저장·재사용은 GEPA와 점수 없이도 사용할 수 있다. GEPA는 선택 기능이며 실제 사용자의 답변 비교와 자동 판정의 일치 여부, 여러 독립 과제에서의 효과를 검증해야 한다.

## 확인

- Python 관련 검사 29개(두 환경의 GEPA·계정별 API·점수 설명·보관함)와 프론트 전체 77개, Vite 빌드 통과. 마지막 배너 중복 제거 후 새 안내 문구에 맞게 회귀 검사를 수정하고 프론트 전체 77개·빌드를 다시 확인했다.
- 실제 Spring Boot 실행의 기존 캐시만 허용하는 생성 함수로 GEPA를 다시 계산했다. 캐시 조회 9회, 새 모델 호출 0회이며 전후 0.7375·원본 유지 결과가 같았다. 원본 프롬프트·평가 피드백이 그대로여서 기존 캐시를 재사용한다.
- 로컬 미리보기에서 동일 선택으로 다시 실행해 실제 과제별 관측값과 65 + 8.75 = 73.75 계산식을 확인했다. 원본 저장본을 수정하거나 새 항목으로 저장하지 않았다. 증거는 Git에 넣지 않는 `data/spring-gepa-score-breakdown-replay.json`과 화면 캡처다.

# 개발자용 프롬프트 작업 공간: 구현 계획 및 작업 지시서

작성일: 2026-10-02

## 0. 이 문서를 읽는 구현 담당자에게

기존 프로젝트를 유지하면서 아래 1차 MVP를 구현한다. 새 앱이나 별도 프레임워크로 다시 만들지 않는다. 저장소의 최신 지침과 작업 상태를 먼저 확인하고, 다른 사람이 수정 중인 파일을 덮어쓰지 않는다.

이 문서는 구현 계획이다. 여기 적힌 기능이 이미 완료됐다고 README나 화면에 표시하지 않는다. 2차·3차 범위는 1차가 끝났다고 자동으로 착수하지 않는다.

**첫 목표:** 업무 설명을 입력하고 요구사항을 확인한 뒤, 변수형 프롬프트를 만들고 샘플 데이터로 시험하여 개발용 파일로 내보내는 흐름을 완주한다.

**AWS 담당 경계:** AWS는 팀원 담당이다. 이번 작업에서는 합성 비용 데이터를 예제로 사용할 뿐, 실제 계정 조회·권한·리소스 탐지 기능을 만들거나 수정하지 않는다. 기존 AWS 화면과 도메인, 검사 함수도 유지한다. 공통 기능이 준비되면 AWS 담당자가 자신의 데이터와 검사를 연결할 수 있게 한다.

이 요청에 포함되지 않은 배포, 실제 AWS 호출, 클라우드 리소스 변경, 새 라이브러리 설치는 하지 않는다. 커밋·푸시는 별도 사용자 지시와 저장소 정책에 따른다.

## 1. 제품 목적

> 전문가의 경험과 사용자의 선택을 바탕으로, 바로 쓰거나 서비스에 연결할 수 있는 맞춤형 프롬프트를 만드는 작업 공간.

초기 대상은 업무 담당자와 AI 기능을 구현하는 개발자가 함께 일하는 소규모 팀이다. 업무 담당자는 규칙과 예시를 제공하고, 개발자는 입출력 형식을 확인해 서비스에 연결한다. 이 대상의 실제 수요는 앞으로 확인할 가설이다.

두 가지 생성 경로를 제공한다.

| 경로 | 산출물 | 이번 작업 |
|---|---|---|
| 바로 사용하기 | 복사 가능한 프롬프트, 도구별 지침 파일 | 기존 동작 유지 |
| 서비스에 연결하기 | 시스템 지침, 입력 템플릿, 변수 정의, 출력 형식, 실행 예제 | 1차 MVP 추가 |

개발자용 경로의 맞춤화는 개인의 문체, 팀의 규칙, 업무 조건을 포함한다. 반드시 지켜야 할 조건은 선호 투표로 변경하지 않는다.

## 2. 현재 코드에서 먼저 확인할 부분

아래는 2026-10-02 확인 기준이며 구현 시 최신 코드를 다시 확인한다.

| 기존 파일 | 활용 방향 |
|---|---|
| `frontend/src/app/App.jsx` | 기존 화면 안에 새 진입점 연결 |
| `api_server.py` | 기존 API 방식으로 새 경로 추가. 프레임워크 교체 금지 |
| `agents/prompt_polish.py` | 점검·다듬기 방식 참고. 문장 점검을 성능 검증으로 표현하지 않기 |
| `engine/generator.py` | 모델 호출·캐시·시간 제한 방식 확인 후 기존 공개 함수 재사용 가능성 판단 |
| `service.py` | 기존 선호 비교 루프 유지. 자유 입력에 기존 축을 억지로 끼워 넣지 않기 |
| `exporters.py` | 기존 내보내기 유지. 서비스용 묶음은 별도 모듈로 추가 |
| `template_library.py` | 기존 템플릿 진입점과 연결 가능성 확인 |
| `team.py` | 팀 선택 집계와 프로젝트 저장은 다른 기능이므로 구분 |

이번 작업은 `engine/`, `checks/`, `domains/`, `optimize/`의 기존 구현을 변경하지 않는 범위로 설계한다. 공통 코드 변경이 꼭 필요하면 필요한 이유와 대안을 먼저 정리한다.

## 3. 사용자 흐름

1. 사용자가 ‘서비스에 연결할 프롬프트 만들기’를 선택한다.
2. 작업 목적·업무 설명·좋은 결과 예시를 자유롭게 입력한다.
3. AI가 내용을 목적·입력·필수 규칙·선호·출력·미결 사항으로 구조화한다.
4. 사용자가 수정하고 ‘이 요구사항으로 만들기’를 누른다.
5. 확인한 요구사항으로 템플릿을 생성한다.
6. 샘플 JSON 입력을 넣고 결과를 시험한다.
7. 누락 변수·출력 형식·규칙 확인 상태를 표시한다.
8. 프롬프트와 실행 자료를 다운로드한다.

정리한 요구사항을 사용자가 확인하기 전에는 확정된 정책으로 취급하지 않는다. AI의 추측은 ‘제안’, 원문에서 확인한 것은 ‘입력에서 추출’로 구분한다. 충돌하는 규칙은 임의로 해결하지 않고 미결 사항으로 남긴다.

## 4. 업무 지식의 분류

| 분류 | 예시 | 처리 |
|---|---|---|
| 목적 | 비용 현황을 설명한다 | 프롬프트의 작업 정의 |
| 필수 규칙 | 입력에 없는 금액을 쓰지 않는다 | 고정 조건, 수정 시 명시적 확인 |
| 선호 | 핵심부터 짧게 설명한다 | 사용자가 편집하거나 결과 비교로 조정 |
| 입력 변수 | 조회 기간, 통화, 비용 항목 | 요청마다 코드가 채움 |
| 참고 자료 | 정책 문서, 매뉴얼 | 지시와 구분한 실행 입력 |
| 출력 계약 | 합계·요약·항목 목록의 JSON | 프로그램이 확인할 형식 |
| 미결 사항 | 빈 목록에서 어떻게 답할지 | 사용자에게 확인 |

업무 설명과 참고 자료는 분석할 데이터다. 그 안의 ‘이전 지시를 무시하라’ 같은 문장을 도구 실행 명령으로 취급하지 않는다. 입력에서 추출한 정책도 사용자 확인을 거친다.

대량 자료 검색·RAG·파인튜닝은 이번 범위에 없다. 소량의 참고 텍스트를 별도 변수로 전달하는 것까지만 고려한다. 전문가의 지식을 모델에 학습했다고 표현하지 않는다.

## 5. 1차 화면

새 공간은 기존 React 디자인을 사용한다. 별도 대규모 UI 개편은 하지 않는다.

### A. 설명 입력

- 작업 이름, 자유로운 업무 설명, 선택적인 결과 예시.
- ‘샘플로 시작’ 버튼으로 합성 비용 보고 예제 제공.
- 정리 시작 전 API 사용 여부 표시.

### B. 요구사항 확인

- 목적, 변수, 필수 규칙, 선호, 출력 형식, 미결 사항을 편집 가능한 형태로 표시.
- AI가 제안한 내용은 원문에서 추출한 내용과 구분.
- 원문과 추출 항목을 대조할 수 있게 원문 근거 또는 짧은 발췌를 보관.
- 미결 사항이 남으면 초안 저장은 허용하되 ‘확인 완료’ 상태로 표시하지 않음.

### C. 프롬프트 편집·시험·내보내기

- 시스템 지침과 입력 템플릿을 따로 표시.
- 시험 JSON 입력, 실행 결과, 검사 결과 표시.
- 결과에 `통과 / 실패 / 미평가`를 구분. 실행하지 않은 것을 통과로 표시하지 않음.
- 프롬프트를 수정하면 이전 시험 결과를 ‘이전 버전 결과’로 표시.
- 필수 규칙 변경 시 요구사항 재확인 필요.
- 1차에는 자동 재작성 반복과 영속 버전 이력 없이 수동 편집·재시험을 지원.

## 6. 데이터 모델 제안

UI와 분리된 순수 Python 자료구조를 사용한다. 구체적인 타입 이름은 저장소 규칙에 맞춰 조정할 수 있다.

```text
PromptProject
  id, title, schema_version, revision
  raw_description
  requirements
    purpose
    variables: name, description, type, required
    hard_rules: id, text, origin, source_excerpt
    preferences: id, text
    output_contract
    open_questions
  confirmed_requirements_revision
  artifact
    system_prompt
    input_template
  runs
    artifact_revision, input_hash, model, mode
    output, checks, elapsed_time, usage_if_available
```

1차는 세션 중 메모리에 보관하고, 프로젝트 JSON 내려받기·가져오기로 이어서 작업한다. 2차에서 영속 저장을 추가한다. 브라우저/서버 재시작 시 저장 범위를 정확히 안내한다. 자동으로 원문·실행 결과를 공용 로그에 남기지 않는다.

## 7. 변수와 출력 계약

- 입력 템플릿은 제한된 `{{variable_name}}` 치환만 지원한다.
- `eval`, 임의 코드, 템플릿 내부 함수 호출을 실행하지 않는다.
- 누락된 필수 변수는 모델 호출 전에 안내한다.
- 변수 값 안의 중괄호나 지시문을 다시 템플릿으로 평가하지 않는다.
- 지침과 요청 데이터는 메시지·구획으로 분리한다. 분리만으로 모든 프롬프트 인젝션이 해결됐다고 주장하지 않는다.
- 출력 계약은 1차에 지원할 필드 타입·필수 필드·배열 범위를 명시한다.
- 새 검증 라이브러리 없이 구현한다면 제한된 계약만 검사하고, 전체 JSON Schema 표준 지원이라고 표시하지 않는다.
- JSON 파싱·필드 타입 검사와 의미 정확성 검사는 따로 보고한다.

## 8. AWS 담당자와 충돌하지 않는 샘플

샘플 이름: ‘합성 비용 데이터 보고’. 실제 AWS 계정·요금·유휴 리소스 탐지 결과가 아니다.

### 자유 설명 예시

> 우리 팀은 비용 보고를 핵심부터 읽고 싶습니다. 조회 기간과 총액을 먼저 설명하고 서비스별 금액을 정리해주세요. 비용이 크다는 이유로 낭비라고 단정하지 마세요. 입력에 없는 금액, 리소스 ID, 절감액을 만들지 마세요. 개발자가 처리할 수 있게 JSON으로 받고 싶습니다.

### 합성 입력

```json
{
  "period_start": "2026-09-01",
  "period_end_exclusive": "2026-10-01",
  "currency": "USD",
  "total": "37.50",
  "services": [
    {"name": "Compute", "amount": "25.00"},
    {"name": "Storage", "amount": "12.50"}
  ]
}
```

### 의도한 출력 구조

```json
{
  "currency": "USD",
  "total": "37.50",
  "summary": "합성 데이터의 총 비용은 37.50 USD입니다.",
  "items": [
    {"service": "Compute", "amount": "25.00"},
    {"service": "Storage", "amount": "12.50"}
  ],
  "limitations": ["비용만으로 유휴 여부나 낭비를 확정할 수 없습니다."]
}
```

문장까지 정답 하나로 고정하지 않는다. JSON 파싱, 합계·통화 보존, 서비스명·금액 대응을 코드로 확인한다. 통화 계산이 필요하면 기존 표준 라이브러리 `Decimal`을 사용한다.

설명 문장 속 근거 없는 판단까지 완벽하게 자동 검증한다고 주장하지 않는다. 해당 부분은 수동 검토 항목으로 표시한다. 합계 불일치 입력은 합계를 임의로 고쳐 정상 처리하지 않고 확인이 필요한 입력으로 분류한다.

### 팀원 영역에서 하지 않을 일

- boto3 호출이나 새 AWS 인증 기능 추가.
- 실제 비용 조회·리소스 생성·삭제.
- `domains/idle_tracker.yaml`, `checks/idle_tracker.py`의 변경.
- 기존 AWS 화면이나 `/api/aws/costs` 흐름 교체.
- 데모 데이터를 실제 조회 결과로 표시.

AWS 담당자에게 넘길 것은 입력 계약, 결과 형식, 샘플 테스트, 선택적으로 연결할 인터페이스다. 실제 조회 연동은 담당자가 결정한다.

## 9. 내보내기

첫 버전은 고정 파일명의 ZIP 다운로드를 제공한다.

```text
prompt-package/
  prompt.md
  input_template.txt
  variables.json
  output_contract.json
  input.example.json
  render_example.py
  project.json
  README.md
```

- `render_example.py`는 먼저 외부 API 없이 변수 검증과 메시지 구성을 실행할 수 있게 한다.
- 실제 모델 호출 예제는 사용하는 라이브러리와 키 설정, 비용 발생을 명시한다. 키를 파일에 넣지 않는다.
- `output_contract.json`은 1차에서 구현한 계약 형식이다. 표준 JSON Schema 내보내기는 지원 여부를 별도로 결정한다.
- 사용자 입력으로 파일 경로를 만들지 않는다. ZIP 내부 경로는 고정하고 `../` 경로가 들어갈 여지를 없앤다.
- `project.json`에는 비밀 키를 넣지 않는다. 원래 설명·샘플·결과를 포함할지 다운로드 전에 선택하도록 한다.
- README에는 사용 방법, 모델 의존성, 버전, 실행한 검사와 미평가 항목을 적는다.
- 요구사항이 바뀌었거나 마지막 시험 이후 수정했다면 시험 결과를 현재 버전 검증으로 내보내지 않는다.

## 10. 계속 다듬는 공간: 2차

1차 완주 후 다음 기능을 추가한다.

1. 프로젝트 영속 저장·삭제와 버전 이력.
2. 개선 방향 추천: 명확화, 중복 축소, 출력 일관성, 예외 처리, 근거 제한, 예시 보강.
3. 추천 이유와 바뀔 규칙 표시.
4. 원본·수정안의 지시문 차이와 실제 결과 나란히 비교.
5. 사용자 승인 후 새 버전으로 저장, 이전 버전 복원.

필수 규칙은 재작성 지시에 보존 대상으로 전달한다. 텍스트가 남아 있다는 검사만으로 의미가 보존됐다고 보장하지 않는다. 중요한 변경은 사용자에게 확인받고 결과 사례로 다시 확인한다.

범용적인 ‘좋은 프롬프트 95점’을 만들지 않는다. 구조 점검, 업무 기준, 사용자 선호를 서로 다른 항목으로 표시한다.

## 11. GEPA: 3차 선택 기능

| 준비 상태 | 제공할 기능 |
|---|---|
| 업무 설명만 있음 | 구조화·초안 생성 |
| 시험 입력도 있음 | 실행과 수동 비교 |
| 평가 사례와 기준까지 있음 | 선택적 GEPA 최적화 |

GEPA는 프롬프트를 실행하고 평가·수정하는 반복 과정이다. 일반적인 문장 다듬기와 구분한다.

- 필수 규칙 위반은 선호 점수와 분리하여 후보 채택을 막는 조건으로 둔다.
- 평가 함수는 도메인별 명시된 검사로 구성한다. 자유로운 업무 설명만으로 신뢰할 수 있는 평가 함수를 자동으로 얻었다고 가정하지 않는다.
- 임의 생성 Python 검사 코드를 새 공개 경로에서 실행하지 않는다.
- 작업 큐·진행 조회·호출 예산·실패 복구를 설계한다.
- 최적화용 사례와 최종 확인 사례를 나눈다.
- 좋아지지 않았으면 기존 버전을 유지하고 그 결과를 보여준다.
- GEPA 결과가 나오면 자동 배포하거나 기존 버전을 덮어쓰지 않는다.

## 12. 권장 모듈 경계

기존 코드 구조를 확인한 뒤 이름은 조정할 수 있다.

```text
prompt_workspace/
  models.py          # UI 독립 자료구조
  requirements.py    # 설명 구조화, 검증, 사용자 확인 상태
  builder.py         # 확인한 요구사항으로 프롬프트 생성
  renderer.py        # 제한된 변수 치환과 입력 검증
  runner.py          # 시험 실행, 결과와 검사 상태
  exports.py         # 고정 파일명 묶음 생성
frontend/src/features/prompt-workspace/
tests/test_prompt_workspace_*.py
```

공통 모듈에 AWS 고유 규칙을 넣지 않는다. 샘플 데이터와 샘플 전용 검사는 별도 예제 영역에 둔다. 새 패키지의 순수 Python 코드는 Streamlit을 import하지 않는다.

`api_server.py`와 앱 진입점은 필요한 연결만 추가한다. 단계별 API는 설명 구조화, 확인한 요구사항 기반 생성, 시험 실행, 내보내기로 나눈다. 요청 크기·시간 제한과 오류 분류를 기존 방식에 맞춘다.

## 13. 호출·저장·안전 기본 조건

- 모델명은 서버 설정으로 결정한다. 클라이언트가 비싼 모델명을 임의 지정하지 못하게 한다.
- 설명 구조화·프롬프트 생성·시험 실행도 모두 비용 상한에 포함한다.
- 모델 결과는 기존 정책에 맞게 캐싱한다. 입력, 시스템 지시, 모델, 생성 설정, 프롬프트/스키마 버전 등 결과에 영향을 주는 조건을 캐시 키에 포함한다.
- 실패·빈 출력·파싱 오류를 성공 캐시로 저장하지 않는다.
- 모델 호출에는 시간 제한과 출력 상한을 둔다.
- 공급자 오류 원문이나 API 키를 화면·로그·내보내기에 넣지 않는다.
- temperature=0도 완전한 결정성을 보장하지 않는다. 모델·설정·버전·캐시 사용 여부를 기록한다.
- 1차는 로컬 사용 범위다. 다중 사용자 공개 서비스의 인증·프로젝트 접근 제어가 구현됐다고 간주하지 않는다.
- 모델이 생성한 코드나 업로드한 파일을 서버에서 임의 실행하지 않는다. 실행 예제는 고정된 템플릿으로 만든다.

## 14. 검증 수준과 완료 기준

사용자 화면의 상태는 다음처럼 구분한다.

- 초안: 요구사항 확인 전.
- 확인된 요구사항으로 생성: 사용자 확인을 반영함.
- 예제 실행 확인: 명시한 입력·버전에서 실행함.
- 검사 통과: 표시한 검사 항목에 한정함.
- 미평가: 의미 정확성 등 아직 확인하지 않은 항목.

1차 완료 기준:

- [ ] 자유 설명에서 요구사항 초안을 만들고 사용자가 편집·확인할 수 있다.
- [ ] 미결 사항을 임의 확정하지 않는다.
- [ ] 확인한 요구사항으로 시스템 지침과 입력 템플릿이 생성된다.
- [ ] 필수 변수 누락을 호출 전에 안내한다.
- [ ] 합성 비용 데이터로 실행하고 구조·금액 검사를 표시한다.
- [ ] 입력 변경과 프롬프트 변경에 맞춰 결과 버전이 구분된다.
- [ ] 프로젝트 JSON으로 저장·불러오기를 할 수 있다.
- [ ] 내보낸 예제를 네트워크 없이 실행해 메시지를 구성할 수 있다.
- [ ] 빈 입력, 깨진 JSON, 누락 값, 모델 오류에서 사용자에게 다음 행동을 안내한다.
- [ ] 기존 비교·템플릿·다듬기·팀·AWS 기능에 회귀가 없다.

정상 사례 외에 빈 서비스 목록, 필수 통화 누락, 합계 불일치, 문자열 안의 중괄호, 충돌하는 요구사항을 포함한다. 테스트는 호출을 모킹한 기능 검증을 먼저 하고, 실제 API는 최소 사례로 별도 확인한다.

몇 개의 예제 통과를 보편적인 효과나 정확성 보장으로 발표하지 않는다. 논문 수준 비교 실험은 ‘기존보다 우수하다’는 연구 주장을 할 때 별도 수행한다.

## 15. WBS 반영안

| 기존 항목 | 연결 또는 변경 |
|---|---|
| 3.7 바로 쓰기 | 서비스용 템플릿·실행 예제 내보내기 |
| 3.10 프롬프트 다듬기 | 2차의 개선 방향 추천·변경 비교 |
| 3.11 프롬프트 시험 적용 | 변수 입력·출력 검사·전후 비교 |
| 3.6 길이 지시 개선 | 후속 동적 템플릿 적용 사례. 이번 AWS 샘플과 분리 |
| 3.5 GEPA | 3차의 선택적 최적화 |
| 신규 | 업무 설명 구조화와 확인, 프로젝트 자료구조, 서비스용 묶음 내보내기 |

팀 프롬프트의 영속 저장과 개인 프로젝트 버전 저장은 다른 작업이다. 같은 것으로 중복 계산하지 않는다. 담당·날짜·공수는 팀 합의 후 실제 WBS에 반영한다.

## 16. 구현 순서와 종료 보고

1. Git 상태와 지침, 기존 모델 호출·API·프론트 연결 방식 확인.
2. 자료구조와 합성 샘플 작성.
3. 제한된 렌더러·입력 계약 검사·내보내기를 API 없이 구현.
4. 요구사항 구조화와 사용자 확인 흐름 구현.
5. 프롬프트 생성·시험 실행과 캐시·호출 상한 연결.
6. React에 하나의 완주 가능한 경로 연결.
7. 필요한 회귀 테스트와 브라우저 흐름 확인.
8. 구현한 범위, 실행 방법, 검사 결과, 남은 제한을 보고.

한 번에 파일 하나 또는 함수 하나 단위로 작업한다. 새 라이브러리가 필요하면 이유와 기존 의존성 대안을 먼저 설명한다. 별도 실험 중인 파일과 기존 AWS 담당 파일은 건드리지 않는다.

최종 보고에는 다음을 포함한다.

- 실제로 완주한 사용 흐름.
- 실제 API 호출 여부와 확인 가능한 비용/호출 수.
- 실행한 테스트와 생략한 확인.
- AWS 담당자에게 넘길 입력·출력 계약.
- 2차·3차로 남긴 기능.

**첫 버전의 성공은 ‘전문가를 복제했다’가 아니라, 담당자의 설명을 확인 가능한 요구사항과 재사용 가능한 실행 템플릿으로 옮겼다는 것이다.**

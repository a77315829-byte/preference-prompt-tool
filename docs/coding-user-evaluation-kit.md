# 코딩 도움 — 실제 참여자 평가 진행 키트

상태: **평가 준비 자료입니다. 실제 참여자 응답은 아직 수집하지 않았습니다.**

목적은 화면을 혼자 사용할 수 있는지와 선택 결과가 본인의 취향을 설명하는지 확인하는 것입니다. 자동 선택 시뮬레이션은 실제 참여자 평가를 대신하지 않습니다. 상세 기준은 [평가 계획](coding-user-evaluation.md)을 따릅니다.

## 1. 시작 전 진행자 준비

- 우선 React/TypeScript 코드를 읽을 수 있는 참여자 3~5명을 모집합니다. 개발 경험이 없는 분의 화면 사용 의견도 받을 수 있지만, 코드 이해도 결과와 섞지 않습니다. 작은 표본 결과를 전체 개발자의 의견으로 일반화하지 않습니다.
- 기록할 항목, 보관 장소·기간, 철회 요청 방법과 기한을 팀에서 정하고 참여자에게 설명합니다. 이 조건이 정해지기 전에는 수집을 시작하지 않습니다.
- 실명·연락처 대신 P01 같은 번호를 씁니다. 계정 비밀번호, API 키, 회사 코드, 개인정보는 기록하지 않습니다. 화면 녹화는 기본적으로 하지 않으며 필요하면 별도 동의를 받습니다.
- 먼저 **무료 데모만** 진행합니다. 실제 AI 평가는 호출 수·예산 승인 후 별도 세션으로 진행합니다. 이 문서를 준비하면서 유료 호출은 하지 않습니다.
- API 서버와 React 화면을 모두 실행합니다. [실행 안내](coding-user-evaluation.md#이-저장소를-macos에서-평가용으로-실행할-때)를 따르고 Vite가 출력한 주소를 사용합니다. 서버가 없는 프론트 단독 예시는 평가에서 제외합니다.
- 브랜치·커밋, 브라우저·화면 크기, 서버 설정과 실제 표시 모드를 기록합니다. 참여자에게 기존 평가 결과나 특정 스타일이 좋다는 설명은 하지 않습니다.

## 2. 참여자에게 보낼 문구

> React/TypeScript 코드 예시를 골라 나만의 코딩 프롬프트를 만드는 화면을 10~15분 정도 사용해 보실 수 있을까요? 화면에서 헷갈리는 부분과 결과가 본인의 취향을 잘 설명하는지 확인하려고 합니다. 이번에는 준비된 예시를 사용하는 무료 데모라서 입력한 기능에 맞는 새 코드를 AI가 만드는 평가는 아닙니다. 정답은 없고, 모르는 질문은 건너뛰거나 언제든 중단하실 수 있습니다. 참여 전 기록 항목·보관 기간·철회 방법을 안내드리겠습니다.

## 3. 첫 사용 — 도움 없이 진행

동의를 받은 뒤 다음 문장만 읽고 시작 시간을 기록합니다.

> 코딩 도움을 찾아서 “클릭 횟수를 보여 주고 초기화할 수 있는 React 버튼 컴포넌트”를 입력해 주세요. 화면 안내를 보며 더 마음에 드는 예시를 선택하고 결과까지 확인해 주세요. 결과를 실제 코딩 도구에 가져가 쓰려면 어떻게 하실지도 보여 주세요. 잘 모르겠거나 멈추고 싶으시면 말씀해 주세요.

진행자는 버튼 위치나 스타일 차이의 정답을 알려주지 않습니다. 도움을 요청하면 요청 시점과 내용을 적은 후 필요한 도움을 주고, 해당 작업은 **도움 없이 성공**으로 기록하지 않습니다.

데모의 입력값은 준비된 과제의 순서를 정할 뿐 해당 기능을 구현하지 않습니다. 회차마다 화면의 실제 과제명을 적습니다. 입력한 기능과 다른 예시가 나오는 것을 기능 생성 성공으로 세지 않습니다.

결과에 도달하거나 중단하면, 추가 버튼 조작을 시키기 **전에** 다음 질문을 합니다.

1. 방금 예시는 입력하신 기능을 새로 만든 결과였나요, 준비된 예시였나요? 그렇게 생각한 이유는 무엇인가요?
2. 무엇이 달라서 A 또는 B를 고르셨나요? 판단하기 어려웠던 회차가 있었나요?
3. 결과의 스타일 설명이 본인의 선택과 맞나요? 맞지 않거나 이해되지 않는 부분은 무엇인가요?
4. 프롬프트를 실제로 사용하고 싶으신가요? 부족한 점은 무엇인가요?
5. 가장 헷갈렸던 화면이나 조작은 무엇이었나요?

1번에 대한 응답은 먼저 그대로 기록한 뒤 오해가 있으면 바로 설명합니다. UI가 모드를 충분히 전달했는지도 별도로 기록합니다. 참여자에게 두 코드의 기능이 같다고 미리 단정하지 않습니다.

### 결과 설문

| 질문 | 응답 기준 |
|---|---|
| 코드 구조 설명이 내 취향과 맞나요? | 1~5 / 이해 못함 / 선호 없음 / 해당 없음 |
| 스타일 관리 설명이 내 취향과 맞나요? | 1~5 / 이해 못함 / 선호 없음 / 해당 없음 |
| 타입 작성 설명이 내 취향과 맞나요? | 1~5 / 이해 못함 / 선호 없음 / 해당 없음 |
| 최종 프롬프트를 이해할 수 있나요? | 1~5 / 판단 불가 |
| 실제 코딩 도구에서 사용하고 싶나요? | 1~5 / 판단 불가 |

일치도는 1=전혀 맞지 않음, 3=일부만 맞음, 5=매우 잘 맞음입니다. 이해도는 1=무슨 뜻인지 모르겠음, 3=일부 이해함, 5=혼자 설명할 수 있음입니다. 사용 의사는 1=사용하지 않겠음, 3=상황에 따라 사용, 5=다시 사용하고 싶음입니다. 2·4점은 양옆 기준 사이입니다. 판단 불가를 3점으로 바꾸지 않습니다. 결과가 ‘미결정’인 축은 특정 선호가 없다는 뜻이며 자동으로 불일치 처리하지 않습니다.

## 4. 추가 조작 확인 — 첫 사용 평가와 분리

첫 사용 설문이 끝난 뒤 새 세션에서 다음 조작을 요청합니다. 처음부터 버튼 이름을 알려준 작업이므로 **스스로 발견한 결과와 따로** 기록합니다.

| 요청 | 확인할 내용 |
|---|---|
| 예시 전체를 열고 다른 예시도 확인한 뒤 닫아 주세요. | 전체 보기·전환·닫기 가능 여부 |
| 이번에는 판단하기 어렵다고 표시해 주세요. | ‘비슷해요’ 선택 후 진행 가능 여부 |
| 이전 선택으로 돌아가 바꿔 주세요. | 수정 이후 화면·결과 반영 여부 |
| 결과에서 마지막 선택을 수정해 주세요. | 비교 화면 복귀 및 결과 갱신 여부 |
| 프롬프트만 복사하고, 개발 요청을 포함해서도 복사해 주세요. | 별도 빈 메모장에 붙여 넣어 내용 확인 |

붙여 넣은 자료는 평가에 필요한 범위만 확인합니다. 로그인·팀 공유·GEPA 최적화는 이 코딩 스타일 평가의 필수 과제가 아니며, 유료 최적화 버튼을 누르지 않습니다.

## 5. 진행자 기록지 — 참여자마다 복사

빈칸은 미수집입니다. 점수나 성공 여부를 미리 채우지 않습니다.

```text
참여자 번호:
평가 일시 / 동의 여부:
고지한 기록 범위 / 보관 기간 / 철회 방법:
개발 경험 / React·TypeScript 경험:
브랜치·커밋 / 브라우저 / 화면 크기:
평가 구분: 무료 데모 / 실제 AI (별도 승인) / 실패 후 데모 전환
서버 설정 / 실제 화면 모드 / 확인 근거 / 전환 사유:

[첫 사용: 추가 조작 안내 전]
시작·종료 시각 / 완료 또는 중단 / 중단 이유:
카테고리 찾기: 도움 없이 성공 / 도움 후 성공 / 미완료 / 미관찰
입력·비교 완료: 도움 없이 성공 / 도움 후 성공 / 미완료 / 미관찰
결과 확인·복사: 도움 없이 성공 / 도움 후 성공 / 미완료 / 미관찰
도움 요청 시점·내용 / 진행자 개입:
참여자가 이해한 실행 모드와 이유 (원문):
선택 이유 / 차이를 이해하지 못한 회차:
결과 구조 / 스타일 관리 / 타입 작성 (표시 그대로):
각 축 일치도 / 이해도 / 사용 의사 (점수 또는 비점수 응답):
불편했던 점 / 개선 의견 (원문):

[추가 조작: 요청받은 작업]
전체 보기·전환·닫기:
비슷해요:
이전 선택 수정:
결과에서 마지막 선택 수정:
프롬프트만 복사 / 요청 포함 복사 / 붙여 넣기 내용 확인:
각 작업의 도움 여부 / 오류 / 재현 순서:
```

회차 수는 화면의 실제 진행 수를 적고, 선택을 수정하면 이전 기록도 남깁니다. A/B 위치와 특정 스타일을 고정해서 연결하지 않습니다.

| 회차·수정 순서 | 화면의 과제명 | A/B의 관찰된 차이 | 선택(A/B/비슷해요) | 선택 이유·도움 여부 |
|---|---|---|---|---|
| | | | | |

## 6. 모아서 보고하기

| 항목 | 실제 수집 후 기입 |
|---|---|
| 동의한 참여자 수 / 완료 / 중단 | |
| 데모 / 실제 AI / 데모 전환 세션 수 | |
| 첫 사용에서 도움 없이 완료한 수 / 해당 작업 참여자 수 | |
| 추가 조작별 완료 수 / 해당 조작을 요청받은 수 | |
| 축별 일치도 점수 분포 / 유효 응답 수 | |
| 이해 못함·선호 없음·해당 없음·판단 불가 수 | |
| 반복된 문제 / 수정 우선순위 | |

소수 파일럿은 가능하면 ‘3명 중 2명’처럼 실제 인원으로 설명합니다. 중단·무응답을 숨기지 않고, 개발 경험과 실행 모드를 구분합니다. 모드가 바뀐 세션은 무료 데모 사용성 참고 자료로만 기록하고 실제 AI 기능 생성 성공률에는 넣지 않습니다.

## 7. 실제 AI 평가는 이후 별도 진행

팀이 호출 수·예산을 승인하고 설정을 확인한 뒤 같은 기준 요청으로 진행합니다. 데모 참여 경험 여부도 기록합니다. 새 기능 구현 여부·A/B 기능 동일성은 사용자 만족도와 별도로 코드 검사·타입 검사·동작 테스트로 확인합니다. 생성 코드는 검토 후 격리된 검증 환경에서 실행하며 참여자의 업무 환경에 바로 실행시키지 않습니다.

무료 데모 결과만으로 ‘AI가 임의 기능을 잘 구현한다’거나 ‘개인화로 성능이 좋아졌다’고 결론 내리지 않습니다. 개인화 효과를 비교하려면 별도의 미사용 과제에서 같은 모델·조건의 기본 프롬프트와 개인화 프롬프트를 블라인드로 비교해야 합니다. 상세 절차와 한계는 [평가 계획](coding-user-evaluation.md)을 참고합니다.

## 1. 현재 실제 코드 흐름

현재 프로젝트의 핵심 흐름은 대략 다음과 같다.

```text
도메인 YAML
   ↓
A/B 후보 생성
   ↓
사용자 선택
   ↓
Estimator
Bradley-Terry 스타일 utility 업데이트
   ↓
UncertaintySelector
다음 질문 선택
   ↓
축별 선호 + confidence
   ↓
Metric Builder
평가 함수 조립
   ↓
최종 개인 프롬프트
   ↓
선택적으로 GEPA 최적화
```

Estimator에서는 각 축의 값마다 utility를 0으로 시작하고, A와 B가 다른 축에 대해서 logistic probability를 계산한 뒤 gradient 방식으로 utility를 갱신한다.

또한 다음 질문도 단순 랜덤 방식이 아니라 현재 confidence가 낮은 축을 우선적으로 선택하고, utility가 가까워 구분하기 어려운 값을 비교하도록 구성되어 있다.

이 부분은 구조적으로 꽤 잘 설계되어 있다.

# 2. 가장 먼저 보완해야 할 연구적 약점

## `confidence`라는 이름이 너무 강함

현재 `confidence()`는 대략 다음 구조다.

```text
utility
 ↓
softmax
 ↓
entropy
 ↓
1 - normalized entropy
```

따라서 이 값은 엄밀한 의미에서

> 사용자의 실제 선호가 이 값일 확률 83%

을 의미하는 것이 아니다.

실질적으로는

> 현재 utility 분포가 얼마나 한쪽으로 뾰족한가

를 표현하는 heuristic score에 더 가깝다.

### 문제점

발표나 논문에서 다음과 같은 질문이 들어올 수 있다.

> confidence 0.72라는 값이 통계적으로 어떤 의미입니까?

현재 방식은 Bayesian posterior probability가 아니므로 이를 명확히 설명해야 한다.

### 추천 수정

변수명을 다음처럼 바꾸는 것도 안전하다.

- `preference_strength`
- `certainty_score`
- `utility_separation`

또는 보고서에서 다음처럼 정의할 수 있다.

> 본 연구의 confidence는 posterior probability가 아니라 추정 utility의 normalized entropy를 이용한 상대적 불확실성 지표이다.

이 부분은 우선순위가 높은 수정 사항이다.

# 3. Learning Rate `0.5`의 근거 부족

Estimator의 기본 learning rate가 `0.5`로 설정되어 있다.

Bradley-Terry 모델의 logistic 구조 자체는 관련 연구에 기반한다고 설명할 수 있지만,

> 왜 learning rate가 0.5인가?

라는 질문에는 현재 특별한 이론적 근거가 없다.

이는 구현상의 hyperparameter라고 보는 것이 맞다.

## 보완 방법

간단한 ablation experiment를 추천한다.

예:

```text
learning rate
0.1
0.25
0.5
0.75
1.0
```

각 값에 대해 다음을 측정한다.

- 4회 후 선호 복원 정확도
- 6회 후 선호 복원 정확도
- 8회 후 선호 복원 정확도
- 평균 convergence 속도
- noise 환경에서의 복원률

예시:

| Learning Rate | 4회 | 6회 | 8회 |
|---|---:|---:|---:|
| 0.1 | 53% | 66% | 72% |
| 0.25 | 61% | 78% | 86% |
| 0.5 | 67% | 85% | 90% |
| 0.75 | 64% | 82% | 88% |
| 1.0 | 59% | 76% | 84% |

이런 결과가 나온다면 0.5라는 값은 단순한 임의값이 아니라 실험적으로 선택된 hyperparameter로 설명할 수 있다.

# 4. 현재 질문 선택은 Information Gain이 아님

현재 selector는 대략 다음 방식이다.

1. confidence가 가장 낮은 축 선택
2. utility가 가장 가까운 값 두 개 선택

이 방식은 논리적으로 타당하고 실용적이다.

하지만 이를

> 최적의 질문을 선택한다

라고 표현하는 것은 과하다.

현재 구현은 정확히 말하면

> 불확실성 기반 heuristic active selection

에 해당한다.

각 질문을 했을 때 posterior uncertainty가 얼마나 감소하는지 계산하는 Expected Information Gain 방식은 아니다.

## 추천 표현

❌ 최적 질문 선택 알고리즘

✅ 불확실도 기반 적응형 질문 선택

향후 연구 방향으로는 다음을 제안할 수 있다.

> Expected Information Gain 기반 Active Preference Elicitation

# 5. 평가 함수 구조는 생각보다 잘 되어 있음

현재 metric builder는 개발자가 단순히

```text
길이 30점
스타일 50점
코드 20점
```

식으로 하드코딩한 구조는 아니다.

축별 검사 결과를 현재 선호 certainty에 따라 weighting하고 평균을 내며, 낮은 certainty의 축도 완전히 제거하지 않도록 최소 weight가 적용되어 있다.

또 freeform 축의 경우 사용자가 직접 입력한 명시적 요구이므로 더 높은 weight를 주는 구조도 존재한다.

## 다만 추가로 확인할 점

`MIN_AXIS_WEIGHT = 0.05`

같은 값 역시 다음 질문을 받을 수 있다.

> 왜 0.05인가?

### 추천 보완

다음 값들을 비교하는 민감도 분석을 수행한다.

```text
0
0.01
0.05
0.1
0.2
```

결과 변화가 크지 않다면 다음처럼 설명할 수 있다.

> 최소 축 가중치 변화에 대해 결과가 크게 변하지 않아 metric이 해당 hyperparameter에 민감하지 않음을 확인했다.

# 6. 현재 가장 큰 설계상 문제: 사용자 선택 오류를 너무 신뢰함

현재 비교 결과는 사실상 다음 두 개만 받는다.

```text
A
B
```

하지만 실제 사용자는 다음과 같은 상황이 많다.

- 둘 다 비슷함
- 둘 다 별로임
- 실수로 클릭함
- 선택하기 어려움

현재 구조에서는 이런 상황을 표현하기 어렵다.

## 추천 개선

### 3단계 선택

```text
A가 좋음
비슷함
B가 좋음
```

추가로

```text
← 이전 선택 수정
```

기능도 추천한다.

Estimator도 다음처럼 확장할 수 있다.

```python
winner = "a" | "b" | "tie"
```

tie를 지원하려면 Davidson 모델이나 Bradley-Terry with ties 계열로 확장하는 방안도 고려할 수 있다.

기획적으로도 다음과 같은 강점이 생긴다.

> 사용자의 불확실한 선택을 억지로 이진 선택으로 강제하지 않는다.

# 7. 8회 고정 질문보다 Adaptive Stopping 추천

현재 구조는 최대 질문 횟수를 기준으로 동작한다.

하지만 사람마다 필요한 질문 수는 다르다.

예를 들어

```text
사용자 A
3~4회만으로 명확한 선호 확인
```

반면

```text
사용자 B
8회를 진행해도 일부 축 불확실
```

일 수 있다.

## 추천 방식

```text
모든 주요 축 certainty > 0.65
→ 조기 종료

최대 질문 수 8회 도달
→ 강제 종료
```

또는

```text
최근 2회 질문 후 선호 순위 변화 없음
→ 종료
```

등이 가능하다.

이 기능은 프로젝트 핵심 주장인

> 더 적은 사용자 노력으로 개인화한다

와 매우 잘 맞는다.

예를 들어 실험 결과가

> 평균 5.3회 비교만으로 개인화 완료

처럼 나온다면 발표에서 상당히 강한 결과가 된다.

# 8. 팀 기능의 중요한 문제

현재 팀 기능은 여러 팀원의 comparison을 하나의 estimator에 합쳐 계산하는 방식이다.

예를 들어:

```text
A 사용자: 8회
B 사용자: 8회
C 사용자: 3회
```

라면 A와 B가 C보다 더 큰 영향력을 갖게 될 가능성이 있다.

더 심한 경우

```text
A 사용자: 20회
B 사용자: 5회
```

라면 A 사용자의 선택이 팀 preference를 크게 좌우할 수 있다.

## 추천 방식

각 개인을 동일한 비중으로 계산하는 구조를 추천한다.

예:

```text
개별 estimator
    ↓
utility normalize
    ↓
멤버별 weight = 1/N
    ↓
team utility
```

또는 개인별 1위 선택을 이용한 majority vote 방식도 가능하다.

추가적으로 팀 UI에는 다음 정보를 보여주는 것이 좋다.

```text
팀 합의도 87%
소수 의견 존재
```

또는

```text
Strict Typing
합의도 100%

함수 분리
합의도 50%
논의 필요
```

이렇게 만들면 팀 기능의 제품 가치가 더 명확해진다.

# 9. 보안/서버 쪽은 비교적 잘 구성됨

서버 코드를 보면 다음과 같은 방어가 들어가 있다.

- 요청 body 크기 제한
- 잘못된 Content-Length 처리
- CORS allowlist
- SameSite cookie
- Origin 기반 CSRF 방어
- Proxy 환경의 `X-Forwarded-For` 처리
- 로그인 brute-force 제한
- 일일 API quota
- 최적화 횟수 제한

캡스톤 프로젝트 수준에서는 보안 측면을 꽤 꼼꼼하게 고려한 편이다.

따라서 앞으로는 보안 기능을 더 늘리는 것보다 연구 검증과 사용자 실험 쪽에 투자하는 것이 더 효율적이다.

# 10. 개인정보 보호도 코드 수준에서 고려됨

피드백 로그에서 사용자 원문이나 생성 결과를 그대로 저장하지 않고, 숫자 형태의 정보만 전달하도록 제한하는 구조가 있다.

이 부분은 발표에서 다음처럼 설명할 수 있다.

## Privacy by Design

> 사용자 원문이나 생성 결과를 피드백 로그에 남기지 않고, 수치형 메타정보만 저장하도록 코드 수준에서 제한했다.

이 점은 단순 문서상의 약속이 아니라 실제 구현으로 보완되어 있다는 점에서 강점이다.

# 11. 현재 실험에서 가장 큰 약점

현재 실험 결과는 요약하면 다음 방향이다.

- 일반 프롬프트 대비 개인화 방식은 우세
- 일부 내부 metric에서는 개선
- ROUGE-L에서는 비교군 대비 큰 유의차가 없는 경우도 존재
- 강한 사용자 작성 프롬프트와는 비슷한 수준

따라서 현재 프로젝트의 가장 좋은 주장은

> 더 좋은 결과를 만드는 시스템

보다는

> 비슷한 수준의 개인화 결과를 더 적은 사용자 노력으로 얻는 시스템

이다.

문제는 그러면 이제 핵심 metric이

> 사용자 노력

이 되는데, 이를 실제 사용자 대상으로 충분히 측정해야 한다.

# 12. 가장 추천하는 추가 실험: User Effort Study

실제 사용자 20~30명을 대상으로 다음 두 조건을 비교하는 것을 가장 추천한다.

## 조건 A: 직접 프롬프트 작성

> 원하는 AI 응답 스타일을 직접 설명하세요.

## 조건 B: 현재 시스템 사용

> A/B 비교 선택을 통해 취향을 설정하세요.

## 측정할 값

- 설정 완료 시간
- 사용자가 직접 입력한 문자 수
- 클릭/선택 횟수
- 주관적 피로도
- 결과 만족도
- 선호 반영 정도
- 다시 사용할 의향

예시 결과:

| 항목 | 직접 작성 | A/B 선호 학습 |
|---|---:|---:|
| 평균 설정시간 | 164초 | 62초 |
| 사용자 입력량 | 238자 | 0자 |
| 평균 선택 횟수 | - | 6.1회 |
| 만족도 | 4.1 | 4.0 |

이런 결과가 나온다면 프로젝트의 존재 이유가 매우 명확해진다.

즉

> 동일한 수준의 개인화 만족도를 더 적은 입력과 시간으로 달성

이라는 강한 주장을 할 수 있다.

# 14. 프로젝트 명칭/정의도 한 단계 확장 가능

> 프롬프트 생성기

라고 보기보다 실제로는

## 추천 프로젝트 설명

기존:

> 선택 기반 프롬프트 자동 생성 도구

> 쌍대 비교 기반 LLM 사용자 선호 추론 및 프롬프트 개인화 시스템

핵심 기술 흐름:

```text
사용자 선택
→ Preference Elicitation
→ Preference Modelling
→ Adaptive Questioning
→ Prompt Personalization
```

이 구조로 설명하면 연구적인 무게가 더 좋아진다.

# 17. 지금 가장 효율적으로 해야 할 작업

현재 단계에서 새로운 기능을 무작정 늘리기보다 다음 네 가지를 우선하는 것이 좋다.

1. `learning_rate / min_weight` ablation
2. tie + 선택 수정 기능
3. adaptive stopping
4. 실제 사용자 A/B 실험

특히 4번이 가장 중요하다.

최종적으로 프로젝트가 다음 주장을 할 수 있게 만드는 것이 가장 강하다.

> 본 시스템은 쌍대 비교 기반 선호 추론을 이용해 사용자가 직접 복잡한 프롬프트를 작성하지 않아도 개인화된 AI 응답 선호를 설정할 수 있으며, 직접 프롬프트 작성 방식과 비교해 더 적은 입력과 시간으로 유사한 수준의 개인화 만족도를 제공한다.

이 방향이 현재 프로젝트에서 가장 설득력 있는 연구 및 기획 방향이다.

# 기본 조립본의 기능 저하는 어디서 오는가 — 4차 실행 전 판단 기준 (2026-11-04)

이 문서는 **과제 고르기와 확증 생성을 하기 전에** 커밋한다. 결과가 나온 뒤 기준을 바꾸지 않는다. 바꿔야 하면 문서 끝
변경 기록에 이유와 함께 적고, 바꾼 기준으로 낸 결과는 확증이 아니라 탐색으로 보고한다.

## 왜 묻는가

서비스가 주는 기본 조립본 (b) 의 기능 통과율이 프롬프트 없음 (a) 보다 낮았다: 2차 과제 -0.1667 [-0.3, -0.0333]
(재채점), 3차 과제 -0.0667 [-0.1333, -0.0167], 1차 과제 -0.0167 [-0.1333, 0.1] (README "코딩 프롬프트 검증").
(b) 는 "역할·과제 문장 + 선호 절 + 항상 지킬 것 + 출력 형식"이다. 선호를 반영하는 대가인지(선호 절), 프롬프트의
나머지 틀 때문인지 가른다. 3차는 과제가 쉬워 (a) 가 100% 를 통과해 차이를 재기 어려웠다 - 이번에는 중간 난이도
과제를 먼저 고른다.

## 묻는 것 (모두 확증 결과에만 적용)

1. **Q1 재현**: (b)−(a) 기능 통과율 차이의 95% 구간 상한 < 0 이면 "기본 조립본이 기능을 낮춘다".
2. **Q2 선호 절**: (b)−(s) 의 95% 구간 상한 < 0 이면 "선호 절이 기능을 낮춘다".
3. **Q3 나머지 틀**: (s)−(a) 의 95% 구간 상한 < 0 이면 "선호 절을 뺀 틀이 기능을 낮춘다".

셋 다 결과 파일의 `summary.findings` 가 기계적으로 계산한다. 아니면 "이 설계로 확인되지 않았다"로 적는다. 제품 문구를
바꿀지는 이 결과를 보고 팀이 정한다 - 이 문서는 근거만 낸다.

## 설계 (고정)

| 항목 | 값 |
|---|---|
| 조건 | (a) 시스템 프롬프트 없음 (b) 기본 조립본 (s) (b) 에서 선호 절("## 이 사용자의 선호" 부터 다음 머리말 전까지)만 뺀 것 |
| 생성 모델 | `openai/gpt-4o-mini` |
| 언어 | `ko` 최종 프롬프트 |
| 프로필 · 선택 이력 | 1~3차와 같은 4개 프로필, 같은 가상 사용자 |
| temperature | 0.7 |
| 실행 검사 | `evaluate_trial.evaluate_candidate` (32977ae 진입 파일 수정 포함) |
| 분석 단위 | 프로필 × 과제 × 반복. (a)·(s) 는 프로필끼리 같은 출력을 공유한다 - 단위가 독립이 아니어서 부트스트랩 구간이 실제보다 좁을 수 있다. 결과에 그대로 적는다 |

### 과제 고르기 (사전등록 규칙)

후보 8개(`benchmarks/coding_ai_quality/v7.json`, split `pool_v4`)는 생성을 한 번도 돌리지 않았다. 시나리오는 정답 통과·
한 군데 틀린 변형 실패·역할별로 나눈 답 통과를 먼저 확인했다(`tests/test_runtime_scenarios_v7.py`, 8과제 모두 처음 시도에서 통과).

1. 후보 8개에서 (a)·(b) 만 반복 0 으로 생성한다(최악 40회).
2. 과제마다 (a) 1개 + (b) 4개를 합친 기능 통과율을 잰다.
3. 그 값이 **0.4 이상 0.85 이하**인 과제만 남기고, **0.6 에 가까운 순서**(같으면 v7 순서)로 **최대 5개**를 고른다.
4. **3개 미만이면 확증을 돌리지 않고** 그대로 보고한다.

고르기 규칙은 (a)(b) 를 합친 통과율로만 정해 (b)−(a) 차이 자체로 고르지 않는다. 확증은 **반복 1~3** 을 새로 생성해,
고르기에 쓴 반복 0 출력을 다시 쓰지 않는다. 그래도 "중간 난이도"로 고른 과제라는 사실은 결과 해석에 남긴다.

### 단계와 명령

```bash
python -m experiments.function_cost_comparison --phase select                          # 사전 확인 (호출 0회)
python -m experiments.function_cost_comparison --phase select --execute --max-api-calls 40 --output-name fc_select
# 원문 검토 (data/function_cost_outputs/) 후 실행 검사, 호출 0회 → 과제 고르기
python -m experiments.function_cost_comparison --phase select --cached-only --behavior --reviewed-outputs \
    --output-name fc_select_behavior
# 확증 (생성 → 검토 → 실행 검사)
python -m experiments.function_cost_comparison --phase confirm --tasks-from fc_select_behavior --execute \
    --max-api-calls 90 --output-name fc_confirm
python -m experiments.function_cost_comparison --phase confirm --tasks-from fc_select_behavior --cached-only \
    --behavior --reviewed-outputs --output-name fc_confirm_behavior
```

### 호출과 비용 (실행 전 추정, 청구액 아님)

| 단계 | 최악 요청 수 (상한) |
|---|---|
| 고르기 | 40 = 8과제 × ((a) 1 + (b) 4) |
| 확증 | 90 = 5과제 × 3회 × ((a) 1 + (s) 1 + (b) 4) |

1~3차 실측 기준 생성 1회 ≈ 입력 700 / 출력 450 토큰. 잔액·청구 금액은 확인하지 않는다. 긴 실행은 `caffeinate -i` 로
돌린다(3차에서 잠자기로 15행이 끊겼다).

## 지표

- **기능 통과율** (주 지표): tsc 타입 검사 + esbuild 빌드 + 과제의 고정 jsdom 시나리오를 모두 통과한 비율. 실행하지 못한
  출력은 분모에 남기고 통과로 세지 않으며 미확인 수를 따로 적는다.
- **축 검사 통과율** (보고용): (s) 는 선호 절이 없으므로 축 검사가 낮을 것으로 예상한다 - 조작 확인으로만 본다.
- 짝지은 차이와 95% 부트스트랩 구간 (단위 복원추출 2,000회, 시드 0).

## 누락 처리

- 생성 오류 행은 같은 명령을 다시 실행해 한 번만 재시도한다(완료된 행은 캐시를 탄다). 남은 누락은 조건별로 보고하고
  짝 비교에서는 두 조건이 다 있는 단위만 쓴다.
- 결과를 본 뒤 단위·과제를 빼지 않는다. 고르기 규칙을 결과를 보고 바꾸지 않는다.

## 이 결과가 말하지 않는 것

- 실제 사람의 선호, 임의 입력에 대한 기능 동일성, 사용자 만족, 다른 모델·언어·도메인으로의 일반화.
- Q2 가 성립해도 선호 절의 어느 줄(코드 구성·스타일 관리·타입)인지는 가르지 못한다. 프로필별 차이는 탐색으로만 본다.
- 확증 60단위(프로필 4 × 과제 5 × 3회)는 작다. 과제·프로필 단위의 작은 차이는 결론으로 쓰지 않는다 (절대 규칙 11).

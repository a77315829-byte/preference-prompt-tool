# Preference Prompt Tool

## 사용자 선호 기반 맞춤형 프롬프트 자동 생성 도구

**마음에 드는 결과를 고르고, 내 답변 방식을 프롬프트로 만들어 다음 작업에 다시 사용합니다.**

AI에게 매번 “짧게 설명해 줘”, “코드는 역할별로 나눠 줘”라고 반복해서 말하는 대신,
예시를 비교하거나 원하는 방식을 선택해 나만의 지침을 만듭니다.
개인은 만든 지침을 보관하고 재사용하며, 팀은 공통 기준과 다른 항목을 확인하고
작업 맥락·자료·사용한 프롬프트를 다음 담당자에게 전달할 수 있습니다.

**현재 검증의 중심(2026-11-10): 문서 요약의 조건 준수와 내용 보존.** 일반 요청·조건을 잘 적은 수동 프롬프트·서비스가 조립한 프롬프트를 같은 원문에서 비교합니다. MACSum 영어 원문과 독립 Codex 보조 에이전트를 사용하며 유료 모델 API는 호출하지 않습니다. [실험 조건·결과·재현 자료](benchmarks/summary_agent_pilot/README.md). 개인 선호를 정확히 찾아낸다거나 사람의 시간·노력을 줄인다는 주장은 하지 않습니다.

기본 요약 지침은 핵심 사건·결과/목적·중요 수치·불확실성을 먼저 보존하도록 보완했습니다.
표현 겹침의 불필요한 상한을 없애고 완전 발췌를 원문 문장과 대조합니다.
[사용하지 않았던 원문에서 수동·수정 전·수정 후 비교](benchmarks/summary_agent_revision/README.md)에 근거와 한계를 기록합니다.

[실패 성찰 후보의 분리 평가](benchmarks/summary_reflection/README.md)는 관찰한 원문 18개를 개선용으로만 쓰고,
새 후보 확인용 6개·최종 평가용 18개를 구분했습니다. 보충 지침 후보는 최종 평가에서 현재 지침보다 핵심 명제
1개를 더 보존했지만 후보 확인에서는 1개가 줄어 기본 지침을 교체하지 않았습니다. 유료 API·실제 GEPA 실행 없이
보조 에이전트로 비교한 결과이며, GEPA 필수화나 사람의 선호·편의성 개선 근거로 사용하지 않습니다.

[실제 GEPA 후속 비교](benchmarks/summary_gepa_offline/README.md)는 설치된 GEPA 탐색과 독립 보조 에이전트를 연결해
유료 모델 API 없이 실행했습니다. 이전 원문을 제외한 개선 6개·후보 선택 6개·최종 평가 9개를 분리했습니다.
GEPA는 현재 지침을 유지했습니다. 새 원문에서 현재본과 비채택 GEPA 후보는 조건을 모두 통과했고 핵심 명제는
각각 22/27·20/27, 사실 문제 표시는 1/9·0/9였습니다(두 익명 검토자 동일). 일반적인 우위나 필수화 근거로
해석하지 않으며 자동 문장 수 검사의 약어 오인과 의미 검토 결과를 분리해 기록했습니다.

이후 [평가 오류·조건 충돌 수정 비교](benchmarks/summary_contract_revision/README.md)에서 약어 문장 구분을 v3로 보완하고,
요약 완료 화면에 **이번 원문의 조건 충돌 확인**을 추가했습니다. 짧은 완전 발췌에 선택 문장이 너무 많으면
분량 확대·재서술·일부 생략 중 사용자가 고른 부분만 바꾸며, 선택 전에는 새 작업용 지침을 만들지 않습니다.
새 원문 9개에서 수동·현재·수정본 모두 조건 9/9, 핵심 명제 25/27로 동률이었습니다(두 독립 검토자 동일).
모든 방식에 같은 보존 대상과 해결된 조건을 제공한 제한된 비교이며 수정본의 우위로 해석하지 않습니다.
기본 지침은 유지하고, 확인한 작업용 지침은 별도로 복사합니다. 유료 모델 API는 호출하지 않았습니다.

코딩 도움의 `AI 답변 방식 설정`과 `React 코드 스타일 비교`는 유지합니다. 코딩은 지정한 답변 조건의 전달·재사용·검증을 확인하는 확장 사례입니다. [코딩 목표·완료 기준](docs/coding-verifiable-goal.md), [검증 지침 프로토타입](benchmarks/coding_contract_v1/README.md). 사람의 편의성 평가는 [선택적 후속 계획](docs/coding-preference-usability-plan.md)으로 남깁니다.
기존 일부 과제 검사가 현재 코딩 전체의 정확도를 입증하지는 않습니다. [코딩 검증 범위 재점검](docs/history/coding-validation-audit-2026-11-10.md)에서 현재 제품·프로토타입·과거 실험을 구분합니다.

[현재 TypeScript/React 지침의 새 과제 비교](benchmarks/coding_react_current/README.md)(2026-11-12)는 실제 4항목 지침을
일반 요청·같은 조건의 수동 지침과 비교했습니다. 새 합성 과제 8개씩, 첫 응답 24개 모두 strict 타입 검사와
React/JSDOM 동작 검사(방식별 69/69)를 통과했습니다. 네 답변 조건 모두 일치는 일반 0/8·수동 8/8·제품 8/8로
두 독립 검토자가 일치했습니다. 일반 요청에는 해당 선호를 주지 않았으며 수동보다 우수하거나 기능 정확도가
향상됐다는 결과는 아닙니다. 수동·제품 응답 각 1개의 일본어 주석도 따로 기록했습니다.
유료 모델 API 없이 진행했으며 별도 React 코드 스타일 비교·사람의 편의성·수정 시간은 이 결과에 포함하지 않습니다.

## 해결하려는 문제

| 사용자가 겪는 문제 | 이 도구의 접근 |
|---|---|
| 원하는 답변을 말로 설명하기 어렵다 | 같은 작업의 두 결과를 비교하면서 선호를 선택한다 |
| 새 대화마다 같은 요구를 반복한다 | 답변 방식을 프롬프트로 보관하고 실제 작업 요청과 함께 복사한다 |
| 개인 취향과 팀의 작업 기준이 다르다 | 차이를 확인하고 이번 작업에서 따를 기준을 항목별로 고른다 |
| 담당자가 바뀌면 맥락과 자료를 다시 설명한다 | 목적·진행 상황·남은 일·참고 자료·사용 지침을 함께 넘긴다 |

개인적으로 AI를 자주 사용하는 사람, 학생·사이드 프로젝트 구성원, 소규모 개발팀과 다음 담당자를 대상으로 합니다.
시간 절감과 협업 효과는 앞으로 사용자에게 확인할 가설이며, 기능 구현만으로 입증됐다고 설명하지 않습니다.

## 사용하는 흐름

1. **내 방식 찾기**: 문서 요약 예시나 코드 A/B를 비교합니다. 코딩은 언어·프레임워크와 답변 방식을 직접 고를 수도 있습니다.
2. **프롬프트 만들기**: 고른 방식과 AI에게 붙여넣을 실제 지시문을 구분해 확인합니다.
3. **보관하고 다시 쓰기**: 이름을 붙여 내 선호 보관함에 저장하고 새 작업에 사용합니다.
4. **팀 기준과 연결하기**: 지원하는 분류에서 개인용·팀용을 비교하거나 항목별 작업용을 조합합니다.
5. **다음 사람에게 넘기기**: 진행 상태·자료·지침을 저장하고 받을 계정을 지정해 인수인계합니다.

문서 요약의 원문은 공백 포함 12,000자까지 입력합니다. 초과 내용을 자동으로 자르지 않고,
입력란에 남겨 직접 줄이거나 나누도록 안내합니다. 완료 화면의 **이번 원문의 조건 충돌 확인**은
원문 문장 부족·보존할 문장과 분량 상한의 충돌을 확인하고, 사용자가 바꿀 조건을 고른 뒤 지침을 만듭니다.
이 조건 확인에는 AI 호출이 없습니다. [길이 정책·충돌 처리 및 검증 범위](docs/history/2026-11-12_summary_length_policy.md)를 참고하세요.

새 코딩 결과와 저장한 코딩 지침에서도 **팀 기준 연결 → 도구 적용 → 실제 작업 비교**를 열 수 있습니다.
설명·주석·구성·출력의 네 항목으로 새 팀을 만들고, 팀장이 정한 기본값·필수 규칙과 개인 선택을 비교합니다.
다른 항목은 따를 쪽을 직접 고르고, 조합과 당시 출처를 새 개인 항목으로 보관합니다.
문서 요약·기존 TypeScript/React의 투표 기반 팀 기록은 별도로 유지합니다.

- **도구 적용**: AGENTS.md, CLAUDE.md, Copilot, Cursor, Markdown 파일을 미리 보고 내려받습니다. 기존 내용을 붙이면 표시한 생성 영역만 교체하는 차이를 확인합니다. 자동 설치·덮어쓰기는 하지 않으며, Cursor의 기존 적용 범위는 자동 병합하지 않습니다.
- **실제 작업 비교**: 같은 과제·도구·모델·기준 커밋에서 일반 지침과 선택한 지침을 비교합니다. 준비·응답 대기와 수정·검사 시간, 기능 통과/실패/미확인/진행 불가, 선호 이유를 독립적으로 기록합니다. TypeScript/React 버그 수정·기능 추가의 검사 안내를 제공합니다.
- **기록과 한계**: 계정별 SQLite에 지침·작업·시간·직접 확인 근거를 보관하고 JSON으로 내려받습니다. 타이머는 창을 닫아도 계속되므로 자리 비움 전에 멈춥니다. 최초 선호 선택 시간은 제외하며, 기능 결과는 사용자 확인 기록이고 자동 실행 점수가 아닙니다. 이 세 기능에는 모델 호출이 없습니다. 평소 AI 도구를 별도로 실행할 때의 비용은 그 도구의 요금에 따릅니다.

구현 범위와 실사용 측정 절차: [2026-11-09 연결 기록](docs/history/2026-11-09_coding_workflow.md).

분량과 원문 표현을 어느 정도 유지할지 선택하면 다음 문서에도 쓸 수 있는 요약 지침을 만듭니다.

### 코드 예시를 보면서 선호 선택

언어와 프레임워크를 고른 뒤 **설명 방식·주석 정도·코드 구성·코드 출력**을 직접 고릅니다. 이름만으로 판단하기 어렵다면 코드 예시 비교를 선택할 수 있습니다.
새 비교(version 4)는 주문·대여 맥락에서 **최대 8회**이고, 1회 이상 응답한 뒤 언제든 **여기까지 비교하고 선택 확인하기**로 마칠 수 있습니다. 최소 8회를 요구하지 않습니다.
결과에는 **1회 선택(반복 확인 전)·반복 일치·엇갈림·선택 부족**을 구분합니다. 한 번 고른 값은 보존하되 반복 일치로 표시하지 않습니다. 미비교·보류·엇갈림으로 값이 정해지지 않은 항목은 기본값으로 채우지 않으며 직접 골라야 지침을 만듭니다.
8회는 사용 부담을 제한하는 상한이며, 취향을 충분히 복원하는 최적 횟수로 검증된 값은 아닙니다.
기존 version 1/2의 단일 비교와 version 3의 8~10회 기록은 원래 방식으로 읽고 재사용합니다. 새 비교 방식으로 재해석하지 않습니다.
아래 기존 화면 캡처는 네 항목 단일 비교 때의 모습이며, 현재 화면은 진행 횟수와 반복 선택 근거를 추가로 표시합니다.

## 기능별 지원 범위 요약

| 기능 | 현재 제공하는 내용 |
|---|---|
| 문서 요약 | 한국어·영어 결과 비교, 길이·표현 선호를 반영한 프롬프트 생성 |
| GEPA로 코딩 지침 다듬기 | 원본 환경·선호를 고정하고 보충 안내를 탐색한 뒤 전후 답변을 비교하고 채택한 후보를 새 항목에 저장 |
| 받은 AI 답변 직접 확인 | 설명·주석·구성·출력의 단서를 확인하고 사용자가 적합성을 직접 판단 |
| 업무 템플릿 | 회의·문서·개발·인수인계용 24개 초안의 검색·복사·점검. 그중 기존 6개는 선택 비교 지원 |
| 요청문 점검 | 역할·조건·출력 형식 등 빠진 요소 확인. AI 수정안은 실제 생성 모드에서 별도로 요청 |
| 반복 업무 지침 만들기 | 입력·규칙·출력 형식을 정리해 프로젝트로 저장·공유. 실시간 공동 편집이나 자동 합의 기능은 아님 |

GEPA는 Python의 **FastAPI·Flask·Django**, Java의 **Spring Boot**,
JavaScript/TypeScript의 **React·Express·Vue·Next.js**, TypeScript의 **NestJS**까지 **13개 조합**에 연결되어 있습니다.
현재 코딩 GEPA는 환경마다 개선용 2개·후보 선택용 2개·별도 확인용 2개의 준비 과제를 사용합니다.
더 나은 후보를 확인하지 못하면 원본을 유지합니다.

평가는 제한된 코드 구조·계산식·설명/출력 형식 검사입니다.
새 코딩 GEPA 경로는 생성 코드를 실행하지 않으며 실제 서버·브라우저 동작·타입·보안·사용자 만족도를 검증한 결과가 아닙니다.
주석과 역할 구성의 적절함은 사람이 실제 답변을 보고 확인합니다.
참고 점수는 범용 프롬프트 품질이나 성공률을 의미하지 않습니다.

```mermaid
flowchart LR
    U[사용자 선택] --> S[선호 추정 또는 명시적 설정]
    S --> P[재사용할 프롬프트]
    P --> L[개인 보관함]
    P -. 선택 기능 .-> G[GEPA 후보 탐색과 전후 확인]
    G --> L
    L --> W[새 작업에 사용]
    T[지원 분류의 팀 기준] --> W
```

| 영역 | 주요 구성 |
|---|---|
| 웹 화면 | React·JavaScript/TypeScript·Vite, 기능별 컴포넌트와 파스텔 선택 UI |

언어 모델 자체를 학습하거나 파인튜닝하는 프로젝트가 아닙니다.
기존 추정 엔진과 새 명시적 선택 흐름을 구분하며, 새 도메인의 표현·검사 설정은 공통 엔진과 분리합니다.
현재 서비스에서 AWS 화면·조회 API·템플릿은 제외했고 과거 실험 자료만 기록으로 보존합니다.

## 코딩 개인화의 근거와 아직 검증하지 않은 것

- [Configurable AI Coding Assistants (FSE Companion 2026)](https://arxiv.org/abs/2607.09215)는 전문 개발자 56명의 설문과 7개 디자인 세션에서 응답 길이 등 작업 관련 설정 수요를 보고합니다. 개인화 기능의 필요성을 뒷받침하지만 이 프로젝트의 네 항목·선택 횟수·생성 지침의 효과를 검증하지는 않습니다.
- [Understanding User Mental Models (IJHCS 2025)](https://doi.org/10.1016/j.ijhcs.2025.103648)는 학생 중심 56명이 참여한 8개 워크숍에서 코드 제안·설명·개인화에 대한 기대를 조사했습니다. 원하는 상호작용에 관한 정성 근거이며 실제 생산성 향상의 대조 실험은 아닙니다.
- [CodeUltraFeedback (TOSEM 2025)](https://arxiv.org/abs/2403.09032)는 설명·가독성·스타일 등 코딩 선호를 기능 정확도와 구분해 평가하는 연구입니다. AI 평가로 만든 선호 데이터와 모델 미세조정을 사용하므로, 우리 도구의 사용자 선호 추정이나 시스템 프롬프트 효과의 직접 증거로 사용할 수 없습니다.
- [GEPA (ICLR 2026)](https://arxiv.org/abs/2507.19457)는 실행 결과에 대한 언어적 성찰로 프롬프트를 탐색하는 방법의 근거입니다. 개인별 코딩 만족도나 8~10회의 적정성을 검증한 논문은 아닙니다.

현재 주장할 수 있는 범위는 **준비된 예시의 반복 선택을 기록하고, 사용자가 확인한 네 가지 답변 방식을 지침에 반영한다**는 것입니다.
서로 다른 실제 프로젝트에서 그 지침이 더 유용한지는 아직 확인하지 않았습니다. 주문·대여 예시도 비슷한 계산 구조라 과제 다양성에 한계가 있습니다.

다음 검증은 React 실제 수정 과제로 일반 요청·사용자가 직접 만든 짧은 체크리스트/설정·선택적 예시 비교로 만든 지침을 비교합니다. GEPA는 별도 단계로 두어 선택 과정의 효과와 섞지 않습니다.
먼저 실제 개발자 3~5명의 탐색적 파일럿으로 계속 투자할 만한 신호와 측정 가능성을 확인하고, 효과를 확정할 본실험 표본수는 별도로 설계합니다.
조건 순서를 균형 있게 배치하고 선택에 쓰지 않은 과제로 기능 테스트, 블라인드 선호, 초기 설정 시간, 요청 준비·검토·수정 시간, 추가 질문 횟수, 요청 비용·대기 시간을 따로 기록합니다. 현재 작업 비교 타이머에는 초기 선호 설정 시간이 포함되지 않으므로 별도 기록이 필요합니다.
사용자별 차이를 반영한 구간 추정과 실패 사례를 보고하며, 선호 점수 상승이 기능 저하를 가리지 않게 합니다. 이 실험은 아직 실행하지 않았습니다.

현재 운영 보완: 코딩·인수인계 초안은 계정별로 이 탭에 24시간 임시 보관하고 로그아웃 시 제거합니다.
GEPA 작업은 SQLite에 7일간 임시 보관하며, 재시작으로 중단된 작업은 유료 호출을 자동 재실행하지 않습니다.
계정 팀의 결과는 참여자에게만 공개하고 초대는 7일 만료·팀장 닫기를 지원합니다. 익명 팀은 공개 체험용입니다.
기존 Streamlit 예약 검사는 중지했고, `smoke-live.yml`은 명시한 React 서비스의 API·정적 파일을 검사하는 수동 워크플로입니다. 브라우저 상호작용 검사는 별도입니다.

## 인터넷에 올려서 사용하기

`microstone` 브랜치에는 화면과 API를 한 주소에서 실행하는 Docker 설정이 있습니다.
영구 디스크에 보관함·인수인계·첨부와 캐시를 저장하고, 이후 원하는 도메인을 연결할 수 있습니다.
실제 AI 호출은 처음에는 꺼 둡니다. 서버 설정을 준비한 상태이며 공개 서비스가 이미 운영 중이라는 뜻은 아닙니다.

`render.yaml`은 **유료 선택지**입니다. 서버와 1GB 디스크의 기본 요금은 월 **$7.25**이며 세금·초과 사용량·AI·도메인 비용은 별도입니다.
[Render 유료 구성을 검토하는 화면](https://render.com/deploy?repo=https%3A%2F%2Fgithub.com%2Fa77315829-byte%2Fpreference-prompt-tool%2Ftree%2Fmicrostone)에서 생성 전 금액을 확인합니다.
무료 가상서버를 사용한다면 같은 Docker 이미지와 영구 볼륨을 사용할 수 있으나, 무료 할당 가능 여부와 운영 조건을 먼저 확인해야 합니다.

[배포 설정·도메인 연결·데이터 유지 안내](docs/DEPLOYMENT.md)

## 로컬 실행

Python **3.12**, Node.js **20.19+ 또는 22.12+**가 필요합니다.
PowerShell에서 서버와 화면을 각각 실행합니다.

```powershell
# 터미널 1: 처음 설치 및 API 서버
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
$env:PPT_LIVE="0"
.\.venv\Scripts\python.exe -X utf8 api_server.py
```

```powershell
# 터미널 2: React 화면
npm ci --prefix frontend
npm run dev --prefix frontend
```

접속 주소는 `http://127.0.0.1:5173/`입니다. 기본 데모에서는 API 키 없이 예시 선택·지침 조립 흐름을 확인할 수 있습니다.
개인 보관함·작업 공유는 같은 로컬 서버의 계정을 사용합니다.
다른 컴퓨터에 링크를 전달하려면 상대도 접근 가능한 공통 서비스 주소가 필요합니다.

실제 생성과 GEPA에는 별도 모델 설정이 필요합니다.
환경별 실제 호출 스위치, 모델·요청 한도, 데이터 저장 위치는 [상세 사용 안내](docs/USER_GUIDE.md)를 참고하세요.
한도에 표시되는 요청 수에는 캐시 조회가 포함될 수 있어 실제 청구 횟수나 금액 상한과 같지는 않습니다.

```powershell
# 개발 환경 검사 — 유료 API 제외
.\.venv\Scripts\python.exe -X utf8 -m pytest -m "not api" -q
node --test "frontend/src/**/*.test.js"
npm run build --prefix frontend
```

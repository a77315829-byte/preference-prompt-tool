# 실패 성찰을 통한 요약 지침 개선 실험

유료 모델 API 없이 독립 Codex 보조 에이전트가 실패를 분석하고, 보충 지침을 제안한 뒤,
새 원문에서 수동 지침·현재 제품 지침·보충 지침을 비교한다. **GEPA 엔진 실행은 아니다.**
Codex 사용량은 소비되며 이 실행에서 토큰 계량값·실제 기반 모델 식별자는 노출되지 않았다.

## 결과와 결정 (2026-11-10)

**성찰 후보의 안정적인 우위는 확보하지 못했다. 현재 제품 지침과 선택적 GEPA를 유지한다.**
후보 확인용 6개에서는 current가 16/18, candidate가 15/18 명제를 보존했다(두 검토자 동일).
조건은 양쪽 모두 6/6 통과했으며 사실 문제 표시는 없었다. 후보 확인 단계에서 채택 기준을 통과하지 못했다.

최종 원문 18개의 핵심 명제는 총 54개다. 두 검토자의 원래 판단을 각각 보고한다.

| 지침 | 명제 보존: 검토 A | 명제 보존: 검토 B | 길이·표현 동시 통과 | 사실 문제 표시가 있는 출력 |
|---|---:|---:|---:|---:|
| 조건을 명시한 수동 지침 | 49/54 | 51/54 | 18/18 | 0/18 |
| 현재 제품 지침 | 50/54 | 51/54 | 18/18 | 0/18 |
| 성찰 보충 지침 후보 | 51/54 | 52/54 | 18/18 | 0/18 |

후보는 최종 평가에서 current보다 명제 1개 더 보존했다. 문서 단위로는 두 검토자 모두 1승·17동률·0패다.
수동 대비는 A가 2승·16동률, B가 1승·17동률이다. 단일 실행의 작은 차이이며 통계적 우위·동등성은 주장하지 않는다.
후보 확인 단계에서는 반대 방향의 차이가 있었고, 사전에 정한 +2개 개선 기준도 current 대비 충족하지 못했다.

두 검토자는 162개 명제 판단 중 158개에 동의했다. 차이 4개는 T10의 핵심 주장에 붙은 배경 대비를
필수로 볼지(세 방법 모두 동일한 쟁점), T18의 비유를 구체적인 역량 주장까지 보존한 것으로 볼지에서 나왔다.
사전 주석 검토가 있었어도 명제 해석의 모호함은 남았다. 유리한 판단만 골라 집계를 바꾸지 않았다.
[원래 집계](results/2026-11-10/final/scores.json), [쟁점 검토](results/2026-11-10/final/adjudication.json).

최종 입력 지침의 평균 공백 구분 단어 수는 수동 57.3, current 298, candidate 511이다.
후보는 213단어를 더 사용하지만 이 결과로 추가 지시의 지속적인 이득을 입증하지 못했다.
출력 평균은 각각 122.9·129.8·116.3단어다. 이는 토큰 비용·실제 모델 지연·사람의 수정 시간 측정이 아니다.

이번에 만든 것은 재실행 가능한 분리·고정·익명 평가·보수적 채택 절차와 연구용 후보다.
외부 유료 모델 API 호출 0회, 실제 GEPA 실행 0회, 요약 66개, 익명 검토 132개를 기록했다.
관련 회귀 검사 98개가 통과했다. 제품 프롬프트를 이 후보로 교체하거나 GEPA를 필수로 켜지 않았다.
코딩 기능과 기존 실험 자료도 그대로 유지한다.

## 분리와 고정

- 개선용: 이미 관찰한 `summary_agent_pilot` 9개와 `summary_agent_revision` 9개, 총 18개.
- 후보 확인용: 개선용 원문과 겹치지 않는 새 MACSum 영어 뉴스 6개.
- 최종 평가용: 앞선 24개와 겹치지 않는 새 원문 18개. 길이 3 × 표현 3 조건을 각각 2개 원문에 배정한다.
- 원문 조건: 250–800 공백 구분 단어, 데이터셋 원문 단위 8개 이상, 주제 조건 없는 참조가 있는 문서.
- 원문 전체 SHA-256 기준으로 중복을 제외하며 샘플링 시드와 데이터셋 해시를 기록한다.
  공개 데이터의 모델 사전학습 포함 여부·비슷한 사건의 기사 중복까지 배제했다는 뜻은 아니다.

후보 제안자는 개선용 자료만 본다. 후보는 한 번 제안한 213단어 보충 지침 하나로 제한했다.
후보 확인·최종 평가 결과를 보고 수정하거나 유리한 출력을 다시 생성하지 않는다.
최종 평가에서는 후보 확인을 통과하지 못해도 연구 조건으로 후보를 그대로 비교한다.
이 경우 제품 기본값을 후보로 바꾸지는 않는다.

`current`는 현재 `summarization_grounded_v2.yaml`을 `build_final_prompt`로 내보낸 실제 지침이다.
`manual`은 첫 파일럿의 조건을 명시한 수동 지침을 조건별로 그대로 재사용한다.
`candidate`는 current 끝에 [후보 보충 지침](candidate.json)을 붙인다.
지침 전체를 비교하는 실험이므로, 보충 지침이 길어진 효과와 내용 자체의 효과는 분리하지 않는다.

## 측정과 선택 규칙

생성 결과를 보기 전에 원문별 핵심 명제 3개와 정확한 근거를 작성한다. 후보를 모르는 별도 에이전트가
최종 평가 명제의 원문 근거·중심성·불필요한 세부 묶음을 검토한다. 주석도 AI 판단이며 사람 정답은 아니다.
최종 생성 전에 지침·원문·명제·기준·코드를 해시로 고정한다. 해시는 변경 탐지용 기록이며 외부 시점 인증은 아니다.

조건마다 새 맥락의 생성 에이전트가 첫 출력만 저장한다. 두 검토자는 방법 이름·지침·자동 점수·다른 검토를
보지 않고 익명 출력과 원문을 평가한다. 같은 계열 모델의 맥락 분리이며 사람 두 명의 검증과 동등하지 않다.

주요 항목은 서로 상쇄하지 않고 별도로 보고한다.

1. 길이와 표현 방식의 조건 준수.
2. 미리 정한 핵심 명제 보존 수(문서당 3개). 이는 원문 전체 내용의 보존율이 아니다.
3. 요약 전체에서 발견된 원문에 없는 주장·잘못된 수치·확정하지 않은 결과의 단정.

단어 겹침·자동 검사·출력 단어 수는 보조 지표다. 누락을 허위 주장과 동일하게 취급하지 않는다.
완전 발췌와 짧은 길이가 충돌하는 사례는 [주석 한계](results/2026-11-10/annotation_limits.json)에 남긴다.
특히 D01은 명제 3개가 최소 3개의 서로 다른 원문 문장을 필요로 하므로 2문장 안에 전부 담을 수 없다.

후보 확인 통과는 **검토자 두 명 모두** current보다 명제 보존이 2개 이상 증가하고, 조건 동시 통과 수가
줄지 않으며, 후보의 사실 문제 표시가 없어야 한다. 최종 채택 근거도 같은 조건을 수동·current 양쪽에
적용하고 후보 확인 통과를 요구한다. +2라는 문턱은 이 소규모 실험의 사전 결정 규칙이며 통계적 신뢰 보장은 아니다.
원래 검토 판단은 보존하며 사후 검토로 유리하게 채택 여부를 바꾸지 않는다.

## 실행·검사

```powershell
# 이미 기록된 실행은 덮어쓰지 않는다. 아래 생성/고정 명령은 새 실행 준비 절차다.
.venv/Scripts/python.exe -X utf8 -m benchmarks.summary_reflection.run sample
# 원문 주석·후보 작성 후
.venv/Scripts/python.exe -X utf8 -m benchmarks.summary_reflection.run freeze --stage selection
# 독립 생성의 첫 출력 수신 후
.venv/Scripts/python.exe -X utf8 -m benchmarks.summary_reflection.run blind --stage selection
# 두 익명 평가 수신 후
.venv/Scripts/python.exe -X utf8 -m benchmarks.summary_reflection.audit --stage selection
.venv/Scripts/python.exe -X utf8 -m benchmarks.summary_reflection.run score --stage selection
# 최종 원문 주석 검토 완료 후 같은 절차를 --stage final로 반복
# 저장된 실험의 변경 여부 확인
.venv/Scripts/python.exe -X utf8 -m benchmarks.summary_reflection.run verify --stage selection
.venv/Scripts/python.exe -X utf8 -m benchmarks.summary_reflection.run verify --stage final
```

Python 실행기는 모델을 호출하지 않는다. 생성과 의미 검토는 명시적으로 배정한 Codex 보조 에이전트만 수행한다.
캐시된 첫 출력·익명 평가·근거·각 검토자별 집계·판정은 `results/2026-11-10/{selection,final}/`에 있다.
동일 명령을 다시 실행해 결과를 덮어쓰거나 재생성하지 않는다.

## GEPA를 필수로 실행할지

GEPA는 실패 피드백에서 지침 후보를 제안하고 시험하는 최적화 방법이다.
이 제한된 성찰 절차는 그 아이디어를 시험하지만 GEPA의 탐색·후보 조합·모델 호출 경로는 실행하지 않았다.
[논문](https://arxiv.org/abs/2507.19457), [공식 구현](https://github.com/gepa-ai/gepa).

현재 요약 `service.optimize()`는 도메인 축의 자동 점수를 최적화하며 의미 보존 평가가 없다.
예시 문서가 trainset과 valset에 중복된다. 따라서 그 점수 상승은 새로운 원문에서의 내용 개선 근거가 아니다.
코딩 GEPA는 별도의 2/2/2 과제 분할과 제한된 정적 검사를 쓰므로 요약 경로와 혼동하지 않는다.
코딩의 별도 과제 결과는 보고되지만 그 결과가 나쁜 후보를 자동 탈락시키는 채택 조건은 아니다.

좋은 기본 지침을 오프라인에서 검증한 뒤 재사용하는 것과, 사용자 요청마다 GEPA를 돌리는 것은 다른 결정이다.
필수 실행에는 실제 GEPA를 사용한 반복 실험, 새로운 원문의 이득, 조건·사실성 악화 방지, 지연·호출량 측정,
개선이 없거나 실패할 때 원본으로 돌아가는 동작이 추가로 필요하다. 이번 실행은 그 근거를 대체하지 않는다.

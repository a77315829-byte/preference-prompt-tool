# 4단계: 생성 코드 실행 검증

2026-10-11 기준. 2단계에서 저장한 `data/coding_ai_quality_trial.json`의 원문을 다시 검사했습니다. **새 AI 호출은 없었고, 3단계 생성 지시 개선 이후의 새 결과도 아닙니다.** 두 모델의 우열이나 교체 여부를 판단하지 않습니다.

## 방법

- 코드 블록에서 파일을 추출해 프론트 프로젝트의 React 19·TypeScript 5.9 환경에서 각각 엄격 타입 검사와 번들을 실행했습니다.
- 타입 검사와 빌드를 모두 통과한 후보만 React·jsdom으로 렌더링해 `counter_reset`, `product_search`의 고정 수용 시나리오를 A/B에 동일하게 적용했습니다.
- 두 후보 모두 해당 시나리오를 통과하면 **검사한 시나리오에 한해** 동작이 일치한다고 기록했습니다. 모든 입력·접근성·시각적 결과의 동일성은 보장하지 않습니다.
- 원문 생성 코드를 로컬 Node에서 실행하므로 사전 검토가 필요합니다. 이 실행기는 보안 샌드박스가 아닙니다.

생성된 후보 8개 중 타입 검사 6개, 번들 빌드 8개, 고정 동작 시나리오 6개가 통과했습니다. 생성된 A/B 네 쌍 중 세 쌍은 검사한 시나리오에서 양쪽이 통과했습니다. **이는 4개 과제 전체의 합격률도, 일반적인 기능 동일성의 증명도 아닙니다.** 나머지 네 모델·과제 조합에는 실행할 수 있는 후보가 없었습니다.

후보 모델의 카운터 A/B는 React 19 타입 환경에서 `JSX.Element` 반환 타입에 대해 `TS2503: Cannot find namespace 'JSX'`가 발생했습니다. 번들 빌드는 되지만 현재 프로젝트 환경에서는 타입 검사를 통과하지 못하므로 동작 검사를 생략했습니다. 생성 지시나 검사 규칙에 React 19 호환 반환 타입(`React.JSX.Element` 또는 추론)을 반영할 필요가 있습니다. 과거의 원문 결과를 고쳐서 합격 처리하지는 않았습니다.

프론트 의존성 설치 후 저장소 루트에서 `python -m benchmarks.coding_ai_quality.evaluate_trial`을 실행하면 상세 판정이 `data/coding_ai_quality_stage4.json`에 기록됩니다. 자동 검사 자체는 `python -m pytest -q tests/test_coding_ai_quality_stage4.py tests/test_coding_ai_quality_benchmark.py tests/test_coding_domain.py`로 확인합니다.

다음에는 React 19 타입 호환 규칙을 생성 지시에 반영하고 **3단계 이후 버전**으로 제한된 재생성을 실시해야 합니다. 그다음 보류 과제와 실제 사용자 기능 입력을 별도로 시험하고, 사람이 A/B의 기능·스타일 차이와 화면 가독성을 검수해야 합니다. 기존 보류 과제는 이번 단계에서 사용하지 않았습니다.
